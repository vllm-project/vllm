# 可编程 KV 缓存：应用协同设计与实验分析

## 1. 从应用意图到缓存执行

多轮工具调用使一个会话跨越多个推理请求。工具等待期间，下一轮需要的缓存可能暂时没有请求引用；分支取消后，最近使用过的缓存也可能失去复用价值。[可编程 KV 缓存提案](https://github.com/vllm-project/vllm/issues/57103)希望利用应用掌握的生命周期信息，改善这两种情况中的缓存保留与资源安排。

提案划分了三方职责：应用知道哪些分支仍有价值、工具何时可能返回，以及任务将在哪里继续；引擎知道当前容量、真实缓存命中和正在运行的请求需求；存储连接组件负责数据传输并报告完成。应用提供明确的缓存操作或供策略使用的任务状态，引擎中的策略据此提出建议，再由引擎统一审批资源。多个策略需要同一段内容时共享一次物理加载，竞争不同内容时则由统一的容量核算决定哪些工作可以执行。

对应的[参考实现](https://github.com/vllm-project/vllm/pull/62382)允许控制动作随模型请求提交，也允许应用在工具等待期间独立发送。引擎将会话、分支和上下文范围解析为可复用内容，通过已有缓存管理器和 CPU/Mooncake 存储路径执行。Mooncake Store 在这里承担共享缓存存储：一个引擎保存的内容，可以由另一个兼容引擎加载；存储可访问与目标 GPU 已可使用是两个不同状态。

| 控制能力 | 实际行为 | 执行约束 |
| --- | --- | --- |
| 保留优先级 | 影响某段缓存被淘汰的顺序，并限定有效期 | 不承诺缓存永远占用显存，不能替代实际使用引用 |
| 复制 | 在主机存储或 GPU 中建立副本，保留源副本 | 目的空间先获批准，所需设备上的内容全部传输并登记后才可复用 |
| 迁出 | 先建立可恢复的存储副本，再回收允许释放的 GPU 源副本 | 仍被请求或传输使用的内容不能提前释放 |

会话与内容的关联独立于副本位置维护。缓存离开显存后，会话仍可声明后续需求；一个分支结束，也只解除自身的需求，不能破坏其他会话仍在使用的共享内容。传输可以延后、部分完成或失败，调用者得到实际效果后再决定重试或重算，不能把“已提交”当作“已准备好”。

原提案讨论过在指定期限内禁止普通淘汰的强保护，本实现提供可回收的优先级保留，不承诺这种强保护。跨引擎复用通过共享存储完成，未实现完整的跨机器请求分配系统。本文验证这些已实现能力及其调度策略，不将提案中的全部能力视为已经交付。

## 2. 两类调度怎样配合

### 2.1 容量与顺序调度

**容量与顺序调度**协调各会话可使用的缓存容量，以及等待请求的执行顺序。容量份额是软约束：空闲份额可以借用，等待过久时可以放宽份额限制，但请求仍须满足实际物理容量要求。它读取引擎当前状态，不需要逐次接收工具暂停预测，也不自行搬运缓存。

容量判断需要同时处理共享内容和生成增长。两个续写请求若共享一段已驻留前缀，后一个请求只需为新增部分分配空间；把共享前缀再次算作新增需求，会错误地延后原本能够执行的请求。运行中的请求还会随生成增长，因此当前空闲容量也不能全部分给等待者。实现先使用实际缓存查询结果计算新增分配量，再为运行请求保留增长空间，并在每个候选请求获准后更新容量判断。

请求顺序综合考虑可复用缓存量、已等待时间和重要性。复用较多的请求可以减少输入重算，等待优先级随时间增长则避免始终偏向同一类会话。实验使用 120 秒的份额等待预算和 30 秒的等待优先级增长尺度；前者只决定何时放宽份额限制，不保证请求一定在该时间内获得 GPU。

### 2.2 应用协同调度

**应用协同调度**在容量与顺序调度之上，增加应用状态驱动的缓存保留和搬运。缓存保留将重要性与保留期限转成淘汰优先级；按需搬运结合工具暂停、预计恢复时间和当前资源状态，决定是否迁出，以及何时预取。预取指请求使用缓存前，将所需内容加载到 GPU。

应用在工具开始执行时就提供预计暂停时间，使传输有机会与工具运行重叠。默认按调用的工具组合分别维护历史估计，用已经完成的暂停平滑更新，没有历史时从 0.25 秒开始。搬运规则同时参考已观测的存出与加载成本：长暂停可能提供传输窗口，短工具调用也可能因系统持续排队而留下可利用的等待时间。最终规则还要求当前有引用的缓存占用达到 KV 预算的 80%，再比较暂停或持续等待窗口与往返传输成本，最低窗口为 0.5 秒。已经观察到的等待仅作启发式信号，无法保证请求此后仍有等长的空闲窗口。

工具返回后，请求仍可能等待 GPU。如果大量内容过早加载，它们会占用其他请求所需空间，也可能在使用前再次被淘汰。存在排队竞争时，预取因此跟随调度器选中的会话启动，先检查完整前缀所需容量，并在准备期间保护已到位的部分。加载失败时请求可以重算；分支取消时撤销未消费的准备，但不会释放仍在传输中使用的缓冲区。

这些策略共享引擎的资源核算，不各自维护独立的可用空间。策略可以建议保留、搬运或调整请求顺序，实际分配、回收和可用性发布仍由引擎执行。

## 3. 实验方法

实验以 GSM8K 数学任务构造多轮工具交互。原生引擎使用 vLLM 已有的缓存与请求调度；容量与顺序调度只增加本地资源安排；应用协同调度再增加上一节的保留与搬运机制。这个递进对照用于观察本地调度的收益，以及应用信息与缓存搬运组合的额外收益。

| 项目 | 设置 |
| --- | --- |
| 模型与硬件 | Qwen3.8-27B，BF16，双卡 A100 80GB PCIe，张量并行 |
| GPU 资源 | 显存利用率 50%，每卡实际 KV 预算约 12.12 GiB，不设置额外的小容量 KV 上限 |
| 并发与上下文 | 并发上限 64，批次 token 预算 4096，最大上下文 16,384 token，启用编译与 CUDA graphs |
| 搬运的额外资源 | Mooncake 主机存储，存储区配置为 64 GB，传输缓冲区配置为 256 MB |
| 真实工具循环 | 采样温度 0.6、采样种子 0；每次生成最多 256 token，整条响应预算 2048 token，最多 6 次模型生成回合 |
| 计时范围 | 包含整批请求、并发排队、工具等待、控制结果收集和相关传输排空；不含服务启动、权重加载与显式预热 |

各组的 GPU 缓存预算相同，搬运组额外使用主机存储和传输 CPU，因此主对照衡量固定 GPU 资源下的系统收益，不代表相同总内存资源下的纯算法收益。搬运组关闭存储连接组件的自动查找与保存，由应用控制和策略触发传输；加载到 GPU 的内容随后参与引擎本地前缀复用。

从问题开始、经过工具调用直到最终作答的一串交互记为一条轨迹。共享同一组 48 条参考例题的轨迹构成一个前缀组。**压力负载**包含 64 个问题各 4 次采样、32 个前缀组，共 256 条轨迹、920 次模型调用、8,781,870 个输入 token 和 60,136 个输出 token。**容量充足负载**从记录中选择 4 个前缀组的 32 条轨迹，各复制为 8 个独立请求，共 256 条轨迹、864 次调用和 66,160 个输出 token。后者减少了竞争的共享内容，并非同一工作量的缩短运行。

性能比较采用固定工作量回放：每次调用的输入 token、输出长度和调用间暂停值固定，模型以温度 0 实际生成，但新尾部不进入后续记录输入，工具不重新执行。真实工具循环则实际执行问题查询和算术工具，并把新生成内容用于后续输入。两种方法分别检验固定任务量下的性能和自然生成中的速度、质量，结果不混算。

| 实验 | 负载与比较内容 | 重复次数 |
| --- | --- | --- |
| 主性能对照 | 压力负载，原生引擎、容量与顺序调度、应用协同调度 | 各 3 次 |
| 常规容量对照 | 容量充足负载，上述三种配置 | 各 2 次 |
| 基础设施空载成本 | 容量充足负载，原生、只启用控制器、启用控制器与存储连接组件，均不发送缓存控制动作 | 各 2 次 |
| 恢复预测诊断 | 分别使用压力与容量充足负载，比较记录暂停与固定申报值；容量实验还比较加入当前占用门槛的前后结果 | 每个诊断条件 2 次；默认预测复用主对照 |
| 组件与直接控制 | 压力负载，单项和成对策略，以及应用直接安排搬运 | 每个配置 1 次 |
| 真实工具循环 | 相同初始问题与生成预算，比较三种调度配置 | 各 2 次 |
| CPU/GPU 性能采样 | 完整压力负载，Yappi 使用 CPU 时钟记录请求服务、调度引擎和两个推理进程；GPU 跳过 128 次迭代后采集 32 次 | 1 次，排除普通吞吐比较 |

各次运行重置缓存并核对工作量与计算资源使用情况。出现其他计算任务与计时重叠，或资源观测不满足预定完整性要求的测量，不纳入性能比较。搬运量按物理传输统计，同一次加载被多个逻辑请求共享时不重复计费。

多次运行按耗时中位数比较，时延分位数先逐次统计再取中位数。吞吐指每秒完成的轨迹数；固定工作量下，吞吐提升为“基线耗时 ÷ 对照耗时 − 1”，耗时下降为“1 − 对照耗时 ÷ 基线耗时”。首个输出等待从请求发出起计，轨迹延迟从获得客户端并发槽起计；整批耗时仍包含所有轨迹在并发槽外的等待。

主性能、常规容量和压力预测对照使用尚未加入当前引用占用门槛的规则；容量预测实验直接比较有无该门槛，后续组件、真实工具循环与性能采样采用增加门槛后的规则。不同测量批次和不同规则的结果分别使用，不能将前一版本的主对照当作最终规则重新测得的增益。

## 4. 实验结果与解释

### 4.1 资源安排贡献了多少性能收益

主压力对照的三种配置完成相同工作量，其中应用协同调度使用尚未加入当前引用占用门槛的规则。表中的延迟指标分别为首个输出等待的 99 分位和轨迹完成时间的 95 分位。

| 配置 | 批量完成时间 | 相对原生吞吐提升 | 相对原生耗时下降 | 首个输出等待 P99 | 轨迹延迟 P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 原生引擎 | 1997.26 秒 | — | — | 125.02 秒 | 758.91 秒 |
| 容量与顺序调度 | 1386.21 秒 | 44.1% | 30.6% | 71.59 秒 | 534.92 秒 |
| 应用协同调度 | 1188.53 秒 | 68.0% | 40.5% | 70.51 秒 | 469.94 秒 |

容量与顺序调度没有搬运缓存，仍取得 44.1% 的吞吐提升，说明共享内容如何计入需求、如何预留生成增长，以及哪些请求先执行，会显著影响这组压力负载的完成效率。应用协同调度相对它再提高 16.6% 吞吐、降低 14.3% 耗时；这一增量包含应用状态、保留与搬运的共同作用，不能单独归因于恢复预测。

| 机制相关指标 | 原生引擎 | 容量与顺序调度 | 应用协同调度 |
| --- | ---: | ---: | ---: |
| 复用的输入 token | 816,144 | 3,317,888 | 4,171,664 |
| 复用输入量占比 | 9.3% | 37.8% | 47.5% |
| 请求平均排队时间 | 73.80 秒 | 38.87 秒 | 32.72 秒 |
| 请求平均输入处理时间 | 4.55 秒 | 3.51 秒 | 2.80 秒 |
| 请求平均后续生成时间 | 54.04 秒 | 48.10 秒 | 41.31 秒 |

应用协同调度将未复用的输入量从约 796.6 万 token 降到 461.0 万 token，同时缩短排队。这些观测支持减少重复输入计算、改善资源安排的解释；请求阶段时间受并发与调度共同影响，不能当作 GPU 算子提速，也不能用来精确分摊整批收益。

原生、容量与顺序调度、应用协同调度的完成时间范围分别为 1983.42–2003.82、1385.85–1388.76、1182.21–1261.62 秒。两种优化配置的 32 个前缀组，轨迹延迟 P95 均低于原生引擎；每组每次只有 8 条轨迹，结果尚不足以覆盖更复杂的会话价值与等待分布。68.0% 属于加入当前占用门槛前的测量，未对最终规则重新测得同条件的主性能增益。

### 4.2 恢复时间预测怎样改变搬运结果

在常规容量充足对照中，原生引擎、容量与顺序调度、应用协同调度的中位完成时间为 170.87、168.97、169.61 秒，复用输入量均为 8,084,608 token，应用协同调度没有发生存出或加载。这个结果说明，原有成本过滤已能避免默认配置下的大量无效搬运；小于约 1% 的耗时差异不作为稳定收益。

恢复预测诊断进一步检查这些规则是否依赖预测输入。实验只改变提供给策略的预计暂停值，模型工作量和记录暂停值保持相同。默认使用已经结束的同类暂停来更新估计；“已知记录暂停”直接读取两次模型调用之间的记录间隔，包括其中的客户端开销，代表仅知道这段暂停的参照条件。它不知道未来 GPU 准入时间，也不是最优调度上界。“统一申报 1 毫秒”和“统一申报 30 秒”则忽略真实间隔，每次提供相同预计恢复值，实际工具或回放暂停没有被改成这两个常数。

| 提供给策略的恢复时间信息 | 压力负载完成时间 | 复用的输入 token | 首个输出等待 P99 |
| --- | ---: | ---: | ---: |
| 历史暂停估计 | 1188.53 秒 | 4,171,664 | 70.51 秒 |
| 已知记录暂停 | 1230.42 秒 | 3,997,616 | 70.63 秒 |
| 统一申报 1 毫秒 | 1181.00 秒 | 4,198,320 | 70.03 秒 |
| 统一申报 30 秒 | 1077.04 秒 | 4,642,456 | 71.19 秒 |

已知记录暂停没有取得最低耗时，1 毫秒条件与默认结果接近，30 秒条件在压力下最快且复用更多。根据决策规则，较长申报值放宽了可利用传输窗口，能够使更多缓存进入保存与准备流程；这与命中增加、完成时间缩短一致。首个输出等待尾延迟却没有同步降低，也表明整批吞吐和单次请求等待不能互相替代。

要判断是否应采用更长预测，还必须检查容量充足时的代价。另一批容量预测诊断得到以下结果，表内各条件使用相同的容量充足工作量，时间不与前面的常规容量对照混算增益。

| 预测与占用条件 | 各次完成时间 | 耗时中位数 | 复用的输入 token | 存出与加载 |
| --- | --- | ---: | --- | --- |
| 已知记录暂停 | 182.33 / 183.52 秒 | 182.93 秒 | 均为 8,084,608 | 均无传输 |
| 统一申报 1 毫秒 | 181.94 / 183.43 秒 | 182.69 秒 | 均为 8,084,608 | 均无传输 |
| 统一申报 30 秒，未增加占用门槛 | 189.94 / 189.33 秒 | 189.64 秒 | 8,057,168 / 8,065,008 | 存出 3.49 / 1.90 GB，均未加载 |
| 统一申报 30 秒，增加占用门槛 | 180.59 / 183.15 秒 | 181.87 秒 | 均为 8,084,608 | 均无传输 |

没有占用门槛时，长暂停申报使中位耗时比已知记录暂停高 3.67%，并减少了缓存复用。两次运行均无抢占，缓存使用率峰值只有 68.5%/70.9%，却仍把可复用内容迁出了 GPU，之后没有读回。这是执行成功但决策退化的直接例子。

原因是长暂停通过了成本窗口判断，汇总的未来增长需求又超过压力阈值，使尚未发生的容量需求触发了迁出。加入当前引用占用条件后，这类低压力操作被过滤，缓存命中恢复完整，存出和加载归零。中位耗时减少 4.10%，但样本少且运行时钟未锁定，不能将全部差值归因于代码；消除无效存出与命中损失，是更直接的行为证据。

压力与容量结果共同限定了预测的作用：恢复时间是决定搬运价值的一项输入，当前资源压力、排队和实际消费时机同样重要。30 秒条件的压力收益不构成通用默认值，现有实验也没有建立预测精度与吞吐之间的单调关系。

### 4.3 单项策略与应用直接控制的效果

组件对照用于检查完整组合中的哪些机制可以独立产生作用。这里的“缓存保留”和“按需搬运”均为第二节描述的机制，使用增加当前占用门槛后的规则。

| 启用机制 | 完成时间 | 复用的输入 token | 抢占 | 轨迹延迟 P95 |
| --- | ---: | ---: | ---: | ---: |
| 缓存保留 | 2213.11 秒 | 589,568 | 16 | 848.65 秒 |
| 按需搬运 | 1918.07 秒 | 1,712,256 | 12 | 756.25 秒 |
| 缓存保留 + 按需搬运 | 2008.92 秒 | 1,415,904 | 7 | 777.87 秒 |
| 缓存保留 + 容量与顺序调度 | 1575.65 秒 | 3,048,976 | 2 | 610.02 秒 |
| 按需搬运 + 容量与顺序调度 | 1369.64 秒 | 3,870,608 | 2 | 528.51 秒 |

在缓存保留上加入容量与顺序调度，耗时下降 28.80%；在按需搬运上加入它，下降 28.59%，两条对照中所有前缀组的轨迹延迟 P95 均下降。这与主对照一致，支持容量核算和请求安排在该负载中的作用，但尚未将二者各自的贡献拆开。

缓存保留与按需搬运组合后，比单独搬运慢 4.74%，且 22 个前缀组的尾延迟更高。本负载的重要性设置较统一，结果不支持增加保留策略就一定获益，也不能据此否定它在关键分支与低价值任务混合场景中的价值。“按需搬运 + 容量与顺序调度”虽然在本批组合中最快，但与另一种成对组合相比同时更换了机制，差额不能全算作搬运贡献。这批单轮实验没有单独的原生或容量与顺序调度参考组，不与主对照跨批次计算增益。

应用直接发出搬运指令的对照，则用于区分“完成指定传输”和“获得有效复用”。它保留引擎可行性检查，但不通过策略筛选收益。

| 应用指定的操作 | 完成时间 | 复用的输入 token | 存出 / 加载 |
| --- | ---: | ---: | --- |
| 直接搬运 | 2192.69 秒 | 642,096 | 554.65 / 217.90 GB |
| 直接搬运并保留 | 2269.10 秒 | 516,656 | 552.34 / 230.75 GB |

两种配置均无后端传输失败，却出现大量加载和较少复用。本模型同时包含注意力缓存与 Mamba 递推状态，完整前缀复用要求各部分的覆盖与检查点兼容。两种配置分别报告 646 和 657 次复制已向 GPU 注册内容，其中操作自身覆盖完整混合前缀的分别为 56 和 48 次，多数只覆盖注意力部分。传输回执只证明指定范围完成，不能自动说明整个模型前缀已可使用。

已有 GPU 内容可能补齐这些缺口，多个请求也可能共享同一次加载，因而不能把不完整的操作范围全部判为浪费。当前观测缺少每次查找时的完整驻留快照，无法给出精确无效搬运率；可以确认的是，后续优化需要同时检查准备完整性和实际使用时机，不能只追求传输次数或字节数。

### 4.4 连续工具交互中的速度与答案质量

真实工具循环采用相同初始问题、提示和生成预算，应用协同调度使用增加当前占用门槛后的规则，模型选择工具、读取结果并继续生成。答案评分要求最终请求正常结束、给出约定的最终答案标记且数值正确；未完成回答和截断仍保留在分母中，文本末尾的偶然数字不算作完整答案。

| 配置 | 各次完成时间 | 模型调用数 | 输出 token | 完整答案正确数 | 抢占 |
| --- | --- | --- | --- | --- | --- |
| 原生引擎 | 2114.16 / 2164.19 秒 | 912 / 921 | 59,412 / 59,658 | 249/256、248/256 | 13 / 10 |
| 容量与顺序调度 | 1455.49 / 1486.53 秒 | 926 / 917 | 59,761 / 59,520 | 249/256、248/256 | 0 / 0 |
| 应用协同调度 | 985.81 / 978.93 秒 | 921 / 919 | 59,088 / 58,969 | 246/256、249/256 | 0 / 1 |

三种配置的完成时间中位数为 2139.17、1471.01、982.37 秒，缓存复用量增加、请求平均排队缩短。实际生成尾部也改变了后续输入和调用数量，设备运行时钟并不完全一致，因此这些时间是在线观测，不能换算成固定工作量主对照的策略收益。

配对检查确认，每次运行中各配置的全部初始提示、题目和采样位置相同。应用协同首轮相对两个参考组均多错 3 条，涉及百分比理解、答案单位和工具回合用尽；另一轮相对各参考组各多答对 1 条。首次生成分叉都发生在相同输入 token 下，但没有对模型输出概率或中间状态逐项比较，尚不能确定具体因果，也没有做到逐轨迹答案一致。

这些观测要求把在线缩时与质量变化同时保留。64 个问题的多次采样相关，不能将所有轨迹当作独立问题来证明准确率不下降；在更充分的质量对照前，不能把在线时间差表述为已经确认无质量代价的增益。

### 4.5 实际复用与故障恢复是否正确

独立质量实验固定 128 个问题和相同的 8 条示例提示，分别比较强制重算与真实加载缓存后的生成。功能服务采用双卡执行、最大上下文 4096、并发 8，关闭图执行；共存两套引擎时每套显存利用率为 45%。这些结果不用于性能比值。

| 搬运路径 | 强制重算正确 | 加载后正确 | 配对答案差异 | 长度截断 | 每题复用输入：重算 / 加载 |
| --- | ---: | ---: | ---: | --- | ---: |
| 主机内存卸载 | 124/128 | 124/128 | 0 | 均为 0 | 0 / 784 token |
| Mooncake 共享存储 | 124/128 | 124/128 | 0 | 均为 0 | 0 / 784 token |

实际命中证明加载路径被使用，配对答案一致则支持这批输入与配置下的搬运正确性。它不替代上一节连续生成的质量检验，也不代表其他模型或上下文条件的保证。

跨引擎加载同样观察到 784 token 的实际命中，短贪心输出与重算一致。共享分支结束、并发加载与取消测试没有破坏其他会话的需求；同时在途的加载预算限制为一个块时，系统能逐步报告部分效果并重试，未完整准备的请求也能回退重算。存储停机与引擎重启时，加载失败被明确报告，陈旧控制请求被拒绝，之后可以重新建立缓存关系。

通过受控入口实际修改并恢复模型参数，还验证了新权重不复用旧缓存、恢复相同旧权重后可以复用兼容内容。这个验证包含真实参数变化，但没有执行完整训练流程，也不覆盖绕过受控入口的任意参数修改。

## 5. 代价与适用范围

### 5.1 控制与搬运成本仍然存在

容量充足负载还比较了不发送缓存动作时的基础设施成本：原生引擎、只启用控制功能、同时启用控制与存储连接组件的完成时间中位数为 168.54、168.49、168.39 秒，均无搬运和抢占。小于 0.1% 的差异没有显示明显空载退化，但不能证明主动控制或其他负载没有开销。

主性能对照中的客户端 CPU 中位数分别为 71.81、54.73、127.31 秒。应用协同调度每次仍有约 1,584 次动作提交、15,070 次结果查询和 4,420 次结果确认；确认用于允许引擎回收已收集的结果记录。后台异步处理减少了推理前等待，却没有消除消息处理、状态维护和传输成本。客户端 CPU 还包括生成流处理与指标采样，不能把全部差额解释为纯控制开销。

完整压力负载的性能采样进一步显示，缓存控制与策略模块函数自身使用 31.73 CPU 秒，占调度引擎所采函数自身 CPU 的 2.54%。CPU 时间可以由多个线程累计，不等同于墙钟耗时；函数自身时间不含子调用，嵌套累计时间也不能相加。这个占比没有覆盖它调用的其他模块、内建函数和原生代码。共享内存轮询函数自身消耗 597.01 CPU 秒，指标格式化为 44.25 CPU 秒，两个推理进程的原生存储加载入口分别为 90.80/86.10 CPU 秒，说明成本分布在多条执行路径中。

采样轮完成相同压力工作量，用时 1096.55 秒，但不进入普通吞吐比较。没有配对的原生性能采样，无法相减得到新增策略的净 CPU 成本；部分原生线程也未进入函数级记录。减少结果查询、批量确认或优化等待，需要以这样的成本分解为依据，同时保留失败反馈、取消和资源释放顺序。

### 5.2 设备等待与测量限制

部分在线运行持续出现软件温控限频：一侧设备的繁忙样本时钟中位数为 765 MHz，另一侧为 1335 MHz，最高温度分别为 86°C 和 69°C。性能采样中的时钟中位数为 750/1335 MHz。测试期间功率上限保持 300 W，未调整时钟或散热设置，早期仅有时钟与功率记录的轮次也没有补写温度或限频状态。

GPU 采样中，计算较慢一侧的主要矩阵乘法累计用时为 11.85 秒，另一侧为 7.67 秒；另一侧的张量并行同步累计更长，为 6.37 秒，前一侧为 0.91 秒。这与计算较慢、对端等待更长的情形一致，尚无锁定时钟的对照来分离散热、通信和调度各自的影响。

GPU 采样只覆盖部分迭代，事件时长还可能重叠，不能外推为整轮 GPU 占用或全部搬运成本。单轮组件结果和较少的预测重复，也不足以建立跨负载的稳定排序。本文结论限于上述模型、人工构造的共享前缀分布、GPU 预算和已验证的 CPU/Mooncake 路径，不能直接推广到其他模型、缓存布局或多机服务。

## 6. 后续问题

恢复预测需要围绕缓存实际消费时间继续验证。工具剩余时间决定应用何时能提交后续请求，排队决定请求何时能够执行，传输决定缓存何时准备好；需要共同估计这几个时刻，再判断何时加载、预测变化后何时取消准备。“已知记录暂停”条件仍未取得最短完成时间，说明仅提高工具耗时估计精度不能代替这项协调。

搬运规则还缺少逐前缀的重算成本、再次使用概率和占用显存的机会成本模型。后续应在留存、迁出后加载、直接重算之间比较预期净收益，并对应实际使用请求，检查完整准备后有多少内容被消费。组件与直接控制实验已经表明，搬运更多内容、叠加更多策略均不保证更快。

质量与负载覆盖也需要扩大。当前工具主要是本地查询和计算，暂停较短，共享前缀由参考例题构造；长工具等待、频繁取消、价值不同的分支及跨引擎恢复可能改变最优决策。进一步的自然任务对照需要同时报告吞吐、长尾等待、答案质量、主机资源和传输量，并覆盖更完整的路由与训练流程，才能判断已测收益可以延伸到哪些应用。
