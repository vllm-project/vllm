# Programmable KV Cache 后续工作

更新日期：2026-10-01。

本文记录首版之后要做的工作、前置依赖和验收标准。
首版实现任务以 [OpenSpec tasks](../../openspec/changes/programmable-kv-cache/tasks.md) 为准；本文不表示首版代码已经完成，也不把尚未完成的首版验收挪成“未来工作”。

## 已确认的首版边界

首版主线：

```text
轻量编排端
  → 已合入的 KvHintsEnvelope / KvHintAction
  → vLLM 传输与分发
  → vLLM 解释原生动作 / 可选策略处理信号
  → 目标解析、资源审批、缓冲区与引用管理
  → vLLM 连接器调用 Mooncake Store
  → 操作实际完成与驻留状态更新
  → 操作结果、增量关联事件、状态查询返回编排端
```

同时保留现有 KVCR 路径：提示消息透传给 KVCR，由 KVCR 解释其动作参数，复用现有 `submit_hint`、query/deliver 和请求清理机制。

- **每个提示消息只走一条解释路径**。
  首版不在同一提示消息内混合 vLLM 原生和 KVCR 动作，不广播给两个解释方，也不失败后悄悄换解释方。
- 沿用已合入的协议字段；不新增自定义 hint 注册器或处理函数插件系统。
- vLLM 定义和执行原生 Retain/Demote 等语义；Mooncake 校验自身存储状态和容量，执行其已有 API 支持的工作。
  首版不修改 Mooncake 项目。
- 两条路径需要 GPU 操作时都遵守 vLLM 的资源与生命周期控制；这不等于已经实现图中虚线标注的“未来 KVCR GPU 操作指令”。
- 显式会话与续接分支的状态命令与策略信号分开；默认没有本地策略时，仍可执行支持的显式命令。
  无人消费的 vLLM 原生信号无副作用。
- 关联信息使用增量事件与状态查询。
  现有完整报告模式只是当前请求命中前缀的补报，不是整个引擎的状态快照。

以下验收仍属于**首版要求**：

| 首版要求 | 验收说明 |
| --- | --- |
| 轻量编排端 → vLLM → Mooncake 流程 | 必须经过实际入口、语义解析与真实 Store 调用；直接调用适配器或只有模拟对象不算完整验收 |
| 无推理请求的 vLLM 原生控制 | 工具等待期间可推进操作；不构造伪推理请求 |
| Mooncake 跨引擎示例 | A 保存、B 提前加载，完成后观察 B 的实际缓存复用 |
| SessionPrefixIndex 与生命周期 | 共享前缀、分支、范围、独立 Retain 声明、显式任务树结束 |
| 统一 GPU 资源管理 | 引用、预留、取消、部分失败、reset/restart、陈旧完成通知 |
| 可配置策略与调度器协作 | 配额准入与请求评分示例；保留现有抢占算法 |
| 两条解释路径兼容 | vLLM 原生不重复透传；KVCR 动作参数保持语义不变；原请求清理不退化 |
| 实验与正确性 | 同权重版本 rollout；权重更新后旧 KV 失效；公平对比和负收益场景 |
| 验证环境分层 | 本机 Qwen3.8-27B TP=2 调试；其他机器的 GPT-OSS-120B、DeepSeek-V4-Flash 全面评测仍需单独记录实际结果 |

## 已确认放到后续的工作

### F1. Dynamo → vLLM-native → Mooncake 实际集成

**状态：已确认后续接入。**
首版用轻量编排端。

依赖：首版 vLLM 原生动作及其参数、能力查询、操作结果和状态事件契约可运行。

- [ ] 在 `../` 下准备 Dynamo 对接仓库并固定兼容提交版本；检查当时已有的 hint 生产与引擎桥接接口，复用已有传输。
- [ ] 将轻量编排端中的 hint 发送流程接到真实 Dynamo 工作进程选择、会话与续接分支及生命周期信息来源。
- [ ] 把原提示消息字段和关联 ID 传到指定 vLLM 引擎；明确独立控制如何到达目标实例，以及原生或 KVCR 路径如何选择。
- [ ] 让 Dynamo 消费能力、实际操作结果、关联与驻留状态增量；处理 DEFERRED、缺失目标、失败、重试与引擎代次变化。
- [ ] 验证工具等待 → Demote → 选择恢复时使用的引擎 → Prefetch → 可复用状态 → 恢复推理。
- [ ] 对比轻量编排端与 Dynamo 的行为，分别报告缓存收益和路由、控制循环开销，不能将所有差异归因于 KV 策略。

**完成标准：** 可复现地运行真实 Dynamo → vLLM → Mooncake；结果能追溯到原始 hint；压力、共享前缀、事件延迟和工作进程重启下仍有正确回退。
记录必要的 Dynamo 改动与双方版本，不将轻量编排端示例称为 Dynamo 集成。

### F2. 同一提示消息内混合原生与后端动作

**状态：明确不属于首版；作为后续分发能力设计。**

依赖：首版整条提示消息的单路径分发，以及两个解释方的能力与错误处理约定稳定。

- [ ] 与相关实现方确定每个动作的唯一解释方选择规则；不能只凭同名 `action_type` 推断两个解释方具有相同语义。
- [ ] 设计分组转发、动作原始顺序、跨组依赖和消息与动作 ID 关联。
- [ ] 定义混合提示消息的部分失败、取消、重试及结果汇总；不默认承诺跨解释方原子事务。
- [ ] 处理未知或有歧义的解释归属；防止 vLLM 原生消费后被原 KVCR 回调再执行一遍。
- [ ] 验证拆分后后端动作参数的值与版本不变，并测量额外控制开销。

**完成标准：** 一个混合提示消息中的每个动作只被选定解释方解释，结果可独立关联；失败、重试与取消不会重复执行或重复计费。
协议字段是否需要演进必须另行协调，不能把新字段暗中塞进首版。

## 图中已提出、但尚未承诺本次实现的后续方向

### F3. KVCR 指令接入共享 GPU 操作

**状态：图中的虚线路径；需与 KVCR 团队明确具体动作后立项。**

依赖：明确的后端动作及结果契约与可复用的 vLLM GPU 资源操作。

- [ ] 确定首批 KVCR G1 动作及由谁解释；保持 KVCR 对其动作参数的解释权。
- [ ] 从 KVCR 集成层调用引擎的 GPU 操作，避免再经过 vLLM 原生动作参数解析。
- [ ] 定义目标块与兼容性、容量预留、源与目的缓冲区传输引用、多并行进程完成、取消和失败回报。
- [ ] 区分现有框架内部的源缓冲区保护回调与新增 GPU 操作；不要把内部传输引用当作已删除的公共 Pin 语义。

**完成标准：** 至少一个明确的 KVCR GPU 动作能经集成层正确执行；并发 vLLM 原生工作与 KVCR 工作不会重复占用容量、提前释放缓冲区或伪报可复用状态。
现有 `submit_hint()` 透传本身不能满足这一验收。

### F4. KVCR 独立于推理请求的控制生命周期

**状态：候选扩展；当前绑定推理请求的路径不能自动宣称支持。**

依赖：KVCR 能力和接口约定；不能仅给现有接口编造请求 ID。

- [ ] 确认 KVCR 是否需要、以及如何支持无推理请求的 hint 的提交与进度推进。
- [ ] 定义独立操作标识、存活期限、取消、清理及结果关联。
- [ ] 明确无消费者/无后续请求时的资源回收和后端断连行为。

**完成标准：** 无推理请求时可推进支持的控制操作，结束后无泄漏；转发成功、执行完成与缓存可复用有明确区别。
若后端不支持，应继续准确报告 unsupported（不支持）。

## 需要另行决定的扩展，不属于已承诺路线

| 编号 | 候选方向 | 开始前需确定 | 完成标准 |
| --- | --- | --- | --- |
| F5 | gRPC 独立控制入口 | 对接方是否需要；与现有 Python/HTTP 控制的兼容面 | 复用相同提示消息与状态记录，跨入口结果一致，明确取消/流控/指定目标引擎 |
| F6 | SimpleCPUOffloadConnector 控制适配 | 是否确有使用需求及与通用 CPU 路径的维护成本 | 实际支持能力可发现；生命周期、引用和失败测试达到同等标准 |
| F7 | 更丰富的冷层 Retain/选择性删除能力 | 后端是否提供所需优先级、TTL 与删除语义；共享对象的声明归属 | 可验证地满足声明的保证；不以弱保留冒充强保证，不以重置整个 Store 实现局部 Evict |
| F8 | 运行中更换策略或连接器 | 用户是否需要；状态交接、排空、回滚和工作进程一致性方案 | 在有在途操作时切换也不泄漏、不误释放、不破坏有效声明 |

F7 如需要修改 Mooncake 本身，属于另一个需明确授权/协调的工作项，不在首版范围。
F8 不是当前“配置式插件”的隐含要求；首版更换插件需重启。

## 使用与更新规则

1. 每项后续工作落地时记录实现仓库/commit/PR、测试命令、实际结果及剩余限制。
2. 首版仍未确定的动作参数、目标范围、重试、范围与缓存组语义继续在 OpenSpec design/tasks 中解决，不因未定而自动归入未来。
3. 首版代码或实验失败继续保持未完成状态；不能通过改写本文宣称首版完成。
4. 新增工作项须注明是“已确认后续”“需要与上游协调”还是“候选待决定”。

## 首版交付对账（2026-10-06 修正）

已实现的控制、逻辑索引、声明与 CPU/Mooncake 搬运有单元测试以及部分本地 Qwen 实际运行证据。
具体证据与限制见 OpenSpec `coverage.md` 和 `validation.md`。
策略/调度有针对性回归；其完整压力、收益和公平性矩阵未完成。

10 月 2 日的完成度统计高估了交付范围：空目标 rollout、未对接真实格式的 verl 脚本，以及仅检查文件存在的 coverage 脚本已移除。
协议错误探针已补齐断言，但伪造过期引擎代次不等于实际重启恢复。
以下仍是首版未完成项：

- 物理驻留状态查询与事件、故障后的状态重建及请求恢复；
- 多轮共享前缀压力、完整分支、范围与任务树示例与应用 rollout 控制器；
- verl Agent Loop 集成及实际权重版本下旧 KV 的失效；
- 策略对比、端到端开销、公平性及外部 GPT-OSS/DeepSeek 评测；
- 成功的 GitHub 查重和满足完整证据要求的 PR 描述。

这些内容保留在 OpenSpec 首版任务中。
F1–F8 的后续边界不变。

## rfc-hint 对齐验证（2026-10-06）

已新增 RFC #59708 的公共基本操作、成功完成/入口分阶段调度、物理副本生命周期内的优先级和逐目标结果。
真实 Mooncake 的请求附带 MOVE/COPY、独立控制、双引擎 COPY 及原生工具等待策略生成基本操作后的完成/复用均已有执行记录；7.11 据此完成。
该验证不代表完整 rollout/RL、驻留状态或公平性矩阵完成。
详见 OpenSpec `validation.md` 的证据索引及 `vllm/v1/kv_hints/README.md`。

## 本地真实 rollout 补齐（2026-10-11）

本轮重新落实原定首版验收：接入真实 verl ToolAgentLoop、实际模型生成与工具执行，记录响应掩码、token 对数概率和奖励分数；增加独立结果 ACK、按操作实例取消、 GPU 当前驻留/优先级查询，以及真实分支、范围与任务树示例。
实际权重更新使用已有 IPC 生命周期，隔离旧 KV 缓存命名空间，不清空其他引擎的共享 Store。

性能目标由用户明确为同等工作和 GPU KV 容量下 rollout 吞吐提升至少 25%。
启动/预热、eager 调试、固定输入回放和实际采样分开记录。
所有收益、退化与未达标配置必须保留。
外部机器目前不可用，GPT-OSS/DeepSeek 验收仍保持未执行；本地测试不能代替该矩阵。
最终完成状态以 OpenSpec 任务和实际结果为准。
