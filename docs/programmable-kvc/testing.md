# Programmable KV Cache：分支实现与验证结果

## 当前实现

本分支实现 RFC 的引擎侧控制与策略执行：应用提供任务、分支、暂停/恢复及缓存意图，策略依据引擎状态提出建议，vLLM 统一检查资源并通过现有 connector 执行。
目标是支持跨请求生命周期的 KV 管理，并使 retention、movement、quota 等策略共享资源状态与执行机制，避免重复分配、冲突搬运和不一致的完成语义。

具体交付包括：

- **控制与状态**：复用 `KvHintsEnvelope`，支持 `SET_PRIORITY`、`COPY_TO`、 `MOVE_TO` 及 session/continuation/range 寻址；支持请求附带和独立控制、关联查询、 GPU 驻留快照、结果 ACK 与取消。
  保留 KVCR 的 opaque 转发路径。
- **资源与执行**：沿用 KVCacheManager/BlockPool 和同一淘汰机制；共享传输只占用一份资源，COPY 完成后才发布可复用内容，MOVE 完成存储后才回收可释放的源副本。
  CPU/Mooncake adapter 负责数据搬运，策略不直接修改分配器。
- **策略与 RL 支持**：提供保留优先级、工具等待搬运和 quota/复用评分策略；增加需求观察、在途预取预算，以及权重更新时的排空、KV 失效和 namespace 切换。

策略可通过启动配置启用、关闭或替换；运行中热切换尚未实现。
当前未接入真实 Dynamo/llm-d 路由器，也未执行完整 RL trainer/optimizer 流程。

本轮增加完整前缀成员引用保护、整组准备预算、实际命中后的准入复核，
并将暂停/搬运成本、当前占用与持续排队用于策略决策。
低占用信号先读物理计数，按需读取请求观察；结束清理包含结果收集与设备搬运排空。

## October 11 阶段验证

功能验证对应 RFC 的资源、生命周期与完成契约：

| 验证目标 | 已执行测试与证据 |
| --- | --- |
| 统一资源审批与异步执行 | 单元/回归覆盖重复 COPY 合并、预算延期、所有 rank 完成后发布、取消与 buffer 引用保护；已有真实 CPU/Mooncake buffer 和请求附带 MOVE/COPY 验证 |
| 请求结束后仍可控制及跨 engine 复用 | primitive 阶段验证独立控制与 A→Store→B 复制，目的 engine 实际命中 784 token，短贪心输出一致；本轮未重新执行双 engine 用例 |
| 分支共享和独立生命周期 | 本轮真实 root/子分支/外部共享任务验证：任务树清理不删除外部声明，TTL 后优先级 90→20→0；COPY/resume 竞争命中 784 token，取消后可正确重算 |
| RL 权重更新隔离 | 本轮实际 IPC 参数更新/回滚：新版本首次推理零命中，旧 epoch 被拒绝；恢复权重与版本后复用旧 Store 内容，命中 1,568 token |

性能验证使用 **Qwen3.8-27B BF16、两张 A100 80GB、TP=2**。
原生基线使用同一源码构建的 vLLM，启用前缀缓存，关闭本分支的控制器与缓存搬运 connector。
各组使用相同的编译、CUDA graphs 和并行配置，最大上下文为 16,384 token，batch token budget 为 4,096；各对照的 GPU KV 预算相同，搬运组另使用 CPU Store。

负载接入真实 **verl ToolAgentLoop**：8 个 GSM8K 问题各采样 4 次，形成 32 条 rollout，并发 16；8 个前缀家族，每请求约 8.8k–10.9k 输入 token。
工具实际执行题目查询和算术计算，轮间暂停约 5–20 ms。

共完成 **19 次固定工作量回放和 3 次真实在线运行**。
主要配置各做三轮回放，每轮固定 113 次模型调用、8,121 个输出 token，并核对输入与输出长度摘要；回放重新执行模型生成，但不重跑工具、不计算 reward。
在线运行实际执行工具并检查 reward。
计时包含控制准备与任务清理，排除服务启动和显式预热；单项策略对照各一次。
每轮重置缓存并隔离 cache salt。三轮结果报告中位数，并保留波动；不同配置按组运行，未随机交错。

## October 11 阶段结果分析

固定工作量的中位结果如下；吞吐变化均相对同一 KV 预算的原生基线。

| KV 预算/卡 | 策略 | 原生耗时 | 策略耗时 | 吞吐变化 |
| --- | --- | ---: | ---: | ---: |
| 2 GiB | quota/前缀复用调度 | 449.06 s | 219.63 s | **+104.5%** |
| 2 GiB | retention + movement + quota | 449.06 s | 247.60 s | **+81.4%** |
| 8 GiB | retention + movement + quota | 54.09 s | 56.13 s | **−3.6%** |

**受限 KV 下，主要收益来自调度。**
quota 将抢占中位数从 118 降至 17，搬运量为零。
该策略结合运行中请求的后续 KV 需求与已有前缀命中调整准入和请求次序，允许借用空闲容量，并通过等待时间约束避免持续延期。
单独保留、单独搬运、应用端搬运与保留组合的单轮收益分别为 10.3%、14.5%、8.0%。
完整策略每轮从 Store 加载、向 Store 写入的中位数据量分别为 11.97 GB 和 33.50 GB；没有后端传输失败，但有 42–89 次对象缺失，rollout 仍全部完成。
这些结果尚未证明冷层搬运或策略组合带来了超过 quota 的净收益。
完整策略也有尾延迟波动：压力组一轮 TTFT P99 为 99.92 s，高于原生中位数 95.98 s。

真实在线运行中，原生、完整策略、quota 的耗时分别为 **452.37、288.73、214.34 s**，三组均为 **32/32 正确 reward**；quota 吞吐高约 111.0%，抢占从 119 降至 8。
quota 的 TTFT P95/P99 从原生的 80.42/81.14 s 降至 28.00/35.29 s，且没有调用达到输出长度上限。
这是每配置一次的在线结果，生成轨迹不同，且只覆盖 8 个独立问题。

**正常资源预算下的 25% 目标仍待验证。**
2 GiB 是人为压小缓存的诊断点。
8 GiB 下，这批负载没有形成明显缓存压力：两组均零抢占、命中 999,600 token，KV 使用率指标峰值约 50%。
策略没有增加复用收益，但保留了关联、信号和查询开销；后续轮次发送推理前的准备等待中位数约 80 ms，原生接近零。
这部分开销需与负载压力分别评估。

当前证据支持 RFC 的控制与资源语义可执行，并验证了调度策略在受限 KV 下的收益。
合理显存预算下的高负载收益、预测提前量及真实故障恢复还缺实验。
后续应固定实际部署的 KV 预算，通过更大的 rollout 批量、并发、分支工作集和工具等待形成压力，同时保留低压力开销对照。

最终整套回归、新一轮 128 题评测、预测误差、实际 Store 停机/engine 重启及外部大模型测试尚未完成。
已有结果不能代替全部 RFC 验收。
