# RFC 本地 RL rollout 实验报告（2026-10-12）

分支实现、验证工作与结论摘要见[分支汇报](testing.md)。
本文保留实验配置、逐项结果与诊断记录。

本报告对应 `rfc-hint` 分支、基线提交 `8b1a1b0f2d` 之上的工作区改动。
用户目标是在相同工作量和 GPU KV 容量下，尽可能提高有效 rollout 吞吐，预期至少 25%；外部机器不可用，本轮仅使用本地 GPU 0、3。
按用户的停止要求，完成正在执行的配额复测和真实在线 rollout 后停止，不继续追加实验。

## 结论

**2 GiB/卡的本地受限负载超过了 25% 吞吐目标；正常部署预算下的目标仍未验证。**
完整策略在 2 GiB/卡的固定工作量压力测试中，中位吞吐提高 81.4%。
单项对照显示，短工具等待下的主要收益来自调度、共享前缀复用和减少抢占；单独增加搬运未达到 25% 目标。
每卡 8 GiB、工作集可以容纳时，完整策略反而使吞吐下降 3.6%。

因此，这份代码已经提供可运行的控制、调度与真实 rollout 接入，以及有条件的性能收益；**完整 RFC 验收和完整 RL 训练性能验证仍未完成**。

| --- | --- | ---: | ---: | ---: |
| 2 GiB | 原生 APC | 449.06 s | 0.07126 | 基线 |
| 2 GiB | 仅配额调度 | **219.63 s** | **0.14570** | **+104.5%** |
| 2 GiB | retention + movement + quota | 247.60 s | 0.12924 | +81.4% |

配额三轮是 219.63、237.75、199.98 秒，来自两个独立启动的同配置服务。
最慢配额轮相对最快原生轮仍提高约 **88.6%**；三轮中位抢占次数 **17**，中位 TTFT P95/P99 **28.92/45.46 秒**，搬运量全为零。
这里只验证本地这批负载，不把三轮数据解释为跨模型、跨环境的置信保证。

它们都是实际 GPU 推理，其中固定回放共完成 608 条轨迹，在线共完成 96 条；不是 704 个独立问题。
全部本轮自建推理服务、Store 和采样进程已停止，后续实验队列已取消。

## 实验设置与“真实”的范围

| 项目 | 本轮设置 |
| --- | --- |
| GPU | NVIDIA A100 80GB PCIe，GPU 0、3，TP=2 |
| 模型 | 本地 Qwen3.8-27B，BF16 |
| 实现环境 | Python 3.12，torch 2.13.0+cu132，transformers 5.17.0 |
| verl | 真实 ToolAgentLoop，提交 `fbb4b3a8bf636f290c9c59fc346f756849e9c241` |
| 推理优化 | torch.compile、CUDA graphs、默认 allreduce；OMP=1 |
| 调度上限 | 并发 16，max model len 16384，batch token budget 4096 |
| GPU KV | 压力组 2 GiB/卡；容量充足组 8 GiB/卡 |
| 原生基线 | 同一源码构建，关闭 programmable 控制器和连接器，使用普通 APC |
| 冷层 | 自建、隔离的 Mooncake Store，TCP；配置 global segment 8GB/客户端 |
| 数据 | GSM8K，8 个问题 × 4 次采样，8 个前缀家族，每个家族 48 个参考例题 |

在线实验调用真实模型和真实 verl 工具循环。
模型先生成 `lookup_problem` 调用，工具返回真实题目，再调用有边界的算术执行器；保留生成 token、token 对数概率、响应掩码、工具结果和最终数字奖励分数。
模型生成、工具执行和轨迹记录均实际运行。
当前模型规模、工具种类和数据规模都有限；没有执行 PPO/GRPO 优化器、梯度更新、训练与推理共卡调度或跨机器网络压力，因此上述数字是 rollout 侧的结果。

固定工作量实验则使用真实在线轨迹，固定每轮输入 token、输出 token 数和记录的工具等待时间。
模型实际重新生成输出；下一轮仍使用记录的原始输入，**不重新执行工具，也不根据回放输出计算奖励分数**。
这用于隔离吞吐差异，不能冒充新的在线质量结果。
所有已完成固定回放还会核对 request ID、turn、输入 token 和输出长度的摘要。

本地工具实际暂停约 5–20 ms。
压力组单次请求约 8,780–10,876 个输入 token，引擎报告约 50,365 个 KV token 容量；通过明确限制 KV 空间触发真实淘汰和抢占。
这是受限资源压力实验，不是采用默认最大显存分配的吞吐测试，也没有并行运行训练器。

性能计时排除服务启动和显式预热，包含调用方的准备等待与任务清理。
压力组两个服务器的首轮各出现一次采样内核首次编译，保留在原始计时中。
三轮范围不是统计置信区间。
不同配置分组运行，没有将所有原生/策略轮次随机交错；主比较期间没有运行本任务的其他模型服务或回归测试。

## 压力测试与单项对照

完整策略的三轮耗时为 241.27、247.60、282.35 秒；原生为 449.57、449.06、 448.44 秒。
最慢策略轮对比最快原生轮，吞吐仍高约 58.8%。
完整策略耗时的最大跨度为其中位数的 16.6%，原生约为 0.25%，因此策略收益有明显的运行间波动。

完整策略中位 TTFT P95/P99 为 47.59/73.83 秒，原生为 80.85/95.98 秒。
但策略第三轮 P99 达到 99.92 秒，约比原生中位数差 4%；不能保证每轮尾延迟都改善。
完整策略中位抢占次数为 27，原生为 118；中位服务端排队时间为 14.00/38.43 秒。

以下是每项一次的诊断对照，不构成接入开销的统计上界：

| 模式 | 耗时（秒） | 吞吐相对原生中位数 | 抢占 | 加载/写入（十进制 GB） |
| --- | ---: | ---: | ---: | ---: |
| 控制器/connector 开启，不发 hint | 418.40 | +7.3% | 95 | 0 / 0 |
| 仅显式保留优先级 | 407.00 | +10.3% | 93 | 0 / 0 |
| 仅显式搬运 | 392.24 | +14.5% | 74 | 26.46 / 69.11 |
| 显式搬运与保留组合 | 415.77 | +8.0% | 86 | 24.05 / 70.34 |

以“不发 hint”组为对照，单独搬运约提高 6.7%，保留约提高 2.8%，直接组合约提高 0.6%。
这些单项都没有达到相对原生 25% 的目标。
不发 hint 的运行也改变了调度/抢占轨迹，不能把它的单次正差异解释为接口自动加速或零开销。

完整策略每轮加载 10.02–14.34 GB、写入 31.91–34.84 GB。
没有失败的后端传输，但保留了每轮 42–89 次缺失对象的传输结果以及 partial/deferred 结果，并允许推理回退。
已经存入或历史上加载成功，不代表以后仍然驻留。
所有完整策略压力轮结束时，详细结果记录为零、策略错误集合为空；ACK 的重放指纹按原 TTL 保留。

## 容量充足时的反例

8 GiB/卡时，原生三轮为 54.09、54.76、53.51 秒；完整策略为 55.96、56.13、 56.78 秒。
每轮都是相同的 32 条轨迹、113 次调用、8,121 个输出 token，缓存命中 999,600 token，零抢占。
策略没有实际搬运，低压力门槛确实避免了无用复制。

原生/策略中位耗时为 **54.09/56.13 秒，策略吞吐下降 3.6%**。
策略 TTFT P95 由 17.81 降至 14.06 秒，P99 由 19.69 变为 19.79 秒。
这组不满足 25% 提升目标。
显存允许时，容纳工作集比在 2 GiB 配额下增加复杂控制更有效；增加显存不能算作同等资源下的算法收益。

## 代码实现与已执行的功能检查

- 接入真实 verl ToolAgentLoop 和异步 HTTP 控制器；保留 token、对数概率、响应掩码、奖励分数、逐目标结果和失败回退。
  搬运可绑定成功完成生命周期，在请求释放前取得源缓冲区传输引用。
- 增加终态结果 ACK，释放详细记录但保留原 TTL 的重放保护；按操作实例取消，避免迟到取消命中新操作；增加有界的 GPU 当前驻留、引用和优先级查询。
- 权重更新要求请求/搬运排空，先清本地 KV、多模态与编码器缓存，再提交新版本和引擎代次。
  非默认版本隔离普通请求哈希，不全局删除其他引擎的 Store 内容。
- 调度加入剩余解码需求、已有前缀复用评分、空闲额度借用和有界等待；限制预取预留，按实际搬运结果反馈策略，避免把未存储的范围当成可用冷副本。
- 控制运行时使用增量缓存计数，避免每次观察遍历全部池；兼容正在运行的预测与实际恢复请求，共享底层 COPY 并保留仍然有用的加载。

实际生命周期检查已通过：root 与两个分支共享前缀，另一个独立任务继续持有它；任务树清理和 TTL 后，有效优先级从 **90 → 20 → 0**。
重复 COPY 与 resume 竞争时实际命中 **784 token**；取消后能够零命中重算，并保持短贪心输出一致。

真实 IPC 权重检查已通过：修改一个实际 layer norm 参数，旧 epoch/namespace 被拒绝，新版本第一次推理命中为零且 token 对数概率改变；恢复原参数和版本后，从保留的旧 Store 对象恢复 **1,568 token** 命中，重现原短输出。
该检查执行实际张量更新与回滚，未执行优化器更新；绕过 start/update/finish 生命周期直接修改张量不在保护范围。

当前驻留查询只覆盖 GPU 状态快照，不保证之后持续驻留。
Mooncake 原生路径仍限制 PCP=DCP=1；通用 CPU 控制要求每个传输单元包含一个缓存块，CPU Share、冷层 Retain/选择性删除、KVCR 独立原生控制和混合解释方提示消息等能力仍受原有覆盖边界限制。

## 使用建议与复现

### 停止后的只读诊断：容量充足时为什么没有净收益

以下来自既有原始记录和代码审阅，没有启动新实验，逐轮计算保存在 `results/rollout-2026-10-11/cache-fit-diagnosis.json`。

- 原生和策略都命中 999,600/1,121,644 个 prompt token，约 89.12%；KV 峰值占用约为预算的 50%，抢占为零。
  策略没有增加实际命中，也没有省下一次抢占重算。
  剩余未命中不能全部视为可消除工作，其中包含首次加载、新增内容、对齐等因素。
- 每个容量充足策略轮仍记录 113 次 association、81 次 tool_wait 和 32 次任务清理。
  81 次信号全部没有派生动作。
  结合客户端的 submit/query/ACK 和清理查询，每轮至少涉及约 600 次独立控制 HTTP 调用；这是代码路径推算，不是网络 profiler 计数。
  零数据搬运并不代表零控制开销。
- `RolloutClient.generate` 在发送下一轮推理前等待后台控制任务；`action` 即使拿到提交结果也继续通过 `wait` 查询和 ACK。
  后续轮次的准备等待中位数，原生约 0.04 ms，策略约 79.5–81.6 ms；后续轮次 TTFT 中位数约从 302–311 ms 变为 529–545 ms。
  所有请求累计的准备等待为 15–17 秒，但这些等待并发重叠，不能把它当作总耗时增加，也不能据此精确分解 3.6% 的退化。
- 服务端 `KVPolicyRuntime.on_signal` 在判断是否生成动作之前就失效并重建观察；指导调度还需要请求需求计算和队列评分。
  低压力目前能避免实际 MOVE，却没有让整条控制路径接近无开销。
  仅配额的压力实验也发出了 81 次未被策略消费的信号，表明测试驱动把纯调度与不必要的 KV 控制流程耦合在了一起。
- 本轮未优化正常推理所需的矩阵运算、解码或 TP 通信。
  已有数据不能判定剩余时间主要受 GPU 算力、显存带宽、通信还是 CPU 调度限制；需要采集算子、通信与调度耗时才能归因。
  89% 的 token 命中率也不能直接换算为 89% 的计算耗时节省。

当前明确可修的方向是：非必需控制不阻塞下一轮推理；复用提交回执、减少查询/ACK 往返；无收益信号和纯配额模式避免不必要的关联/搬运控制；低压力时跳过不需要的状态观察。
真正依赖 COPY 完成的请求仍须遵守发布和缓冲区生命周期，不能直接删除必要等待。
移除这些开销主要是恢复到原生水平。
要在约 54 秒的原生基线上提升吞吐 25%，需要将耗时降低到约 43.3 秒，即再消除至少约 10.8 秒的真实关键路径工作；目前没有证据证明控制优化本身具备这部分收益。

当前本地短工具场景，应先给工作集足够的 KV 空间；必须限制 KV 时，优先评估配额调度。
冷层搬运按压力、工具等待时间和复用收益选择性启用。
后续优化应重点减少重复写入和控制 RPC/轮询开销，并用容量充足组作为退化检查。


加 `--policy-components quota` 选择仅配额；`--cache-gib 8` 复现容量充足组； `--live-after-replay` 另外执行原轨迹配置对应的真实在线工具循环。
工具会创建并清理自己的服务和 Store，端口占用时拒绝启动。
