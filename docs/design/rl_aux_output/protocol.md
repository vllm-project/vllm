# Aux Outputs for RL: Delivery Protocol

Status: draft (v5). Measurements behind each rule are in [experiments](experiments.md); sizes in [scenarios](scenarios.md); alternatives in [design space](design_space.md).

## 1. What a row is

**Outputs.**

| Output | Follows | Positions | Bytes/token (DeepSeek-V4.1-Flash) | Use |
|---|---|---|---|---|
| `routed_experts` (R3) | KV | all | 40 layers × 6 × uint16 = 480 B | routing replay in the trainer |
| `indexer_topk` | KV | all | 8 layers × 512 × 20 bit, zstd: ~2.5–3.6 KB (16 KB raw) | sparse-attention replay |
| `topk_logprobs` | sampling | generated | k × 8 B | truncated distillation, KL |
| `sampling_mask` | sampling | generated | CSR, ≤ 256 ids per row | reconstruct the truncated/masked support |
| `hidden_states` | sampling | generated | `lm_head` input in the dtype that enters `lm_head` (codec `raw`): 16 KB as float32; optional fp8 + per-token scale (codec `fp8`): ~4.1 KB | full-vocabulary student training |

The sampled token's logprob is returned inline with the response; that number is the behavior probability. Logits recomputed from hidden states are not bitwise equal to vLLM's (max diff 2e-4 even in fp32), so trainers must not try to reproduce the behavior logprob from them.

**Hidden states are exact by default.** They are stored as the very values that entered `lm_head`, so the trainer's full-vocabulary logits differ from the engine's only by its own matmul (logprob error max 7.8e-4 against about 0.3 with fp8). fp8 is a size option, chosen per deployment, and the manifest says which one a request used.

**Indexer rows.** A cell (one position, one indexer layer) holds the top-k selected positions in ascending order with the `-1` pads last. That is the order the engine's top-k produces and the trainer's top-k kernel expects, so replay compares cells as sequences, not sets. Every codec must restore exactly this order on decode; a decoder that reorders pads still passes any set-based check while replay silently loses its effect.

**Position convention.** Row `p` belongs to position `p`: the position that processes token `p` and produces the logits for token `p+1`. KV-following outputs have a row at every position. Sampling-following outputs have a row only where `p+1` is a token generated by this request, i.e. `p ∈ [P−1, P+O−1)` for prompt length `P` and output length `O`. Positions count the engine-side sequence (after multimodal expansion).

**Units.**

- *Request*: one engine request (one turn).
- *Trajectory*: the sequence of requests whose prompts extend each other (the turns of one agent rollout, one GRPO sample, one fork branch).
- *Session*: the consumption unit, released together: a GRPO group, a trajectory tree, one agent rollout. A session contains one or more trajectories.
- *Weight version*: incremented by every weight update the engine applies.

**The right row.** For every position of a trajectory, the delivered row is the one from the first computation of that position in the trajectory, i.e. the computation whose KV or logits the trajectory went on to use. Later computations of the same position (next-turn re-prefill of an unfinished block, recomputation after preemption, a prefill overlapping a speculative verification) never replace it. For a fork, positions before the fork point belong to the parent trajectory.

## 2. Invariants

1. **Requested means delivered, or reported missing.** Every requested row can be read, or the manifest names the rows that are missing. A row is never replaced by a different computation.
2. **First computation wins**, per trajectory, as defined above.
3. **Same version, same tokens, same row.** Under the train-inference consistent build (#62365: batch invariance with bitwise identical results across batch composition, chunk size and prefix-cache hit vs miss), all computations of the same tokens at the same weight version are identical. Rows of one version may therefore be shared between trajectories of a session. Rows of different versions are never interchangeable.
4. **Rows carry their version.** The manifest lists `weight_versions` segments covering `[0, rows)`; each segment's version is the version of the computation whose rows are stored there.
5. **Freed once used.** All objects of a session are deleted when the session is consumed and the training step has committed.
6. **Every reference points at objects that exist.** The manifest is written after the objects it lists; the response is sent after the manifest.

## 3. Request and response

**Request fields.**

| Field | Meaning |
|---|---|
| `aux_outputs` | Which outputs to produce. Absent means none. |
| `aux_session` | The session. All objects share the key prefix `<job>/<session>/` and are released together. |
| `aux_trajectory` | The trajectory within the session (needed when a session holds several: GRPO samples, forks). Tails and version segments are tracked per trajectory. |
| `aux_parent` | For the first request of a fork: the parent trajectory (`""` for the session's root). The fork takes over the parent's state at the fork point. Ignored without `aux_trajectory`. |
| `aux_start` | "I already have the first `aux_start` rows." For the next turn of a trajectory it must equal the previous request's real row count (`prompt + generated − 1`): the engine cannot tell real rows from truncated drafts (§6.7), so it relies on this value to know which previous rows came first. |

Sampling-parameter constraints (when requesting `topk_logprobs`, `sampling_mask` or `hidden_states`): temperature, `top_k`, `top_p`, `min_p` and token masking are allowed; with any truncation or masking `top_k ≤ 256`; parameters that change logit values (penalties, `logit_bias`) are rejected because the trainer cannot reconstruct them.

**Response.**

```json
"prompt_token_ids": [...],
"aux": {
  "status": "ok",
  "manifest": {"backend": "mooncake", "key": "<job>/<session>/<req>/m", "nbytes": 2380}
}
```

- `status` is always present when `aux_outputs` was requested; `unavailable` only if the store is unreachable. A response without `aux` to a request that asked for it is an error.
- `<req>` is the caller-visible request id (engine-internal ids carry a random suffix).
- **Inline mode** (small scale): data in the response, nothing in a store.

**Manifest** (one per request, covering the whole sequence `[0, rows)`):

| Field | Meaning |
|---|---|
| `key_prefix`, `tail_key` | `<job>/<session>` and the R3 tail key; readers build every object key from these |
| `blocks` | ordered object names of the full blocks; usually the block hash, `hash~<tag>` for a trajectory's own copy (§5), `hash~r` never appears (a lost block is reported missing) |
| `tail_start`, `tail_nbytes` | the tail object covering `[tail_start, rows)`; it can span several blocks |
| `rows` | rows covered; can exceed `L−1` (see §7) |
| `weight_versions` | `[[start, version], ...]` covering `[0, rows)`, describing the stored objects |
| `fields` | per output: name, dtype, per-token shape, codec, layout, `missing` and `holes` counts; for sampling-following outputs the chunk count and every chunk's row count (`chunk_lens`: a preemption flushes a short chunk). Hidden states: codec `raw` stores each row as `d` values of the field's `dtype`, the dtype that enters `lm_head`; codec `fp8` stores `d` e4m3 codes plus one float32 scale per row. Indexer: the codec of block and tail objects (patches name theirs in `r3_cone`) |
| `invalid_from` | first position computed on invalid KV, if the engine ever rewound this request (§6.8); rows from here are not valid |
| `r3_cone` | partial capture only (§6.11): the trajectory's patch list, `ends`, and `uncovered` counts |

## 4. Objects

- **Block** `<job>/<session>/<name>`: KV-following rows of one full KV block (R3; the indexer under `<name>/idx`). Written when the block fills and its hash is known.
- **Tail** `<job>/<session>/<req>/t` (indexer: `/t/idx`): rows from `tail_start` to `rows`, written at request end.
- **Generated chunk** `<job>/<session>/<req>/h/<i>`: sampling-following outputs (hidden states: 64 generated positions per chunk).
- **Manifest** `<job>/<session>/<req>/m`.
- **Error marker** `<manifest key>!err`: written when the manifest, the tail or a generated chunk of that request could not be written.

Objects are immutable. Block hashes are vLLM's prefix block hashes (including multimodal, LoRA and `cache_salt` keys), so a name's content depends only on its full prefix.

## 5. Deduplication and copies

Within a session a block is stored once per distinct computation that some trajectory must see. Each stored object carries a version record: the weight version of every position in the block.

- **Same trajectory:** a trajectory that already holds a block (its own copy, or a shared one it used) drops any later recompute of it. First computation wins.
- **Another trajectory, same version at every position:** shares the stored copy (invariant 3). The comparison is per position, not per set of versions: a block whose first rows are at v0 and the rest at v1 is not the same as a block computed entirely at v1. Identical bytes do not override a version mismatch, because the labels must describe the delivered rows.
- **Another trajectory, a different version anywhere in the block:** stores its own copy as `hash~<tag>` and lists that name.
- **Rows served by a prefix hit:** inside the requesting trajectory's version record they are marked "as recorded by the object" and match any version. A copy that keeps such rows takes their versions from the object it hit.
- **Blocks entirely before the request's own rows:** a block whose last position precedes the request's first computed position, or that the trajectory (or its parent, for a fork) already holds, was computed first by an earlier request. It is shared as is.
- **Failures are per object:** a write failure marks that exact object (`hash`, `hash~<tag>`, or an indexer object) as lost. The lost object is never rewritten. A failed indexer object does not affect the block's R3 object.
- **Writer bookkeeping:** per (session, trajectory) the writer keeps which name it holds for each hash, plus a digest, owner and version record per stored object. All of it is dropped when the session is released.

## 6. Engine behavior, event by event

### 6.1 Prefill and decode

Rows are captured from the forward, per request, at the captured positions (not the scheduler's token start, which async scheduling runs ahead). Full blocks are written as soon as their hash is known; blocks that fill before their hash arrives wait in the request's state.

### 6.2 Prefix-cache hits

Allowed only up to the longest prefix the session already published (the delivery pool is the session's cache). Rows for hit positions are therefore always in the pool. Cross-session hits are truncated.

A hit can end mid-block. The rows of that block before the hit point were computed by whoever filled the block, and this request never captured them. When the request publishes the block, those rows are taken from the session's stored object for the block, which is the object whose KV the hit used. If that object cannot be read, the block is reported missing. Pad rows are never published as valid.

### 6.3 The next turn of a trajectory

vLLM does not cache unfinished blocks, so the next turn re-prefills `[start of the last unfinished block, aux_start)`. Those positions keep the previous request's rows: the worker remembers each trajectory's last tail (start and rows, possibly several blocks) and splices it into any block or tail written later at the same positions. With speculative decoding the previous request's last step can already have computed position `aux_start` itself (its input is the last sampled token); that row came first too and is spliced, and the new version segment starts one position later.

### 6.4 Forks

The fork's first request names its parent. At its first capture the fork takes over the parent's state at the fork point:

- **Tail:** the parent request the fork continues from ended at the fork point, so its tail is the parent tail reaching `aux_start` with the smallest end. Later turns of the parent end further. The worker keeps a short history of tails per trajectory, keyed by start and end.
- **Blocks:** the blocks the parent held before the fork point. With speculative decoding the parent's last step may have verified position `aux_start` itself and completed that block. In that case the fork-point tail starts right after the block, and the whole block is the parent's.
- **Version segments:** the parent's segments up to where the fork's own rows begin. Segments the parent started later belong to the parent's later turns.
- **Fork-point tail gone:** if the tail has left the history, the fork's recompute of the partial block is its own computation and carries its own version. It is never labelled with the parent's.

### 6.5 Preemption

A preemption is not a finish. The scheduler reports it separately. The worker stashes what only this computation has, plus a freeze point equal to the capture cursor:

- rows of blocks not yet published, and the tail;
- indexer blocks;
- the hidden-state cursor and chunk lengths;
- `invalid_from`.

**Resume.** The stash is restored, and positions below the freeze point keep the stashed rows. This happens with or without session metadata on the resumed request.

**Finish.** At the real finish, a stashed full block goes through the version rule of §5 even if a sibling has meanwhile published the same hash. The stash holds this trajectory's first computation, and a sibling's copy can be of another version. A request that finishes while parked (the output in flight at the preemption ended it) is finished from the stash, including tails that span several blocks.

**Abort.** A request that ends and is preempted in the same step is finished, not stashed. An abort while parked drops the stash.

### 6.6 In-flight weight update

`pause_scheduler("keep", clear_cache=True)` waits until no batch is in flight, then `reset_prefix_cache(reset_running_requests=True)` preempts every running request and starts a new store namespace (generation). Requests that finished before the reset are finished in the old generation first; running requests are stashed as in 6.5. Then the version is bumped and scheduling resumes. Versions are stamped on rows at forward time.

### 6.7 Speculative decoding

- A request has 1 + num_draft logits rows per step. Hidden states are captured for every logits row of the global batch with per-request offsets (before sampler sharding), and only the accepted rows are kept.
- A full block can finish before its hash arrives, and capture can end exactly on a block boundary: the tail is then assembled from those hash-less blocks plus the buffer's partial block, if any.
- The last step can accept drafts past `max_tokens`; the scheduler truncates those tokens, but their rows were captured. They are delivered in the tail (readers truncate to `L−1`) and never spliced into the next request, whose prompt has different tokens there.

### 6.8 KV-load failures

Block-level KV-load failure recovery rewinds a request's computed tokens. vLLM refuses block-level recovery for models with several KV cache groups (DeepSeek-V4.1-Flash has 9), and request-level failures recompute before any capture, so the rewind cannot occur there. For single-group models, a rewind marks `invalid_from` in the manifest: rows computed on invalid KV are reported, never delivered as valid.

### 6.9 Writes and write failures

- A background thread writes; it never blocks the forward. One TP rank writes (the others compute identical rows and skip); "key already exists" counts as success.
- **Host work off the critical path.** The writing rank also captures and assembles every request's rows each step. Done inline, under the lock the engine's output path holds, that work stalled the rank's GPU while the other ranks waited for it in collectives, and it, not the bytes, was most of the cost of the indexer and hidden states (experiments: engine overhead). Capture therefore runs on its own thread, fed by one ordered queue from inside the lock: the queue preserves the order in which the output path handled requests, so first computation wins exactly as if the work ran inline. The queue is bounded, and an error on the capture thread is raised at the engine's next step instead of being lost.
- **Encoding off the writer thread:** indexer compression (zstd, which releases the GIL) runs on a small thread pool ahead of the writer. The writer takes the results in order. Manifests stay on the writer thread, because they read the sizes of the objects put before them. At 512K context, a single writer thread spent 46% of its time in zstd and the engine paused about 3% of the time on writer backlog. The pool removes most of that wait.
- **Full pool:** objects must never be evicted (§9). A put into a full pool fails and is retried until it lands. Each worker caps pending bytes, and beyond the cap the engine schedules no new tokens until writes catch up.
- **A failed block write:** that object is lost for good, and its exact name is marked lost. Later recomputations are not substituted: they can be of another version, and the version record of those positions describes the lost computation. The block stays missing, and every manifest that lists it reports it.
- **A failed manifest, tail or chunk write:** the writer writes the request's error marker (retrying ~1 s). A reader that finds the marker fails that request at once instead of waiting; siblings are unaffected.
- Tail and manifest are written as soon as the request finishes, not at a later engine step (an idle engine never runs one).

### 6.10 Abort and undeliverable responses

A normal abort writes a manifest for the computed positions. Request-private objects of responses that cannot be delivered are deleted by the engine; session-shared blocks are left to session release.

### 6.11 Partial capture on models with replay layers

**Why.** On DeepSeek-V4.1 only layers up to 20 write KV for every row. The rest of layer 20 and layers 21–39 run in eager prefill steps on each request's trailing rows only, in stages that shrink by 127 rows per layer from a 128-row window. Asking for exact KV-following rows at every position forces every new prompt row through those layers. That is where the cost of R3 comes from on this model (experiments: engine overhead). Partial capture keeps the stages as they are and delivers only the cells some sampled token depends on.

**Which cells are exact.** A prefill step ending at `e` computes a cell at layer `L ≥ 20` exactly only for its last `cone(L) = 128 + (39 − max(L, 21)) × 127` rows. When the step replays from a start `r > 0` inside the context (a prefix hit), cells below `r + (L + 1) × 127` are not exact either. A step of at most 128 rows (decode) is exact on every layer.

**Blocks and tails** keep the rules of §4–§6. Their columns below layer 20 are exact and are delivered as before. Readers ignore their columns from layer 20 up.

**Which cells are needed.** A sampled token at position `t` depends on the cell at layer `L ≥ 20` of the rows `[t − need(L), t)`, with `need(L) = 1 + (39 − L) × 127`: one 127-row window step per later layer. `cone(L)` is at least `need(L)`, so every step computes the cells its own sampled token needs.

**Cone patches.** Each request collects, per step, the deep cells inside that step's exact range, first computation first, for R3 and for the indexer slots of layers 20 and up. At finish it writes one patch object per output (`<req>/t/c/r3`, `<req>/t/c/idx`) holding the needed cells that no earlier patch of the trajectory holds. Each cell carries its weight version. For deep cells that per-cell version is the authoritative one; the manifest's version segments describe the blocks and the tail. The two differ in one case: a fork whose fork-point tail is gone recomputes that block's shallow rows under its own version, while the parent's deep cells below the fork point stay.

**The patch list.** The manifest field `r3_cone` lists every patch of the trajectory in request order, each with the end up to which its rows belong to this trajectory:

- At finish, earlier patches are clipped to the request's cut. The cut is `aux_start + 1` when the previous request of the trajectory (or the parent, for a fork) computed position `aux_start` itself and this request holds that computation: the previous tail contains it, or it completed a block whose hash this request shares. Otherwise the cut is `aux_start`; a request that edits the context inside that block, or a fork whose fork-point tail is gone, owns the rows from `aux_start` on.
- A fork starts from the parent's list clipped at the fork point. Indexer patch entries name their codec (`idx_codec`).
- `ends` lists `[prompt, end]` for every request of the trajectory, clipped at the cut like the patches and inherited at a fork. With it a reader computes the needed cells of the whole trajectory (`need(L)` rows before each sampled token) and reports, position by position, every needed cell no patch holds.
- `uncovered` counts this request's needed cells that no patch holds, for example cells of a window the request did not compute. Nothing is substituted for them.

**Reader.** Set every deep cell to no-replay (R3 `65535`, indexer `−2`), then overlay the listed patches in order, each up to its end, first written wins. The trainer runs its own routing (or indexer) at no-replay cells, cell by cell. A replay hook that gathers at the sentinel instead is wrong.

**Preemption.** The request's cells are stashed and restored on resume, so cells computed before the preemption win over the recompute. A recompute of the same step adds nothing. A request aborted while it replays below the preemption point finishes at that point from the stash, like a request that finished while parked; needed cells the stash cannot supply count in `uncovered`.

Partial capture changes what is stored, not the invariants: every cell a sampled token depends on is delivered from its first computation, with its version, or counted in `uncovered`.

## 7. Training side

```python
rows = aux.read(manifest_ref, kind="routed_experts", layers=range(l0, l1), tokens=sample_tokens)
...
aux.release_session(job, session)  # after the session is consumed and the step committed
```

- **read** reads the manifest, then the blocks, chunks and tail, and returns rows for `[0, L−1)`:
  - truncate to `L−1`: the manifest can cover more rows (async scheduling computes one more position; speculative decoding can capture truncated drafts);
  - check the error marker; a missing block or a `missing`/`holes` count fails the sample;
  - verify each block's tokens against the sample;
  - R3 sanity: the 6 expert ids in a row are distinct; an all-zero row is an error;
  - replay compares expert sets; rows whose set is unchanged keep the trainer's own ids and weights;
  - with partial capture (§6.11), overlay the cone patches; no-replay cells run the trainer's own routing;
  - a failed read fails the step collectively: all ranks all-reduce a success flag and retry or skip together;
  - decode on the GPU: copy the encoded indexer bytes and decode them where replay runs, in engine order (§1, indexer rows). A single CPU thread decoding numpy is the bottleneck of the whole path: about 180 MB/s, against more than 10 GB/s for the store's get. Decoded, one 512K request's indexer is about 8 GiB of int32, so decode it in position ranges, or on the CPU, when the GPU has no room for it.
- **release** deletes everything under `<job>/<session>/` (Mooncake `remove_by_regex`), once the session will not grow, all reads are done and the step has committed. It also tells the writer to drop the session's bookkeeping (a release marker), so writer memory is bounded by live sessions.
- Retrying a failed step re-reads; rolling back to an earlier checkpoint requires regeneration; saving rollouts offline requires reading them inline first.

## 8. Driver

1. **In-flight cap:** admit at most `C` sessions with `C × max_session_bytes ≤ 0.75 × pool`, where `max_session_bytes = longest context × bytes/token × branching factor`. The next turn of an admitted session is always admitted. Count bytes, not requests; cap each policy separately.
2. **Release** as in §7.
3. **Deadlock fallback:** if the pool fills and no session completes for a while (default 60 s), abort the most recently admitted sessions, delete their objects and regenerate them.

## 9. Store

- **No eviction.** A listed object that disappears breaks invariant 4 silently: the reader can only time out. Objects are written hard-pinned, or soft-pinned with eviction of soft-pinned objects disabled on the master. They leave the store only through session release or the abort fallback. Without pinning, an overfull pool evicted 1.81M keys and the readers hung.
- **Segment lifetime.** Mooncake keeps one replica per object by default, so an object lives in whichever segment it was placed in. A node's segment must stay up until every consumer of every object placed on it has read and released. Taking down one replica's segment when that replica finished removed other replicas' objects.
- **Sizing with real bytes per token.** At 512K context the indexer is 10 KB per token packed and about 5.6 KB after zstd (ratio ~1.8, against 4.6–6.7 at short context); under partial capture blocks omit the deep indexer slots, which shrinks it further. R3 adds 480 B per token, and hidden states 16 KB per generated token as exact float32 (about 4.1 KB as fp8). The in-flight cap of §8 must use the numbers of the configured codecs at the target context; a cap computed from short-context sizes over-admits by about 2×.
- At job end, delete everything under `<job>/` and report the number of keys as a leak metric (expected 0).

## 10. Checklist

Inference framework:
1. Send `aux_outputs`, `aux_session`, `aux_trajectory`, and `aux_parent` on a fork's first request.
2. Store `prompt_token_ids`, the manifest reference, the generated tokens and the inline sampled logprobs.
3. Treat a missing `aux` as an error.

Training framework:
1. Carry the manifest reference through shuffling, packing and rank sharding.
2. Keep the in-flight cap; release after the step commits.
3. Read per rank, truncate to `L−1`, fail collectively.
4. Hook R3 replay where the model computes routing (some MoE implementations call `route` directly, bypassing a router-level hook).
5. Run the train-inference consistent build; otherwise invariant 3 does not hold and siblings must not share rows.

## 11. Scenarios

| Scenario | What happens |
|---|---|
| Single-turn GRPO | n trajectories, one session; prompt blocks stored once per version |
| Multi-turn agent | one trajectory; each turn writes only new blocks; the last manifest covers the sequence |
| Forks / tree search | each branch is a trajectory with a parent; parent blocks shared |
| Weights updated between turns | each turn's rows labelled with their version; a block recomputed at another version by another trajectory gets its own copy |
| In-flight weight update | pause, reset, stash running requests, bump the version, resume |
| Preemption | stash and resume; no rows lost or replaced |
| Speculative decoding | accepted rows only; hash-lagging blocks delivered in the tail |
| Full pool | writer blocks, engine pauses scheduling; nothing dropped |
| Write failure | reported as missing or as an error marker; never substituted |
| Cross-session prefix hit | truncated |
| Context rewriting / compaction | rewritten prefixes hash differently and are rewritten |
| Multiple policies / LoRAs | a session per policy; separate in-flight caps |
| Job end | delete by job prefix, report the count |

## 12. Known limits

- **A prefix hit does not say which computation produced the KV it hits.** The session's first copy of a block is listed for every hit on that hash. This is wrong only if all three of the following happen: the KV of the first computation is evicted from every cache tier; another trajectory recomputes the block at a different weight version (it keeps its own copy, and its KV is now the cached one); and a third trajectory hits that KV. Two fixes are possible. One is to follow vLLM's KV cache events (stored / removed, per block hash) so the worker knows which object the cached KV belongs to. The other is to carry R3 in the KV cache itself (#64383), which makes rows follow the KV by construction. The indexer would still need the first.
- **Partial capture, window-carrying KV loads.** The worker takes a request's first captured position as its replay start. A KV load that restores the sliding window computes from the hit without replaying, so its exact cells are masked and reported in `uncovered`, not delivered. The scheduler's replay start has to reach the worker to fix this. Such loads are not used with the P-S design.
- **Partial capture, forks after a regeneration.** A fork takes the parent's current patch list. If the parent regenerated below the fork point after the fork's snapshot, the fork would read the other branch's cells. Blocks pick the branch by content hash; patches are positional. A branch id per patch fixes it.
- **Partial capture, `uncovered` is per request.** A hole is reported by the request whose tokens needed it, not again by later requests of the trajectory.
- **The engine-local row cache (c1)** reads hit rows from a generation-scoped base store. Its version records describe spliced rows rather than the base payload, and a request parked across a generation change reads the new generation. The P-S design (§6.2) does not use this path.
