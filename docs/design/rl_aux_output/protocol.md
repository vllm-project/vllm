# Aux Outputs for RL: Delivery Protocol

Status: draft (v5). Measurements behind each rule are in [experiments](experiments.md); sizes in [scenarios](scenarios.md); alternatives in [design space](design_space.md).

## 1. What a row is

**Outputs.**

| Output | Follows | Positions | Bytes/token (DeepSeek-V4.1-Flash) | Use |
|---|---|---|---|---|
| `routed_experts` (R3) | KV | all | 40 layers × 6 × uint16 = 480 B | routing replay in the trainer |
| `indexer_topk` | KV | all | 8 layers × 512 × 20 bit, zstd: 2.5–3.6 KB up to 128K context, ~5.6 KB at 512K (16 KB raw) | sparse-attention replay |
| `topk_logprobs` | sampling | generated | 128 × (int32 id + fp32 logprob) = 1 KB | truncated distillation, KL |
| `sampling_mask` | sampling | generated | CSR, ≤ 256 ids per row | reconstruct the truncated/masked support |
| `hidden_states` | sampling | generated | `lm_head` input in the dtype that enters `lm_head` (codec `raw`): 16 KB as float32 | full-vocabulary student training |

The sampled token's logprob is returned inline with the response; that number is the behavior probability. Logits recomputed from hidden states are not bitwise equal to vLLM's (max diff 2e-4 even in fp32), so trainers must not try to reproduce the behavior logprob from them.

**Hidden states are exact.** They are stored as the very values that entered `lm_head`, so the trainer's full-vocabulary logits differ from the engine's only by its own matmul (logprob error max 7.8e-4).

**Top-k logprobs.** k = 128, at generated positions only. Today they are returned inline in the response, by the frontend; on the one-node 14.6K workload this made rollouts 46.8% longer (experiments: top-k inline). A store path like that of hidden states is planned, not built: captured on the GPU at sampling, written in generated chunks per request (§4), and read back as `[generated length, 128]`.

**Indexer rows.** A cell (one position, one indexer layer) holds the top-k selected positions in ascending order with the `-1` pads last. That is the order the engine's top-k produces and the trainer's top-k kernel expects, so replay compares cells as sequences, not sets. Every codec must restore exactly this order on decode; a decoder that reorders pads still passes any set-based check while replay silently loses its effect.

**Position convention.** Row `p` belongs to position `p`: the position that processes token `p` and produces the logits for token `p+1`. KV-following outputs have a row at every position. Sampling-following outputs have a row only where `p+1` is a token generated by this request, i.e. `p ∈ [P−1, P+O−1)` for prompt length `P` and output length `O`. Positions count the engine-side sequence (after multimodal expansion).

**Units.**

- *Request*: one engine request (one turn).
- *Trajectory*: the sequence of requests whose prompts extend each other (the turns of one agent rollout, one GRPO sample, one fork branch).
- *Session*: the consumption unit, released together: a GRPO group, a trajectory tree, one agent rollout. A session contains one or more trajectories.
- *Weight version*: incremented by every weight update the engine applies.
- *Generation*: the engine's store namespace. A weight update that resets the prefix cache starts a new one (§6.6).

**Two delivery modes.**

- *Store mode*, the subject of §3–§11: rows go to a store keyed per session, and the store doubles as the session's prefix cache, so rows for prefix-hit positions are always there (§6.2). The design space calls this design P-S ("pool as session cache").
- *Inline mode* (§12), for small scale: rows come back in the response. Rows for prefix-hit positions come from an engine-local block-row cache, allocated and evicted with the KV; the design space calls that cache c1.

The store is Mooncake: a master places objects on holders, each a process that contributes a memory segment and, by default, a local SSD directory (§8, §9).

**The right row.** For every position of a trajectory, the delivered row is the one from the first computation of that position in the trajectory, i.e. the computation whose KV or logits the trajectory went on to use. Later computations of the same position (next-turn re-prefill of an unfinished block, recomputation after preemption, a prefill overlapping a speculative verification) never replace it. For a fork, positions before the fork point belong to the parent trajectory.

## 2. Invariants

1. **Requested means delivered, or the request fails.** Every requested row can be read, every cell of it exact. If a store write the request depends on fails, the request fails: its reader gets an error, not a partial sample. A row is never replaced by a different computation.
2. **First computation wins**, per trajectory, as defined above.
3. **Same version, same tokens, same row.** Under the train-inference consistent build (#62365: batch invariance with bitwise identical results across batch composition, chunk size and prefix-cache hit vs miss), all computations of the same tokens at the same weight version are identical. Rows of one version may therefore be shared between trajectories of a session. Rows of different versions are never interchangeable.
4. **Rows carry their version.** The manifest lists `weight_versions` segments covering `[0, rows)`; each segment's version is the version of the computation whose rows are stored there.
5. **Freed once used.** All objects of a session are deleted when the session is consumed and the training step has committed.
6. **Every reference points at objects that exist.** The manifest is written after the objects it lists; the response is sent after the manifest.

## 3. Request and response

**Request fields.**

| Field | Meaning |
|---|---|
| `aux_outputs` | Which outputs to produce. Absent means none. |
| `aux_session` | The session. All objects share the key prefix `<job>/<session>/` and are released together. |
| `aux_trajectory` | The trajectory within the session (needed when a session holds several: GRPO samples, forks). Tails and version segments are tracked per trajectory. |
| `aux_parent` | For the first request of a fork: the parent trajectory (`""` for the session's root). The fork takes over the parent's state at the fork point. Ignored without `aux_trajectory`. |
| `aux_start` | "I already have the first `aux_start` rows." For the next turn of a trajectory it must equal the previous request's real row count (`prompt + generated − 1`): the engine cannot tell real rows from truncated drafts (§6.7), so it relies on this value to know which previous rows came first. |

Sampling-parameter constraints (when requesting `topk_logprobs`, `sampling_mask` or `hidden_states`): temperature, `top_k`, `top_p`, `min_p` and token masking are allowed; with any truncation or masking `top_k ≤ 256`; parameters that change logit values (penalties, `logit_bias`) are rejected because the trainer cannot reconstruct them.

**Response.**

```json
"prompt_token_ids": [...],
"aux": {
  "status": "ok",
  "manifest": {"backend": "mooncake", "key": "<job>/<session>/<req>/m", "nbytes": 2380}
}
```

- `status` is always present when `aux_outputs` was requested; `unavailable` only if the store is unreachable. A response without `aux` to a request that asked for it is an error.
- `<req>` is the caller-visible request id (engine-internal ids carry a random suffix).
- **Inline mode** (small scale) returns the rows in the response instead of the store; it is specified in §12.

**Manifest** (one per request, covering the whole sequence `[0, rows)`):

| Field | Meaning |
|---|---|
| `key_prefix`, `tail_key` | `<job>/<session>` and the R3 tail key; readers build every object key from these |
| `blocks` | ordered object names of the full blocks: usually the block hash; `hash~<tag>` when the trajectory keeps its own copy of a block another trajectory stored at a different weight version (§5); `hash~r` never appears |
| `tail_start`, `tail_nbytes` | the tail object covering `[tail_start, rows)`; it can span several blocks |
| `rows` | rows covered; can exceed `L−1` (see §7) |
| `weight_versions` | `[[start, version], ...]` covering `[0, rows)`, describing the stored objects |
| `fields` | per output: name, dtype, per-token shape, codec, layout; for sampling-following outputs the chunk count and every chunk's row count (`chunk_lens`: a preemption flushes a short chunk). Hidden states: codec `raw` stores each row as `d` values of the field's `dtype`, the dtype that enters `lm_head`. Indexer: the codec of block and tail objects |
| `invalid_from` | first position computed on invalid KV, if the engine ever rewound this request (§6.8); rows from here are not valid |

## 4. Objects

- **Block** `<job>/<session>/<name>`: KV-following rows of one full KV block (R3; the indexer under `<name>/idx`). Written when the block fills and its hash is known.
- **Tail** `<job>/<session>/<req>/t` (indexer: `/t/idx`): rows from `tail_start` to `rows`, written at request end.
- **Generated chunk** `<job>/<session>/<req>/h/<i>`: sampling-following outputs (hidden states: 64 generated positions per chunk).
- **Manifest** `<job>/<session>/<req>/m`.
- **Error marker** `<manifest key>!err`: written when the manifest, the tail or a generated chunk of that request could not be written.

Objects are immutable. Block hashes are vLLM's prefix block hashes (including multimodal, LoRA and `cache_salt` keys), so a name's content depends only on its full prefix.

## 5. Deduplication and copies

Within a session a block is stored once per distinct computation that some trajectory must see. Each stored object carries a version record: the weight version of every position in the block.

- **Same trajectory:** a trajectory that already holds a block (its own copy, or a shared one it used) drops any later recompute of it. First computation wins.
- **Another trajectory, same version at every position:** shares the stored copy (invariant 3). The comparison is per position, not per set of versions: a block whose first rows are at v0 and the rest at v1 is not the same as a block computed entirely at v1. Identical bytes do not override a version mismatch, because the labels must describe the delivered rows.
- **Another trajectory, a different version anywhere in the block:** stores its own copy as `hash~<tag>` and lists that name.
- **Rows served by a prefix hit:** inside the requesting trajectory's version record they are marked "as recorded by the object" and match any version. A copy that keeps such rows takes their versions from the object it hit.
- **Blocks entirely before the request's own rows:** a block whose last position precedes the request's first computed position, or that the trajectory (or its parent, for a fork) already holds, was computed first by an earlier request. It is shared as is.
- **A failed write fails every request that lists the object.** The writer records the exact name (`hash`, `hash~<tag>`, or an indexer object) as failed and never rewrites it; a request whose manifest would list a failed name gets an error marker instead of a manifest (§6.9).
- **Writer bookkeeping:** per (session, trajectory) the writer keeps which name it holds for each hash, plus a digest, owner and version record per stored object. All of it is dropped when the session is released.

## 6. Engine behavior, event by event

### 6.1 Prefill and decode

Rows are captured from the forward, per request, at the captured positions (not the scheduler's token start, which async scheduling runs ahead). Full blocks are written as soon as their hash is known; blocks that fill before their hash arrives wait in the request's state.

### 6.2 Prefix-cache hits

Allowed only up to the longest prefix the session already published (the delivery pool is the session's cache). Rows for hit positions are therefore always in the pool. Cross-session hits are truncated.

A hit can end mid-block. The rows of that block before the hit point were computed by whoever filled the block, and this request never captured them. When the request publishes the block, those rows are taken from the session's stored object for the block, which is the object whose KV the hit used. If that object cannot be read, the block cannot be written, and the request fails like any request with a failed write (§6.9). Pad rows are never published as valid.

### 6.3 The next turn of a trajectory

vLLM does not cache unfinished blocks, so the next turn re-prefills `[start of the last unfinished block, aux_start)`. Those positions keep the previous request's rows: the worker remembers each trajectory's last tail (start and rows, possibly several blocks) and splices it into any block or tail written later at the same positions. With speculative decoding the previous request's last step can already have computed position `aux_start` itself (its input is the last sampled token); that row came first too and is spliced, and the new version segment starts one position later.

### 6.4 Forks

The fork's first request names its parent. At its first capture the fork takes over the parent's state at the fork point:

- **Tail:** the parent request the fork continues from ended at the fork point, so its tail is the parent tail reaching `aux_start` with the smallest end. Later turns of the parent end further. The worker keeps a short history of tails per trajectory, keyed by start and end.
- **Blocks:** the blocks the parent held before the fork point. With speculative decoding the parent's last step may have verified position `aux_start` itself and completed that block. In that case the fork-point tail starts right after the block, and the whole block is the parent's.
- **Version segments:** the parent's segments up to where the fork's own rows begin. Segments the parent started later belong to the parent's later turns.
- **Fork-point tail gone:** if the tail has left the history, the fork's recompute of the partial block is its own computation and carries its own version. It is never labelled with the parent's.

### 6.5 Preemption

A preemption is not a finish. The scheduler reports it separately. The worker stashes what only this computation has, plus a freeze point equal to the capture cursor:

- rows of blocks not yet published, and the tail;
- indexer blocks;
- the hidden-state cursor and chunk lengths;
- `invalid_from`.

**Resume.** The stash is restored, and positions below the freeze point keep the stashed rows. This happens with or without session metadata on the resumed request.

**Finish.** At the real finish, a stashed full block goes through the version rule of §5 even if a sibling has meanwhile published the same hash. The stash holds this trajectory's first computation, and a sibling's copy can be of another version. A request that finishes while parked (the output in flight at the preemption ended it) is finished from the stash, including tails that span several blocks.

**Abort.** A request that ends and is preempted in the same step is finished, not stashed. An abort while parked drops the stash.

### 6.6 In-flight weight update

`pause_scheduler("keep", clear_cache=True)` waits until no batch is in flight, then `reset_prefix_cache(reset_running_requests=True)` preempts every running request and starts a new store namespace (generation). Requests that finished before the reset are finished in the old generation first; running requests are stashed as in 6.5. Then the version is bumped and scheduling resumes. Versions are stamped on rows at forward time.

### 6.7 Speculative decoding

- A request has 1 + num_draft logits rows per step. Hidden states are captured for every logits row of the global batch with per-request offsets (before sampler sharding), and only the accepted rows are kept.
- A full block can finish before its hash arrives, and capture can end exactly on a block boundary: the tail is then assembled from those hash-less blocks plus the buffer's partial block, if any.
- The last step can accept drafts past `max_tokens`; the scheduler truncates those tokens, but their rows were captured. They are delivered in the tail (readers truncate to `L−1`) and never spliced into the next request, whose prompt has different tokens there.

### 6.8 KV-load failures

Block-level KV-load failure recovery rewinds a request's computed tokens. vLLM refuses block-level recovery for models with several KV cache groups (DeepSeek-V4.1-Flash has 9), and request-level failures recompute before any capture, so the rewind cannot occur there. For single-group models, a rewind marks `invalid_from` in the manifest: rows computed on invalid KV are reported, never delivered as valid.

### 6.9 Writes and write failures

- A background thread writes; it never blocks the forward. One TP rank writes (the others compute identical rows and skip); "key already exists" counts as success.
- **Host work off the critical path.** The writing rank also captures and assembles every request's rows each step. Done inline, under the lock the engine's output path holds, that work stalled the rank's GPU while the other ranks waited for it in collectives, and it, not the bytes, was most of the cost of the indexer and hidden states (experiments: engine overhead). Capture therefore runs on its own thread, fed by one ordered queue from inside the lock: the queue preserves the order in which the output path handled requests, so first computation wins exactly as if the work ran inline. The queue is bounded, and an error on the capture thread is raised at the engine's next step instead of being lost.
- **Encoding off the writer thread:** indexer compression (zstd, which releases the GIL) runs on a small thread pool ahead of the writer. The writer takes the results in order. Manifests stay on the writer thread, because they read the sizes of the objects put before them. At 512K context, a single writer thread spent 46% of its time in zstd and the engine paused about 3% of the time on writer backlog. The pool removes most of that wait.
- **Full memory:** objects must never be lost (§9). A put that does not fit is retried until it lands: with SSD-first, the store makes room by offloading to disk; with pinned memory, only releases make room. Each worker caps pending bytes, and beyond the cap the engine schedules no new tokens until writes catch up. Writers report a stall when no put has landed for a deadline, and the driver aborts (§8).
- **A failed write fails the request.** A block, tail, chunk or manifest write that fails after its retries makes the writer write the request's error marker (retrying ~1 s) instead of its manifest, and every later request of the session that would list a failed block gets an error marker too. A reader that finds the marker fails that request at once; siblings that do not list the failed object are unaffected. The marker is the fast path, not the guarantee: a manifest can be written before a shared object's failure is known (another trajectory or writer published the name first). The guarantee is the reader's: a request whose manifest lists an object that does not exist fails. When the manifest exists, that check decides and a marker beside it is stale (another writer stored the object after all); the marker only fails a request whose manifest is absent, without waiting for a timeout. Nothing is substituted: a recomputation can be of another version. Finer reporting (delivering the rest of the request and naming the missing rows) is left for later; the request fails as a whole.
- Tail and manifest are written as soon as the request finishes, not at a later engine step (an idle engine never runs one).

### 6.10 Abort and undeliverable responses

A normal abort writes a manifest for the computed positions. Request-private objects of responses that cannot be delivered are deleted by the engine; session-shared blocks are left to session release.

### 6.11 Full-depth capture on models with sliding-window layers

**Bounded replay.** On DeepSeek-V4.1 only layers up to 20 keep KV for every row; the rest of layer 20 and layers 21–39 attend through a 128-row sliding window. By default vLLM does not cache that window per row. On a prefix hit, and for every new prompt row, it runs those layers in eager prefill steps on each request's trailing rows only, in stages that shrink by 127 rows per layer. Cells of those layers on other rows are never computed exactly. Asking for exact KV-following rows at every position under bounded replay forces every new row through the stages, which cost about 41% of throughput in the top scenario of the experiments (512K context, 51 sessions in flight per replica; experiments: engine overhead).

**Full depth.** Aux capture runs with bounded replay off: `CacheConfig.swa_bounded_replay=False` (`--swa-bounded-replay=False`). Every new row runs all 40 layers. The sliding-window KV is prefix-cached only as snapshots of the last 128 rows of every window layer:

- at prompt end, as vLLM does by default (`prefix_cache_retention_interval=0`);
- at decode end, with the decode-end snapshot patch (`VLLM_SWA_DECODE_SNAPSHOT=1`), so the next turn of a trajectory also hits the previous turn's generated tokens.

One snapshot is 128 rows × 40 layers, about 2.7 MB, against about 692 MB for a 32K sequence if the window KV of every row were kept.

**Prefix hits.** A hit is clamped to the longest snapshot at or below the full-attention hit; rows after it run all layers. This clamp comes on top of the session clamp of §6.2 and only shortens hits. Rows recomputed between the snapshot and the previous request's end are second computations of positions the trajectory already holds; §5 and §6.3 keep the first.

**What changes for delivery.** Nothing. Every captured cell is exact, so R3 and indexer rows of every layer live in blocks and tails like those of any MoE model, under §4–§6.10, and the reader has no layer-specific logic.

**Requirements.**

- **Append-only history.** Multi-turn reuse needs each prompt to extend the previous one token for token. A chat template that drops earlier turns' reasoning changes the prefix, and every turn re-prefills from the first changed token at full depth (Known limits).
- **No speculative decoding with the decode-end snapshot.** The first version of the snapshot patch refuses speculative decoding. With speculative decoding, only prompt-end snapshots apply.

**Cost.** At 14.6K context, 512 sessions × 16 turns on one node, full depth took 58–62% less time than bounded replay in every arm, R3 off included, with 0 missing and 0 wrong rows; decode-end snapshots took another 10.5% off (experiments: full depth). The 512K top scenario has not been run at full depth.

## 7. Training side

```python
rows = aux.read(manifest_ref, kind="routed_experts", layers=range(l0, l1), tokens=sample_tokens)
...
aux.release_session(job, session)  # after the session is consumed and the step committed
```

- **read** reads the manifest, then the blocks, chunks and tail, and returns rows for `[0, L−1)`:
  - truncate to `L−1`: the manifest can cover more rows (async scheduling computes one more position; speculative decoding can capture truncated drafts);
  - check that every object the manifest lists exists, in one batched existence check: if one is absent, or decodes to a malformed object, the request has failed and so does the sample; without a manifest, an error marker fails the request at once;
  - verify each block's tokens against the sample;
  - R3 sanity: the 6 expert ids in a row are distinct; an all-zero row is an error;
  - replay compares expert sets; rows whose set is unchanged keep the trainer's own ids and weights;
  - a failed read fails the step collectively: all ranks all-reduce a success flag and retry or skip together;
  - decode on the GPU: copy the encoded indexer bytes and decode them where replay runs, in engine order (§1, indexer rows). A single CPU thread decoding numpy is the bottleneck of the whole path: about 180 MB/s, against more than 10 GB/s for the store's get. Decoded, one 512K request's indexer is about 8 GiB of int32, so decode it in position ranges, or on the CPU, when the GPU has no room for it.
- **release** deletes everything under `<job>/<session>/` once the session will not grow, all reads are done and the step has committed: a release marker first, then force removal, a wait for the writers, and a second force removal (§8). The marker also makes writers drop the session's bookkeeping, so writer memory is bounded by live sessions.
- **Every request's manifest stays readable until release**, not only the last one of a trajectory. A training sequence can be any request's prefix: a segment of a compacted rollout, a summary segment, or one sample per turn (state, action) as some recipes train. Read each with its own manifest reference, truncated to that sequence's length.
- **Samples the trainer drops still release.** Timeouts, staleness filters, incomplete or zero-advantage groups and partial rollouts carried into a later step all end in `release_session` once the session will not be trained on, or the store keeps them until job end.
- Retrying a failed step re-reads; rolling back to an earlier checkpoint requires regeneration; saving rollouts offline requires reading them inline first.

## 8. Driver

Terms: a **holder** is a process that contributes a Mooncake segment (memory, and with SSD-first a local offload directory); the **master** places objects on holders. A **group** is the sessions admitted together; a session's **branching factor** is its number of trajectories.

1. **Admission by disk.** With SSD-first (§9) memory is a cache and the limit is disk. Admit a new group only if `free disk − segment − reserve − reserved ≥ group bytes`, where:
   - `group bytes = rows a session writes × bytes/token × sessions in the group`, with bytes/token of the configured codecs at the target context (§9). A session writes, summed over its trajectories, every row no other trajectory of the session already holds at the same version: about `longest context × branching factor` when trajectories only grow, but `segments × compaction threshold` when the context is compacted (each continuation re-prefills a summary and recent turns at new positions, so its rows are new);
   - `segment` is the holder's memory segment size: objects in memory still need a place on disk when evicted;
   - `reserve` is headroom kept free for other users of the disk and for bucket files not yet reclaimed (default 16 GiB);
   - `reserved` is the sum of `group bytes` over groups admitted and not yet released. It is conservative: bytes a group has already written count both here and in the drop of free disk.

   Re-check before each new group; when the check fails, wait for releases. The next turn of an admitted session is always admitted. Keep a separate ledger per policy (a policy or LoRA has its own sessions). Without SSD, admit only while `reserved + group bytes ≤ 0.75 × pool`, and pin (§9).
2. **Release** (`release_session`, §7) does, in order: write the session's release marker, so writers drop its queued and retried puts; force-remove its keys (`remove_by_regex(regex, force=True)`); wait until every writer has reported nothing pending for the session; force-remove again, counting keys that came back. Force is required: a read takes a lease of about one second on its keys, renewed by every get and existence check, and a removal without force inside the lease removes nothing and reports 0.
3. **Stall and liveness.** Abort the step, with its context, when a holder or the master process exits, or when writers report no successful put for a deadline (default 600 s) while puts are pending. A holder's objects, in memory and on its disk, are readable only through that holder: after it dies the master still lists its keys and every get returns empty. So a holder is never restarted within a job, even on a fresh directory: every session with objects on it is regenerated, which in practice means the step.
4. **Deadlock fallback** (no SSD): if the pool fills and no session completes for a while (default 60 s), abort the most recently admitted sessions, delete their objects and regenerate them.

## 9. Store

Every acked object stays readable until its session is released. A listed object that disappears breaks invariant 1 silently: the reader can only time out. Two configurations hold this.

**SSD-first (default).** Each holder's segment is a memory cache in front of a local NVMe directory; objects leave memory by offload, never by loss.

- **Holder setup:** `setup(dict(..., global_segment_size=..., enable_ssd_offload=True, ssd_offload_path=<dir>))`. An 8 GB segment was enough at 512 sessions × 14.6K context; size it to at least a few times the largest batch put.
- **Master flags:** `--enable_offload=true --offload_on_evict=true --offload_force_evict=false --enable_disk_eviction=false --client_ttl=600`. Objects are not pinned: a pinned object is never evicted, hence never offloaded.
- **Offload on eviction only.** With `--offload_on_evict=false` (offload at put) the store evicts objects whose disk write has not completed and loses them without any error or counter: 3% of 100K small objects, and every session of a full rollout read back incomplete, at about 20× slower turns.
- **`client_ttl` longer than any holder pause.** A holder silent for longer than the TTL is dropped with every object in memory (10 s default: a 30 s pause lost all of them; 600 s: none). A pause shorter than the TTL is tolerated; the put-stall deadline of §8 still aborts if puts stop landing meanwhile.
- **One fresh directory per holder and job, deleted at job end.** Removal is logical: bucket files are not reclaimed, and a holder started on an old directory re-registers keys that were removed. Space is reused across removals, so disk use follows the peak live bytes, not the total written.
- **A failing disk stalls; it does not lose acked data.** A failed bucket write is logged (`FILE_WRITE_FAIL`) and leaves its partial file; memory stays full and every later put fails, which the put-stall deadline of §8 turns into an abort. `--quota_bytes` does not bound the offload directory, so the driver's admission (§8) and a free-disk check outside the store are the only guards; the partial files go with the directory at job end.
- **Every holder eligible for placement is SSD-backed**; an object placed on a memory-only holder can be evicted and lost.
- **Cost:** at 14.6K context × 512 sessions with all outputs, an 8 GB segment spilling 36 GB ran rollouts about 1–2% slower than a 96 GB pinned pool (eight same-node pairs, median +1.3%, range −1.8% to +7.6%) and read back about 2% slower, with nothing missing (experiments: aux objects on SSD).

**Pinned memory (no SSD).** Objects are written hard-pinned, or soft-pinned with eviction of soft-pinned objects disabled on the master. They leave the store only through session release or the abort fallback. Without pinning, an overfull pool evicted 1.81M keys and the readers hung. The pool must hold every admitted session (§8).

**Both:**

- **Segment lifetime.** Mooncake keeps one replica per object by default, so an object lives on whichever holder it was placed on, in memory or on that holder's disk. A holder must stay up until every consumer of every object placed on it has read and released. Taking down one replica's segment when that replica finished removed other replicas' objects.
- **Sizing with real bytes per token.** At 512K context the indexer is 10 KB per token packed and about 5.6 KB after zstd (ratio ~1.8, against 4.6–6.7 at short context). R3 adds 480 B per token, and hidden states 16 KB per generated token as exact float32. Admission (§8) must use the numbers of the configured codecs at the target context; measure them on a short run at that context, since numbers from short contexts over-admit by about 2×.
- **At job end,** force-remove everything under `<job>/`, report the number of keys removed as a leak metric (expected 0), then delete each holder's offload directory.

## 10. Checklist

Inference framework:
1. Send `aux_outputs`, `aux_session`, `aux_trajectory`, and `aux_parent` on a fork's first request. After a context compaction, continue under a new `aux_trajectory` in the same session (the summarizing request itself is the next turn of the segment it summarizes).
2. Store `prompt_token_ids`, the manifest reference, the generated tokens and the inline sampled logprobs.
3. Treat a missing `aux` as an error.

Training framework:
1. Carry the manifest reference through shuffling, packing and rank sharding.
2. Admit by disk (or by `0.75 × pool` without SSD); release with `release_session` after the step commits.
3. Read per rank, truncate to `L−1`, fail collectively.
4. Hook R3 replay where the model computes routing (some MoE implementations call `route` directly, bypassing a router-level hook).
5. Run the train-inference consistent build; otherwise invariant 3 does not hold and siblings must not share rows.

## 11. Scenarios

| Scenario | What happens |
|---|---|
| Single-turn GRPO | n trajectories, one session; prompt blocks stored once per version |
| Multi-turn agent | one trajectory; each turn writes only new blocks; the last manifest covers the sequence, every earlier manifest its own prefix |
| One sample per turn (state, action) | each request's manifest is read for its own turn; blocks of the shared prefix are stored once |
| Sub-agents trained as their own sequences | each sub-agent is a trajectory of the rollout's session; its rows never mix with the caller's |
| Prefix tree of continuation and summary branches | each branch is a trajectory with a parent at the compaction point; leaves are read with their own manifests |
| Partial rollouts across training steps | the session stays admitted until its last trajectory is consumed; every row carries its version |
| Forks / tree search | each branch is a trajectory with a parent; parent blocks shared |
| Weights updated between turns | each turn's rows labelled with their version; a block recomputed at another version by another trajectory gets its own copy |
| In-flight weight update | pause, reset, stash running requests, bump the version, resume |
| Preemption | stash and resume; no rows lost or replaced |
| Speculative decoding | accepted rows only; hash-lagging blocks delivered in the tail |
| Full memory | SSD-first: objects offload to disk; pinned: writer blocks and the engine pauses scheduling; nothing dropped |
| Holder or disk failure | holder death: keys listed but unreadable, step aborts; disk write failure: puts stall, deadline aborts |
| Write failure | the request fails with an error marker; never substituted |
| Cross-session prefix hit | truncated |
| Context rewriting | rewritten prefixes hash differently and are rewritten |
| Context compaction (summarize, continue from system prompt + summary + recent turns) | the summary request extends its segment's trajectory; each continuation is a new trajectory of the session, sharing only blocks that hash the same (the system prompt) at the same version; the session lives and holds its objects until the whole rollout is trained, and is admitted by the rows of all its segments |
| Multiple policies / LoRAs | a session per policy; separate in-flight caps |
| Job end | delete by job prefix, report the count |

## 12. Inline mode

At small scale (one node, short multi-turn agents) rows are returned in the response and nothing goes to a store. Delivery needs no session or trajectory.

- **Range.** The request sets `aux_start` to the end of the rows the framework already holds, and the response returns `[aux_start, rows)`. The framework keeps earlier turns' rows and concatenates them, so a next turn's re-prefill of the previous turn's unfinished block is not returned again.
- **Prefix hits.** Rows for hit positions inside that range come from the engine-local block-row cache (c1), allocated and evicted with the KV and scoped to the engine's generation (§6.6). For R3 it costs about 1% of the KV on DeepSeek-V4.1-Flash; for the indexer about 54 GB raw per engine (scenarios §10).
- **Cache loss.** The cache is per-replica engine state, lost on a restart. When a hit's block is no longer cached, the position is recomputed, and the row returned is the computation this request actually used.
- **Top-k logprobs** are returned inline today in either mode (§1).
- **Limits.** The cache reads hit rows from a generation-scoped base store. Its version records describe spliced rows rather than the base payload, and a request parked across a generation change reads the new generation. Store mode does not use this path.

Design c1 in experiment X1 delivered every row of all 112 requests, equal to the inline rows (experiments: designs compared).

## 13. Known limits

- **Per-trajectory state lives in the engine worker.** The previous tail, the version record and the names a trajectory holds are kept in the writing worker's memory, so a trajectory's next turn must return to the same replica, and a replica restart loses its trajectories. A follow-up can move that state into the store: each request carries the previous request's manifest reference (the manifest already holds the tail, versions and blocks), and the engine reads it when the request starts. A next turn could then go to any replica and survive restarts, for one manifest read per request (about a millisecond), with deduplication shared by replicas writing one session (or occasional extra copies accepted). Inferring the trajectory from token prefixes, or a global lifetime keyed by block hash and version, were considered and are not worth their cost.
- **Release is per session.** A long agentic session (hundreds of trajectories, up to about a day) keeps every object until it is released, including the copies of blocks recomputed at a new version after each weight update resets the GPU prefix cache. GRPO groups are trained within one step, so session release fits them; long sessions are the costly case. Two follow-ups are possible: release a trajectory's private objects (its tails, manifests and `hash~<tag>` copies) when that trajectory is consumed, by ownership alone; or release single blocks by reference counts kept per session, which needs the writer to know who lists each name, the trainer to report each request it consumed, and the engine to stop hitting deleted blocks.
- **Teacher scoring at prompt positions.** On-policy distillation runs a teacher over the student's sequence as a prompt and needs the teacher's top-k logprobs (or hidden states) at those prompt positions. Top-k and hidden states are captured at generated positions only; prompt positions need a capture over `[aux_start, P)` stored like blocks.
- **Contexts that are not append-only** (history reasoning dropped, rewritten or truncated context) re-prefill from the rewrite point every turn: rows are correct, but prefix reuse and the decode-end snapshot (§6.11) do not apply, and the full-depth recompute grows with every rewritten turn.
- **A prefix hit does not say which computation produced the KV it hits.** The session's first copy of a block is listed for every hit on that hash. This is wrong only if all three of the following happen: the KV of the first computation is evicted from every cache tier; another trajectory recomputes the block at a different weight version (it keeps its own copy, and its KV is now the cached one); and a third trajectory hits that KV. Two fixes are possible. One is to follow vLLM's KV cache events (stored / removed, per block hash) so the worker knows which object the cached KV belongs to. The other is to carry R3 in the KV cache itself (#64383), which makes rows follow the KV by construction. The indexer would still need the first.
