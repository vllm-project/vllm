# Aux Outputs for RL: Delivery Protocol

Status: draft (v4). Measurements behind each rule are in [experiments](experiments.md); sizes in [scenarios](scenarios.md); alternatives in [design space](design_space.md).

## 1. What a row is

**Outputs.**

| Output | Follows | Positions | Bytes/token (DeepSeek-V4.1-Flash) | Use |
|---|---|---|---|---|
| `routed_experts` (R3) | KV | all | 40 layers × 6 × uint16 = 480 B | routing replay in the trainer |
| `indexer_topk` | KV | all | 8 layers × 512 × 20 bit, zstd: ~2.5–3.6 KB (16 KB raw) | sparse-attention replay |
| `topk_logprobs` | sampling | generated | k × 8 B | truncated distillation, KL |
| `sampling_mask` | sampling | generated | CSR, ≤ 256 ids per row | reconstruct the truncated/masked support |
| `hidden_states` | sampling | generated | `lm_head` input, fp8 + per-token scale, ~5 KB | full-vocabulary student training |

The sampled token's logprob is returned inline with the response; that number is the behavior probability. Logits recomputed from hidden states are not bitwise equal to vLLM's (max diff 2e-4 even in fp32), so trainers must not try to reproduce the behavior logprob from them.

**Position convention.** Row `p` belongs to position `p`: the position that processes token `p` and produces the logits for token `p+1`. KV-following outputs have a row at every position. Sampling-following outputs have a row only where `p+1` is a token generated by this request, i.e. `p ∈ [P−1, P+O−1)` for prompt length `P` and output length `O`. Positions count the engine-side sequence (after multimodal expansion).

**Units.**

- *Request*: one engine request (one turn).
- *Trajectory*: the sequence of requests whose prompts extend each other (the turns of one agent rollout, one GRPO sample, one fork branch).
- *Session*: the consumption unit, released together: a GRPO group, a trajectory tree, one agent rollout. A session contains one or more trajectories.
- *Weight version*: incremented by every weight update the engine applies.

**The right row.** For every position of a trajectory, the delivered row is the one from the first computation of that position in the trajectory, i.e. the computation whose KV or logits the trajectory went on to use. Later computations of the same position (next-turn re-prefill of an unfinished block, recomputation after preemption, a prefill overlapping a speculative verification) never replace it. For a fork, positions before the fork point belong to the parent trajectory.

## 2. Invariants

1. **Requested means delivered, or reported missing.** Every requested row can be read, or the manifest names the rows that are missing. A row is never replaced by a different computation.
2. **First computation wins**, per trajectory, as defined above.
3. **Same version, same tokens, same row.** Under the train-inference consistent build (#62365: batch invariance with bitwise identical results across batch composition, chunk size and prefix-cache hit vs miss), all computations of the same tokens at the same weight version are identical. Rows of one version may therefore be shared between trajectories of a session. Rows of different versions are never interchangeable.
4. **Rows carry their version.** The manifest lists `weight_versions` segments covering `[0, rows)`; each segment's version is the version of the computation whose rows are stored there.
5. **Freed once used.** All objects of a session are deleted when the session is consumed and the training step has committed.
6. **Every reference points at objects that exist.** The manifest is written after the objects it lists; the response is sent after the manifest.

## 3. Request and response

**Request fields.**

| Field | Meaning |
|---|---|
| `aux_outputs` | Which outputs to produce. Absent means none. |
| `aux_session` | The session. All objects share the key prefix `<job>/<session>/` and are released together. |
| `aux_trajectory` | The trajectory within the session (needed when a session holds several: GRPO samples, forks). Tails and version segments are tracked per trajectory. |
| `aux_parent` | For the first request of a fork: the parent trajectory (`""` for the session's root). The fork takes over the parent's state at the fork point. Ignored without `aux_trajectory`. |
| `aux_start` | "I already have the first `aux_start` rows." Needed for sampling-following outputs and inline mode. |

Sampling-parameter constraints (when requesting `topk_logprobs`, `sampling_mask` or `hidden_states`): temperature, `top_k`, `top_p`, `min_p` and token masking are allowed; with any truncation or masking `top_k ≤ 256`; parameters that change logit values (penalties, `logit_bias`) are rejected because the trainer cannot reconstruct them.

**Response.**

```json
"prompt_token_ids": [...],
"aux": {
  "status": "ok",
  "manifest": {"backend": "mooncake", "key": "<job>/<session>/<req>/m", "nbytes": 2380}
}
```

- `status` is always present when `aux_outputs` was requested; `unavailable` only if the store is unreachable. A response without `aux` to a request that asked for it is an error.
- `<req>` is the caller-visible request id (engine-internal ids carry a random suffix).
- **Inline mode** (small scale): data in the response, nothing in a store.

**Manifest** (one per request, covering the whole sequence `[0, rows)`):

| Field | Meaning |
|---|---|
| `blocks` | ordered object names of the full blocks; usually the block hash, `hash~<tag>` for a trajectory's own copy (§5), `hash~r` never appears (a lost block is reported missing) |
| `tail_start`, `tail_nbytes` | the tail object covering `[tail_start, rows)`; it can span several blocks |
| `rows` | rows covered; can exceed `L−1` (see §7) |
| `weight_versions` | `[[start, version], ...]` covering `[0, rows)`, describing the stored objects |
| `fields` | per output: name, dtype, per-token shape, codec, layout, `missing` and `holes` counts, chunk layout for sampling-following outputs |
| `invalid_from` | first position computed on invalid KV, if the engine ever rewound this request (§6.8); rows from here are not valid |

## 4. Objects

- **Block** `<job>/<session>/<name>`: KV-following rows of one full KV block (R3; the indexer under `<name>/idx`). Written when the block fills and its hash is known.
- **Tail** `<job>/<session>/<req>/t` (indexer: `/t/idx`): rows from `tail_start` to `rows`, written at request end.
- **Generated chunk** `<job>/<session>/<req>/h/<i>`: sampling-following outputs (hidden states: 64 generated positions per chunk).
- **Manifest** `<job>/<session>/<req>/m`.
- **Error marker** `<manifest key>!err`: written when the manifest, the tail or a generated chunk of that request could not be written.

Objects are immutable. Block hashes are vLLM's prefix block hashes (including multimodal, LoRA and `cache_salt` keys), so a name's content depends only on its full prefix.

## 5. Deduplication and copies

Within a session a block is stored once per distinct computation that a trajectory must see:

- A trajectory that already holds a block (its own copy, or a shared one it used) drops any later recompute of it. First computation wins.
- Another trajectory computing the same block **at the same weight version** shares the stored copy (invariant 3).
- Another trajectory computing it **at a different version** stores its own copy as `hash~<tag>` and lists that name. Versions are compared as the set of versions in the block's segments, not the segment boundaries (a block whose first rows came from a prefix hit has a segment starting mid-block).
- A block that starts before the request's `aux_start` and whose hash the session already published is always shared: those tokens were computed first by an earlier request (the previous turn, or the parent of a fork).
- The writer keeps per (session, trajectory) which name it holds for each hash, plus a digest, owner and version record per stored object. All of it is dropped when the session is released.

## 6. Engine behavior, event by event

### 6.1 Prefill and decode

Rows are captured from the forward, per request, at the captured positions (not the scheduler's token start, which async scheduling runs ahead). Full blocks are written as soon as their hash is known; blocks that fill before their hash arrives wait in the request's state.

### 6.2 Prefix-cache hits

Allowed only up to the longest prefix the session already published (the delivery pool is the session's cache). Rows for hit positions are therefore always in the pool. Cross-session hits are truncated.

A hit can end mid-block. The rows of that block before the hit point were computed by whoever filled the block; this request never captured them. The request does not publish that block (it would publish pad rows as valid); the request that computed the whole block publishes it.

### 6.3 The next turn of a trajectory

vLLM does not cache unfinished blocks, so the next turn re-prefills `[start of the last unfinished block, aux_start)`. Those positions keep the previous request's rows: the worker remembers each trajectory's last tail (start and rows, possibly several blocks) and splices it into any block or tail written later at the same positions. With speculative decoding the previous request's last step can already have computed position `aux_start` itself (its input is the last sampled token); that row came first too and is spliced, and the new version segment starts one position later.

### 6.4 Forks

The fork's first request names its parent. At its first capture the fork takes the parent's tail that covers the fork point and the parent's version segments, restricted to blocks before the fork point (blocks the parent computed later are not the fork's). Blocks before the fork point that the parent published are shared (§5).

### 6.5 Preemption

A preemption is not a finish. The scheduler reports it separately; the worker stashes what only this computation has: rows of blocks not yet published, the tail, indexer blocks, the hidden-state cursor, and a freeze point equal to the capture cursor. On resume the stash is restored and positions below the freeze point keep the stashed rows. If the output in flight at the preemption finishes the request while it is parked, the request is finished from the stash. An abort while parked drops the stash.

### 6.6 In-flight weight update

`pause_scheduler("keep", clear_cache=True)` waits until no batch is in flight, then `reset_prefix_cache(reset_running_requests=True)` preempts every running request and starts a new store namespace (generation). Requests that finished before the reset are finished in the old generation first; running requests are stashed as in 6.5. Then the version is bumped and scheduling resumes. Versions are stamped on rows at forward time.

### 6.7 Speculative decoding

- A request has 1 + num_draft logits rows per step. Hidden states are captured for every logits row of the global batch with per-request offsets (before sampler sharding), and only the accepted rows are kept.
- A full block can finish before its hash arrives, and capture can end exactly on a block boundary: the tail is then assembled from those hash-less blocks plus the buffer's partial block, if any.
- The last step can accept drafts past `max_tokens`; the scheduler truncates those tokens, but their rows were captured. They are delivered in the tail (readers truncate to `L−1`) and never spliced into the next request, whose prompt has different tokens there.

### 6.8 KV-load failures

Block-level KV-load failure recovery rewinds a request's computed tokens. vLLM refuses block-level recovery for models with several KV cache groups (DeepSeek-V4.1-Flash has 9), and request-level failures recompute before any capture, so the rewind cannot occur there. For single-group models, a rewind marks `invalid_from` in the manifest: rows computed on invalid KV are reported, never delivered as valid.

### 6.9 Writes and write failures

- A background thread writes; it never blocks the forward. All TP ranks compute identical rows; "key already exists" counts as success.
- **Full pool:** retry until the write lands. Each worker caps pending bytes; beyond the cap the engine schedules no new tokens until writes catch up.
- **A failed block write:** the block is lost for good. Its hash is poisoned: later recomputations are not substituted (they can be of another version, and the version record of those positions describes the lost computation). The block stays missing and every manifest that lists it reports it.
- **A failed manifest, tail or chunk write:** the writer writes the request's error marker (retrying ~1 s). A reader that finds the marker fails that request at once instead of waiting; siblings are unaffected.
- Tail and manifest are written as soon as the request finishes, not at a later engine step (an idle engine never runs one).

### 6.10 Abort and undeliverable responses

A normal abort writes a manifest for the computed positions. Request-private objects of responses that cannot be delivered are deleted by the engine; session-shared blocks are left to session release.

## 7. Training side

```python
rows = aux.read(manifest_ref, kind="routed_experts", layers=range(l0, l1), tokens=sample_tokens)
...
aux.release_session(job, session)  # after the session is consumed and the step committed
```

- **read** reads the manifest, then the blocks, chunks and tail, and returns rows for `[0, L−1)`:
  - truncate to `L−1`: the manifest can cover more rows (async scheduling computes one more position; speculative decoding can capture truncated drafts);
  - check the error marker; a missing block or a `missing`/`holes` count fails the sample;
  - verify each block's tokens against the sample;
  - R3 sanity: the 6 expert ids in a row are distinct; an all-zero row is an error;
  - replay compares expert sets; rows whose set is unchanged keep the trainer's own ids and weights;
  - a failed read fails the step collectively: all ranks all-reduce a success flag and retry or skip together.
- **release** deletes everything under `<job>/<session>/` (Mooncake `remove_by_regex`), once the session will not grow, all reads are done and the step has committed. It also tells the writer to drop the session's bookkeeping (a release marker), so writer memory is bounded by live sessions.
- Retrying a failed step re-reads; rolling back to an earlier checkpoint requires regeneration; saving rollouts offline requires reading them inline first.

## 8. Driver

1. **In-flight cap:** admit at most `C` sessions with `C × max_session_bytes ≤ 0.75 × pool`, where `max_session_bytes = longest context × bytes/token × branching factor`. The next turn of an admitted session is always admitted. Count bytes, not requests; cap each policy separately.
2. **Release** as in §7.
3. **Deadlock fallback:** if the pool fills and no session completes for a while (default 60 s), abort the most recently admitted sessions, delete their objects and regenerate them.

## 9. Store

- Objects are written with soft pin + TTL, the master configured with `allow_evict_soft_pinned_objects=false`.
- TTL ≥ longest session lifetime + queueing + margin; the master's eviction high watermark ≤ in-flight cap − one session's maximum bytes.
- At job end, delete everything under `<job>/` and report the number of keys as a leak metric (expected 0).

## 10. Checklist

Inference framework:
1. Send `aux_outputs`, `aux_session`, `aux_trajectory`, and `aux_parent` on a fork's first request.
2. Store `prompt_token_ids`, the manifest reference, the generated tokens and the inline sampled logprobs.
3. Treat a missing `aux` as an error.

Training framework:
1. Carry the manifest reference through shuffling, packing and rank sharding.
2. Keep the in-flight cap; release after the step commits.
3. Read per rank, truncate to `L−1`, fail collectively.
4. Hook R3 replay where the model computes routing (some MoE implementations call `route` directly, bypassing a router-level hook).
5. Run the train-inference consistent build; otherwise invariant 3 does not hold and siblings must not share rows.

## 11. Scenarios

| Scenario | What happens |
|---|---|
| Single-turn GRPO | n trajectories, one session; prompt blocks stored once per version |
| Multi-turn agent | one trajectory; each turn writes only new blocks; the last manifest covers the sequence |
| Forks / tree search | each branch is a trajectory with a parent; parent blocks shared |
| Weights updated between turns | each turn's rows labelled with their version; a block recomputed at another version by another trajectory gets its own copy |
| In-flight weight update | pause, reset, stash running requests, bump the version, resume |
| Preemption | stash and resume; no rows lost or replaced |
| Speculative decoding | accepted rows only; hash-lagging blocks delivered in the tail |
| Full pool | writer blocks, engine pauses scheduling; nothing dropped |
| Write failure | reported as missing or as an error marker; never substituted |
| Cross-session prefix hit | truncated |
| Context rewriting / compaction | rewritten prefixes hash differently and are rewritten |
| Multiple policies / LoRAs | a session per policy; separate in-flight caps |
| Job end | delete by job prefix, report the count |
