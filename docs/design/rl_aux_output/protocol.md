# Aux Outputs for RL: Delivery Protocol

Status: draft (v3.9). Measurements behind each rule are in [experiments](experiments.md); sizes in [scenarios](scenarios.md); alternatives in [design space](design_space.md).

RL trainers need per-token data that only the inference engine computes: the experts each MoE layer routed to (R3, for routing replay), sparse-attention indexer selections, top-k logprobs, the sampling support set, and the last hidden state before `lm_head` (for full-vocabulary distillation). This document specifies how vLLM delivers these "aux outputs" to the trainer at scale: who writes what, where, when, and who frees it.

## Principles

1. **Requested means delivered.** If a request asks for an aux output, the trainer can read it. A full store makes the engine wait; it never drops rows or gives up on a write.
2. **Freed once used.** Objects are stored per session (consumption unit). The driver deletes a whole session once it is consumed and the training step has committed. No distributed reference counting. The store only reclaims expired objects as a backstop.
3. **Written per block; the reference comes last.** Each full KV block's rows are written as soon as the block completes. At request end, the tail and a small manifest are written, and only then is the final response (carrying the manifest reference) sent. Every reference the client sees points at objects that already exist.
4. **The first computation wins.** A position's rows come from the first forward that computed it; for generated tokens, that is the forward whose logits sampled the next token. vLLM does not cache unfinished blocks, so the next turn re-prefills `[start of the unfinished block, aux_start)`. That prefill can route a few rows differently even with batch invariance on. Rows the session already delivered are kept; the recomputation never overwrites them.

## Outputs

| Output | Follows | Positions | Bytes/token (DeepSeek-V4.1-Flash) | Use |
|---|---|---|---|---|
| `routed_experts` (R3) | KV | all | 40 layers × 6 × uint16 = 480 B | routing replay in the trainer |
| `indexer_topk` | KV | all | 8 layers × 512 × 20 bit, zstd: ~2.5–3.6 KB (16 KB raw) | sparse-attention replay |
| `topk_logprobs` | sampling | generated | k × 8 B | truncated distillation, KL |
| `sampling_mask` | sampling | generated | CSR, ≤ 256 ids per row | reconstruct the truncated/masked support |
| `hidden_states` | sampling | generated | `lm_head` input, fp8 + per-token scale, ~5 KB | full-vocabulary student training |

- The sampled token's logprob is not stored; it is returned inline with the response (per-token logprobs in `processed_logprobs` mode). That number is the behavior probability.
- fp8 hidden states multiplied by the teacher's `lm_head` give a full-vocabulary distribution within KL < 1e-3 of vLLM's (argmax agreement 98–100%). Recomputing logits from hidden states is not bitwise equal to vLLM's logits (max diff 2e-4 even in fp32), so trainers must not expect to reproduce the behavior logprob from hidden states.

**Position convention.** Row `p` belongs to position `p`: the position that processes token `p` and produces the logits for token `p+1`. KV-following outputs have a row at every position. Sampling-following outputs have a row only where `p+1` is a token generated by this request, i.e. `p ∈ [P−1, P+O−1)` for prompt length `P` and output length `O`. Positions are counted on the engine-side sequence (after multimodal expansion); responses always return the engine-side `prompt_token_ids`.

## Inference side

### Request

| Field | Meaning |
|---|---|
| `aux_outputs` | Which outputs to produce. Absent means none. |
| `aux_session` | The session (consumption unit) the request belongs to: a GRPO group, a trajectory tree, a multi-turn agent trajectory. All its objects share one key prefix and are released together. |
| `aux_start` | "I already have the first `aux_start` rows of this sequence." Needed only for sampling-following outputs and inline mode; KV-following outputs are deduplicated per block within the session. |

Sampling-parameter constraints (when requesting `topk_logprobs`, `sampling_mask` or `hidden_states`): temperature, `top_k`, `top_p`, `min_p` and token-masking parameters (guided decoding, `allowed_token_ids`, `bad_words`) are allowed; with any truncation or masking, `top_k ≤ 256` is required; parameters that change logit values (repetition/frequency/presence penalties, `logit_bias`) are rejected because the trainer cannot reconstruct them.

### Response

```json
"prompt_token_ids": [...],
"aux": {
  "status": "ok",
  "manifest": {"backend": "mooncake", "key": "<job>/<session>/<req>/m", "nbytes": 2380}
}
```

- `status` is always present when `aux_outputs` was requested. It is `unavailable` only if the store itself is unreachable; a full store makes the engine wait instead. A response without `aux` to a request that asked for it is an error, not "no data" (e.g. a router dropped the field).
- `<req>` is the caller-visible request id. Engine-internal ids carry a random suffix and must not be used in keys.
- The **manifest** is a small self-describing object covering the whole sequence `[0, P+O−1)`, not just this request's new rows: the ordered block keys (shared within the session), the generated-chunk keys, the tail key, each field's name, dtype, per-token shape and codec, the total row count, and the tokens of each block (for verification). A training sample reads exactly one manifest, that of its leaf request.
- **Inline mode** (small scale): the data is returned in the response, nothing is written to a store, and release is a no-op.

### Objects

- **Block** `<job>/<session>/<block_hash>`: all KV-following outputs for one full KV block, plus the block's tokens. Written when the block fills. Deduplicated within the session by block hash.
- **Generated chunk** `<job>/<session>/<req>/g/<i>`: sampling-following outputs, one object per `block_size` generated positions.
- **Tail** `<job>/<session>/<req>/t`: rows of the last, unfinished block, written at request end.
- **Manifest** `<job>/<session>/<req>/m`: written at request end, after the tail and before the response.
- Objects are immutable. Block hashes are vLLM's prefix block hashes (including multimodal, LoRA and `cache_salt` extra keys), so a key's content depends only on its full prefix.

### Next request

Multi-turn continuations, forks and GRPO siblings use the same `aux_session`; blocks already written are reused, not rewritten. A turn that switches policy or adapter uses a new session (same tokens, different routing; the block hash also includes the adapter name).

## Training side

```python
rows = aux.read(manifest_ref, kind="routed_experts", layers=range(l0, l1), tokens=sample_tokens)
...
aux.release_session(job, session)  # after the session is consumed and the step committed
```

`aux` is a small standalone package (no vLLM or torch dependency) returning numpy arrays.

- **read**
  - Reads the manifest, then the blocks, generated chunks and tail; returns rows covering `[0, L−1)`.
  - The manifest may report one row more than `L−1`: async scheduling runs one forward for the last sampled token before the request is known to be finished. `read` always truncates to `L−1`.
  - Verifies each block's tokens against the sample; a mismatch is an error.
  - R3 sanity: the 6 expert ids in a row are distinct; an all-zero row (the engine never saw the routing) is an error.
  - Expert order within a row is not sorted. Replay compares sets; rows whose set is unchanged keep the trainer's own ids and weights.
  - No waiting: a manifest implies all its objects exist. A failed read (store node down) fails the whole step; all ranks read, all-reduce a success flag, and retry or skip together.
- **release**: deletes everything under `<job>/<session>/` (Mooncake `remove_by_regex` with force). Immediate and idempotent. The driver calls it once the session will not grow, all planned reads are done, and the step that used it has committed on all ranks. Dropped samples are not released individually; their blocks may be shared.
- Retrying a failed step re-reads (nothing was released). Rolling back to an earlier checkpoint requires regeneration. Saving rollout data offline requires reading it inline first.

## Driver

1. **In-flight cap** (keeps "requested means delivered" from deadlocking): admit at most `C` concurrent sessions with `C × max_session_bytes ≤ 0.75 × pool`, where `max_session_bytes = longest context × bytes/token × branching factor`. New sessions wait for a slot; the next turn of an admitted session is always admitted (blocking it could deadlock). Count bytes, not requests. With several policies sharing a pool, cap each policy separately.
2. **Release timing**: as above, after the step commits.

**Deadlock fallback**: the cap is computed for the worst case, so the pool should never fill. If it does and no session completes for a while (default 60 s), the driver aborts the most recently admitted sessions, deletes their objects and regenerates those samples. The engine never drops rows on its own.

## Engine and store guarantees

**Where rows come from**

- KV-following rows live and die with the KV. On a prefix-cache hit, a block's rows come from an engine-local block-row cache allocated and evicted together with the KV (sized to the KV token capacity; R3 on DeepSeek-V4.1-Flash is ~1.6 GB per TP4 engine, ~1% of the KV). Positions computed by this request take rows from this request's forward.
- A block present in the local block-row cache but not yet written for this session (another session computed that prefix first) is written into this session at request end.
- **First computation wins** (principle 4): when publishing a block, back-filling a block or writing a tail, positions before `aux_start` that this session already delivered take the rows from the session's previous tail. The worker remembers each session's last tail (start and rows) and overwrites those positions when a later write starts at the same position.
- Do not cap prefix hits at `aux_start` to regenerate rows: capping only creates more second computations. If the block-row cache does not fit, offload rows with the KV (make the row cache a KV layer) rather than capping.
- A no-cache full-prefill recomputation is not a correctness reference; it may legitimately differ from the first computation. The check is that inline rows (returned by the engine, first computation) equal the rows read back.
- Session-level dedup by block hash assumes rows for a block are bitwise identical regardless of scheduling. Verify the deployment before relying on it: the same prompt run alone, as 8 identical copies in one batch, and mixed with long prompts must give identical rows.
- Backends that cannot expose routing (fused kernels that bypass top-k) must reject R3 at startup.

**Writes**

- Each full block is written from a background thread in the worker, without blocking the forward.
- All TP ranks compute identical rows. Have one rank write; if several do, "key already exists" counts as success (otherwise retries spin forever).
- **On a full pool, retry until the write lands** (backpressure). Each worker caps its pending bytes; beyond the cap, the engine stops scheduling new tokens until writes catch up.
- **Write the tail and manifest as soon as the request finishes.** Do not defer them to a later engine step: an idle engine never runs one.
- Before responding, the engine deletes the request-private objects (tail, generated chunks, manifest) of responses that cannot be delivered. Session-shared blocks are left to session release.

**Retention**

- Objects are written with soft pin + TTL and the master configured with `allow_evict_soft_pinned_objects=false`: never evicted within the TTL, reclaimable afterwards when space is needed.
- TTL ≥ longest session lifetime + batching and queueing time + margin. The master's eviction high watermark ≤ in-flight cap − one session's maximum bytes.
- Objects are deleted only by the engine (undeliverable responses), by driver session release, or by expiry.
- At normal job end, delete everything under `<job>/` and report the number of keys deleted as a leak metric; it should be 0.

## Framework checklist

Inference side:
1. Send `aux_outputs` and `aux_session` with every request (one session per consumption unit; a new session when the policy changes).
2. Store `prompt_token_ids`, the manifest reference, the generated tokens and the inline sampled logprobs in the sample.
3. Treat a missing `aux` as an error.

Training side:
1. Carry the manifest reference through shuffling, packing and rank sharding.
2. Keep the in-flight cap; call `release_session` after the step commits.
3. Each rank reads its own fields, layers and positions, truncated to `L−1`; handle read failures collectively.
4. Hook R3 replay where the model actually computes routing. For example, some MoE implementations call `route` directly and bypass a router-level replay hook.
5. Read inline before saving rollouts offline.

## Scenarios

| Scenario | Inference side | Training side | Notes |
|---|---|---|---|
| Single-turn GRPO | n requests, one session | each sample reads its manifest; release the group | prompt blocks stored once |
| Multi-turn agent | same session every turn | read the last turn's manifest; it covers the whole sequence | each turn writes only new blocks |
| Framework trims trailing tokens | same session | read the new manifest | trimmed positions are not in it |
| Forks / tree search | same session | each leaf reads its manifest; release the tree | parent blocks shared |
| Context rewriting / compaction | same session | read the new manifest | rewritten prefixes hash differently and are rewritten |
| Multiple policies / LoRAs | new session per policy | separate in-flight caps | block hash includes the adapter |
| Abort and resume | a normal abort still writes a manifest for the computed positions | — | hard-cancelled requests' objects are deleted by the engine |
| Full pool | writer blocks, engine pauses scheduling | in-flight cap makes this rare; deadlock fallback aborts the newest sessions | no rows dropped |
| Cross-session prefix hit | — | — | rows come from the local block-row cache and are written into the session |
| Pipeline / context / tensor parallel trainer | — | each rank reads its own fields, layers and positions | — |
| Job end | — | delete by job prefix and report the count | expected 0 |
