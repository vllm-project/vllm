# Routed Experts Return (MoE Routing Replay / R3)

`--enable-return-routed-experts` makes vLLM return the routed experts (the expert IDs each MoE layer's router selected) for every token of a request. RL trainers use it for MoE routing replay (R3): the training forward pass reuses the rollout's routing.

```bash
vllm serve Qwen/Qwen3-30B-A3B --enable-return-routed-experts
# offline: LLM("Qwen/Qwen3-30B-A3B", enable_return_routed_experts=True)
```

The flag sets `AuxOutputConfig.enable_return_routed_experts` (full form: `--aux-output-config '{"enable_return_routed_experts": true, "max_bytes": N}'`). There is no per-request on/off switch.

## Requirements

Startup fails with a `ValueError` unless:

- the runner is `generate` and the model is **MoE**;
- **prefix caching is enabled** (the default). `--no-enable-prefix-caching` fails; the old v0.21 advice to disable it is wrong.

Rejected at startup: adaptive speculative verification, DCP/PCP > 1, and the `NixlConnector`, `NixlPullConnector`, `NixlPushConnector`, `MoRIIOConnector`, `MooncakeConnector` KV connectors. Regular speculative decoding works. With pipeline parallelism, each stage passes the routing of its layers and of the earlier stages to the next one with its intermediate tensors, and the last stage returns the rows of every layer.

### How it works: aux output connector

Routing is stored by the aux output connector (`vllm/distributed/aux_output_connector/`, configured via `--aux-output-config`), keyed by KV block hash and shared with prefix caching, which is why prefix caching is required. `max_bytes` is its host-memory LRU capacity (default: derived from KV cache capacity). If a prefix-cache hit needs evicted rows, the worker raises `BlockObjectStoreError`; increase `max_bytes`.

### Backend row restoration

A backend's `MoERunner` or `RoutedExpertsCaptureSource` can optionally implement
`restore_routed_experts_rows(topk_ids, ctx) -> Tensor`. During binding, the capturer
selects the first such module in `model.modules()` order and uses its callback
for every captured layer. Without a provider, the existing DP/TP recovery is used.
Existing capture sources need no changes.

The callback must restore this DP rank's token-ordered logical expert IDs for all
captured layers, using the supplied `ForwardContext` rather than the provider's
layer-specific state. It must preserve the input, device, dtype and top-k width,
and keep collective participation consistent across ranks, including empty
ranks. Operations must support graph replay. Models requiring different per-layer
restorers cannot use this hook. Repeated layer IDs do not select a different
restorer; the existing buffer-write semantics are unchanged.

## Output format

| API | Field |
| --- | --- |
| Offline (`LLM`, `AsyncLLM`) | `CompletionOutput.routed_experts`: `np.ndarray` or `None` |
| `/v1/completions`, `/v1/chat/completions` | `choices[i].routed_experts`: base64 `.npy`, **non-streaming only** |
| `/inference/v1/generate` | `routed_experts` per choice (base64 `.npy`); with `stream: true`, on the final chunk |

- **Shape:** `(num_tokens - 1 - routed_experts_prompt_start, num_moe_layers, num_experts_per_tok)`, `num_tokens` = prompt + output. The last sampled token has no row.
- **Rows:** row `i` is position `routed_experts_prompt_start + i` of `prompt_token_ids + output_token_ids`.
- **dtype:** `uint8` for at most 256 experts, else `uint16`; logical expert IDs.
- Filled only when the request finishes. `None` if the flag is off or the request aborted before any forward pass.

```python
import base64, io
import numpy as np

experts = np.load(io.BytesIO(base64.b64decode(choice["routed_experts"])))
```

## `routed_experts_prompt_start`

Per-request, default `0`: drops the first N prompt-token rows (e.g. routing already received in earlier turns). Must be `0 <= value <= prompt_len`, else HTTP 400. Pass it top-level on `/v1/*completions`, inside `sampling_params` on `/inference/v1/generate`, or as `SamplingParams(routed_experts_prompt_start=...)`.

Example: [examples/rl/routed_experts_e2e.py](../../examples/rl/routed_experts_e2e.py).

For sparse-attention selections, see [Indexer Replay](indexer_replay.md).
Indexer and routed-expert return can be enabled independently or together.

## Sessions: delivering rows through a shared object store

`routed_experts_prompt_start` keeps earlier turns out of a response, but the client must then hold every row it has received, and each sibling request or trainer worker that needs the same prefix must be handed them. A session stores the rows once in a shared object store instead: any request of the session, on any replica, and any process that can reach the store, reads them by key.

Start the server with `--aux-output-config '{"enable_return_routed_experts": true, "object_key_prefix": "<run>"}'` (and/or `"enable_return_indexer_topk": true`) and send `aux_session` inside `sampling_params` on `/inference/v1/generate`. Requests without a session keep the inline behavior.

- **Store.** The Mooncake client is configured by the file `"mooncake_config_path"` names, or by `MOONCAKE_CONFIG_PATH` when it is not set, and must use `"mode": "standalone-store"`: objects placed in the memory of an embedded client disappear when that client exits. Use a master and pool separate from any Mooncake KV store, which evicts and can be reset with `remove_all(force=True)`. The Mooncake KV connector reads `MOONCAKE_CONFIG_PATH`, so with it set `"mooncake_config_path"` to the object store's file. Only a write the store refuses for lack of memory (Mooncake error -200, for example while memory is full) is retried, every 0.2 s, and the engine waits while writes progress. If writes are pending and none lands for `"object_put_stall_timeout_s"` (default 600 s), including when a write hangs inside the store, or the store fails a write for another reason, the engine stops at its next step.
- **Store capacity.** By default objects are not pinned, and the store keeps them by offloading to SSD on eviction: memory is a cache and the SSD holds every object until it is removed. Start `mooncake_master` with `--enable_offload=true --offload_on_evict=true --offload_force_evict=false --enable_disk_eviction=false --client_ttl=600`. Offload at put lost objects without an error and is not supported, and a holder silent for longer than the client TTL is dropped with its objects (600 s kept all of them in our tests). Start every `mooncake_client` the master can place objects on with `--enable_offload=true` and `MOONCAKE_OFFLOAD_FILE_STORAGE_PATH` set to a new, empty SSD directory of its own, and delete the directory when the job ends: removal deletes only metadata, and a holder restarted on an old directory registers removed keys again. Removed objects keep their disk space until the directory is deleted, so size the SSD by the bytes written in the job and admit new sessions by free disk. Keep disk eviction off: it deletes objects by age, including ones not yet released. The engine cannot see the master's settings: without offload on eviction, an object that is not pinned is lost when memory evicts it. Mooncake keeps one copy of each object, on the holder it was placed on: keep every holder up until the objects on it are read and removed, and never restart a holder within a job, or the objects other replicas placed on it are lost. For a store without SSD, set `"object_hard_pin": true`: objects are never evicted, memory must hold everything written between two removals, and when it is full and nothing is removed the engine stops at the stall deadline.
- **Key prefix.** `object_key_prefix` enables sessions. It is one path segment without `/`. Objects are immutable, so never reuse a prefix: choose a new one for every start of a deployment, including a restart of the same job, and a different one for every deployment that shares the store. Replicas of one deployment that share a configuration use the same prefix: replicas that compute the same positions of a session at the same weight versions write the same keys. A session under another prefix shares no KV with it.
- **Requests.** `aux_session` is a non-empty string without `/`. It is rejected without `object_key_prefix`, together with `stop` strings (the frontend ends such a request before the engine can return its keys; use `stop_token_ids`), and on streaming-input requests. `routed_experts_prompt_start` and `indexer_topk_prompt_start` are ignored for a session request. Only the Python API server accepts `aux_session`.
- **Weight versions.** The weight version of the KV of every position is part of the block hashes of a session request (per-segment cache salts), so every KV cache tier and KV connector keyed by block hashes reuses KV across a weight update only where its versions are the ones the request states, with no connector-specific code. Pass the previous response's `aux_version_segments` with the session's next request: `[[start, version], ..., [end, null]]`, starts increasing from 0 and adjacent versions differing. The engine salts the prompt positions below `end` (rounded down to an object, and to the last object that ends before the prompt's last token) with these versions and later positions with the current weight version (`update_weight_version`, `default` before the first call). A request without them computes its prompt as if new to the session. When the weight version changes, positions of live session requests that are neither computed nor hashed yet are salted with the new version; hashed positions keep their names. Change the version only while no step is in flight, that is while the engine is paused: the engine does not check this, and a change with a step in flight can give the positions that step computes, or a draft it later rejects, the wrong version.
- **Objects.** The engine writes one immutable object per block of the full-attention KV cache group, holding one array per enabled output (`routed_experts`, `indexer_topk`), named `<object_key_prefix>/<aux_session>/<hash of the block's last hash block>`, once the block's last position is computed. The rows after the last listed block are one object named `<object_key_prefix>/<aux_session>/tail/<hash>`, where the hash covers the preceding block, the tokens, the versions of those positions and the request's other block-hash extra keys (LoRA, multimodal inputs, prompt embeddings), so tails of different branches, lengths or versions never share a key.
- **Hidden states.** `"enable_return_hidden_states": true` also stores, as field `hidden_states` with shape `[tokens, hidden_size]`, the hidden states that the model's forward pass returns for every position. For most models these are the input of the LM head; a model that applies its final normalization inside `compute_logits` (Step3.5) returns the states before it. NumPy has no bfloat16, so a bfloat16 model's rows are int16 bit patterns: `torch.from_numpy(rows).view(torch.bfloat16)`.
- **Top-k logprobs.** `"return_topk_logprobs": k` stores, for every position `p`, the `k` most likely next tokens and their log-probabilities (the model's logits from `compute_logits`, log-softmax in float32, before any sampling parameter) as fields `topk_token_ids` (int32) and `topk_logprobs` (float32), shape `[tokens, k]`. Unlike `prompt_logprobs`, which disables prefix-cache hits, a hit keeps the rows of the request that computed the position, so a teacher can score long multi-turn prompts incrementally. The engine computes them for the scheduled tokens of session requests only, in chunks of at most 1024 rows and, as for `prompt_logprobs`, at most 64Mi / (k + 1) rows. Neither the float32 logits of a chunk nor the step's results are part of the memory profile: leave headroom in `gpu_memory_utilization` for about 1024 × vocabulary size × 10 bytes plus the results, session tokens of a step × k × 8 bytes, twice that while the chunks are concatenated. On the host the results are copied to pinned memory, then staged per request and serialized into their objects, and up to `2 * max_num_seqs` steps of objects wait to be written, so host memory needs several times the results' size.
- **Response.** The final output of a stopped request (the last chunk when streaming) lists in `aux_output_keys` the keys of the objects holding rows `[0, num_tokens - 1)`, in order, and returns `aux_version_segments` for the session's next request, up to the last full object computed after its block hashes existed: with hash look-ahead, the object that the last sampled token completes is left to the next request, which computes it again under its own version. Every turn lists all its keys, about 100 bytes per KV cache block of the request. A request that stops on an output in flight while it is preempted, or is aborted, lists no keys. Read the rows with `object_store.read_aux_rows(object_store.MooncakeAuxObjectStore.create(mooncake_config_path), keys, "routed_experts")` (or `"indexer_topk"`) from `vllm.distributed.aux_output_connector` with the engine's `"mooncake_config_path"` (`None` reads `MOONCAKE_CONFIG_PATH`); it waits up to 600 seconds for objects that are still being written. Keep the read timeout no shorter than the engine's `"object_put_stall_timeout_s"` (also 600 seconds by default), since a full store can hold writes back that long while the engine keeps running. A timeout does not by itself mean the objects are lost: behind a deep queue a healthy engine can land them later. Check the engine first, since an engine stopped on a write stall fails its steps and pauses with the write error; if it is healthy, read again, or after its next completed pause, instead of dropping the sample. Create the store client in a process that does not start an engine afterwards: a Mooncake client created before the engine breaks CUDA initialization in the engine's workers.
- **KV cache layout.** The engine refuses to start with `object_key_prefix` without prefix caching, if the target model has no plain full-attention KV cache group, if prefix-cache hits may end inside a KV block, if block hashes look ahead more than one token, or with prefix replay (disable `CacheConfig.swa_bounded_replay` for models that use it). For models with sliding-window KV cache groups (DeepSeek-V4 class), set `prefix_cache_retention_interval` to `null` or the block size so that a later turn hits the outputs of earlier turns.

The engine only writes objects; the consumer deletes them with a Mooncake client (`mooncake.store.MooncakeDistributedStore`) connected to the same store: `remove_by_regex(object_store.aux_session_pattern(object_key_prefix, aux_session), True)` for a session after reading the objects of its last turn, or `remove_by_regex(object_store.aux_prefix_pattern(object_key_prefix), True)` for everything under the prefix. Release by session, not by the keys a response lists: a session also holds the objects of blocks hashed when a request stopped, which that response lists in its tail and the next turn lists by name. Delete a session only after its requests have finished and every engine that served them has completed a pause since (`pause_generation` in any mode, as before a weight update): a completed pause has written every object of the requests that finished before it, including aborted requests and requests whose response lists no keys, and fails instead if a write failed or writes stalled past `"object_put_stall_timeout_s"`. Delete a prefix only after the engines that write under it have shut down or stopped writing to it: Mooncake skips objects that are still being written, even with force, and they stay in the store. Do not send another request with a released `aux_session`: the engine still lets it hit the KV of the removed objects. Continue under a new session name, which recomputes the prefix.

### Limits

- A key names the tokens and the weight versions a request states for them, and the store keeps the first object written under it. A position computed again keeps its name and so the earlier rows: after its KV was lost (evicted from every tier, tiers cleared at a reset, client `aux_version_segments` from a replica whose KV is not here), after a preemption, for a trailing block that EAGLE-style drafting computes again, and with `prompt_logprobs` or `skip_reading_prefix_cache`. Provision KV storage so session prefixes stay cached.
- A failed synchronous KV load reported through `invalid_block_ids` is not supported for session requests. The report arrives after the step ran: the objects completed by that step, and by a step already in flight under asynchronous scheduling, including the tails of requests that finished, were computed from the invalid KV and are already written under their final names, and the store keeps them. With more than one KV cache group, any `invalid_block_ids` makes the scheduler raise, whatever the policy. With one group and `kv_load_failure_policy="recompute"`, recomputing the request usually stops the engine with an assertion (not under `python -O`), but nothing stops it when the request is aborted, preempted or reset (`reset_running_requests`) before it is scheduled again, when a request that shares the invalid block is not rolled back with it (for example one absent from the failing step under asynchronous scheduling), or when a request finishes on an output already in flight. With the default `"fail"` the request fails, but the objects stay and a retry or the next turn reads them. Use, for session requests, `MooncakeStoreConnector` with `load_async` at its default `true`, which loads asynchronously and reports failed loads, or `OffloadingConnector`, which raises on a failed synchronous load. Neither backend of `SimpleCPUOffloadConnector` reports a failure. The CPU backend copies in both directions on one thread, and a failed copy ends it. The disk backend (`kv_offload_backend="disk"`) loads and stores on separate threads: a failed read, or a failed GPU copy while loading, ends the load thread; a failed write, or a failed GPU copy while storing, ends the store thread. The failed transfer and every later one on that thread never finish, and the engine never goes idle. Once a store is stuck (on the CPU backend, any store after a failed copy in either direction), every later pause hangs, and with it the weight update and sleep; while only loads are stuck, pauses in `wait` or `abort` mode hang, and after an abort of the stuck request every pause in any mode. Either way there is no engine error or request failure and the blocks stay held, and shutdown ends only when the process manager kills the engine after its timeout, skipping teardown: object writes still queued at the kill are lost. The disk backend's offload file is removed only at its next start, however the engine exits.
- A block is hashed when its tokens exist, not when it is computed, and a request keeps its hashes. A request waiting at a weight update, including one added while the engine is paused for it, names its whole prompt with the version current when it was hashed; a partly prefilled request, and a decoding request whose last sampled token completes a block, name the positions hashed before a weight update and computed after it by the earlier version; so do siblings with the same prompt whose prefill progress differs at the update.
- Draft KV that multi-module MTP computes again after a weight update carries the target positions' versions; the target rows are not affected.
- Same name means same rows only with batch invariance.
- Configure KV connectors to store the blocks that decoding completes, for example `save_decode_cache: true` for `MooncakeStoreConnector`: otherwise the last block of every turn is missing from the store, and the next turn computes it again on a replica that does not hold it.
- Replicas that share the object store must enable the same outputs.
- Replicas that share KV stores or the object store must hash identically: the same hash algorithm with `PYTHONHASHSEED` set to one value everywhere or unset everywhere (unset, only a cryptographic algorithm such as `sha256` gives every process the same seed), hash block size, full-attention KV block size (the object size) and look-ahead.
- The object pool needs its own Mooncake master, separate from any Mooncake KV store: with a Mooncake KV connector, set `"mooncake_config_path"`.
- The store keeps objects only with SSD offload on eviction on every holder it can place them on, or with `"object_hard_pin": true` and memory for everything written between two removals.
- Prefill/decode disaggregation (NIXL, Mooncake P2P, Moriio) is not supported: the decode side does not receive the prefill's segments.
