# b12x Linear and MoE Backends

[b12x](https://pypi.org/project/b12x/) provides optional CUDA kernels for
NVIDIA SM120 and SM121 GPUs. Install the dependency with:

```bash
uv pip install "vllm[b12x]"
```

b12x linear kernels participate in automatic selection after established
optimized backends and before emulation. Select the linear and MoE backends
explicitly with:

```bash
vllm serve <model> \
    --linear-backend b12x \
    --moe-backend b12x
```

Only pass `--moe-backend b12x` for a compatible packed-weight MoE model. The
linear and MoE backends can be selected independently.

b12x uses MXFP8 activations by default for MXFP4 MoE and the checkpoint's
activation format for NVFP4 MoE. MXFP4 falls back to BF16 when its A8 path does
not support the model configuration. Set `VLLM_B12X_MOE_FP4_FORCE_A16=1` to
force BF16 activations for either FP4 weight format.

## Compressed MXFP4 expert scales

Set `VLLM_B12X_MOE_MXFP4_CSF=1` with `--moe-backend b12x` to keep eligible
MXFP4 expert block scales compressed in GPU memory. This option is disabled by
default and requires a b12x installation exposing `Mxfp4CsfWeights`, such as
FlashInfer's experimental b12x package. An older standalone b12x package may
not expose that API.

```bash
VLLM_B12X_MOE_MXFP4_CSF=1 vllm serve <MXFP4-model> --moe-backend b12x
```

Scales are encoded losslessly after each tensor-parallel rank loads its shard.
FlashInfer selects the scale representation from the supported weight geometry.
When a prepared execution plan supports inline decoding, the GEMM kernels read
compressed scales directly. Other plans expand routed experts' scales into
shared buffers before the MoE call. The selection is prepared and cached before
CUDA graph capture. Activation precision is unchanged. GEMM layouts and
intermediate rounding follow the selected FlashInfer kernels.

This reduces resident scale memory for compressible checkpoints at the cost of
load-time encoding. Compression ratio and inference overhead depend on the
prepared representation and batch shape; inline storage can be larger than the
canonical compressed payload.

This path requires MXFP8 activations, gated experts, a hidden size divisible by
256, and a per-rank intermediate size divisible by 64. Both dimensions must be
at most 8160. Compact layouts (an intermediate size of 64 modulo 128) require
SiLU, BF16 input/output, and the native prepared execution API. Packages exposing
only the older binding require an intermediate size divisible by 128.

Other shapes, BF16 activation backends (including
`VLLM_B12X_MOE_FP4_FORCE_A16=1`), and packages without the CSF API keep
uncompressed scales and emit a warning. Expert biases remain unsupported, so
gpt-oss checkpoints cannot use this backend.

Resident CSF layers do not support weight reloading. Scale expansion buffers
are shared across layers of the same shape and dtype; execution must be
serialized on one CUDA stream.

### Choosing memory saving or inline decoding

Expansion retains the smaller canonical CSF representation. Inline decoding
avoids separate scale-expansion work but can use a larger resident representation.
Prefer expansion when model or KV-cache capacity is the main constraint; inline
can help decode throughput when enough memory is available.

With a compatible FlashInfer package, set `B12X_W4A8_CSF_INLINE=0` before loading
the model to keep expansion:

```bash
B12X_W4A8_CSF_INLINE=0 VLLM_B12X_MOE_MXFP4_CSF=1 \
    vllm serve <MXFP4-model> --moe-backend b12x
```

`B12X_W4A8_CSF_INLINE=1` permits inline decoding where the package, geometry,
and prepared capacity support it. It does not force unsupported plans inline.
The representation is selected during model loading, so restart the server when
changing this setting. FlashInfer 0.7.2.post1 uses expansion for full-N128 shapes;
the [proposed inline extension](https://github.com/flashinfer-ai/flashinfer/pull/8060)
adds compact packing for those shapes.

For example, a GLM-5.3-Flash MXFP4 TP2 comparison on two DGX Sparks measured:

| Scale path | Model allocation per rank | Total saved versus uncompressed | Output tokens/s at concurrency 8 |
| ---------- | ------------------------- | ------------------------------- | ------------------------------- |
| Expansion with stock FlashInfer | 80.02 GiB | 7.06 GiB | 57.78 |
| Inline with the proposed FlashInfer extension | 80.68 GiB | 5.74 GiB | 62.19 |

The uncompressed parent allocated 83.55 GiB per rank. Inline used 1.32 GiB more
across the pair than expansion, while increasing throughput by 7.6% and reducing
median inter-token latency from 120.07 to 109.82 ms. Model allocation excludes
the subsequent KV cache allocation.

These are configuration-specific observations from one pass with 1024-token
inputs, 256-token outputs, BF16 model dtype and W4A8 computation. The two CSF
arms used the same vLLM source and settings. See the
[validation and reproduction details](https://github.com/vllm-project/vllm/pull/64828).

## Supported Configurations

| Backend | Supported configurations |
| ------- | ------------------------ |
| Linear | Per-tensor FP8, 128x128 block FP8, MXFP8, NVFP4 (including W4A16), MXFP4, IQ2_XS, IQ2_XXS, and Q8_0 |
| MoE | Tensor-parallel MXFP4 weights with BF16 or MXFP8 activations; NVFP4 weights with BF16, NVFP4, or MXFP8 activations; IQ2_XS, IQ2_XXS, and Q8_0 weights with BF16 activations |
| Embedding | Packed Q8_0 lookup with BF16 output |

The b12x MoE backend does not support expert parallelism, expert maps, EXL3, or NF3.

## ModelOpt block codecs

ModelOpt mixed-precision checkpoints select block codecs through the
`quantization_config.quantized_layers` entries in `config.json`. Each entry
declares `quant_algo`, `group_size`, `block_payload_bytes`, and `packing="ggml"`:

| `quant_algo` | `group_size` | `block_payload_bytes` |
| --- | --- | --- |
| `IQ2_XS` | 256 | 74 |
| `IQ2_XXS` | 256 | 66 |
| `Q8_0` | 32 | 34 |

Serialized matrices have uint8 shape `[N, K/group_size, block_payload_bytes]`.
Dense preparation rearranges the encoded blocks without expanding the matrix
to BF16. Routed experts use bias-free SiLU or non-gated ReLU²; tensor-parallel
shards must preserve whole blocks and satisfy the kernel's alignment constraints.
Only Q8_0 supports packed embedding lookup.

Quantized normalization weights and other packed vectors are not supported.
Store normalization weights as ordinary floating-point tensors and omit their
entries from `quantization_config.quantized_layers`.

Dense, embedding, and expert matrices remain packed. Their execution uses BF16
activations without activation quantization. Prepare the kernels and workspaces
before CUDA graph capture.
