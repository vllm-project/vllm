Grid Hints vs Pixels

Sending the decode instance a patch grid instead of the image raises throughput 1.23–1.28× at low concurrency and cuts time-to-first-token by a third — then the advantage decays to nothing by concurrency 32, as the decode GPU becomes the constraint.

The mechanism is visible in the stage timings: the decode instance's time-to-first-byte roughly halves while the encode stage holds constant. That is the duplicated image transform disappearing from the decode side, which is exactly what the change removes.

Validity

Why these numbers can be trusted

✓

Nothing was queueing

Peak vllm:num_requests_waiting was 0 at the encoder at every load point, so the encoder never queued. The decode instance stayed at 0–2 through concurrency 8, then rose to 5–8 at 16 and 17–18 at 32 — so the two highest points are partly queue measurements and the clean comparison is concurrency 1 through 8. Sampled once per second and sliced per load point.

✓

The encode stage is flat between arms

148.6 / 149.7 / 164.8 / 189.2 ms against 153.9 / 150.5 / 153.2 / 168.1 ms. The encoder receives identical requests in both arms, so a flat encode stage is what correctness looks like. An earlier 50% gap here was queue depth wearing a stage's name.

✓

Order was alternated and the effect survived

Grid wins by the same margin whether it runs first or second, and baseline reproduces to within 2–5% across reps.

✓

Both arms were verified to have engaged

The proxy rewrote 112 of 112 image references in the hint arm and exactly 0 in the baseline arm, asserted per load point rather than assumed.

Earlier measurements

What made the first attempts meaningless

An earlier round of this comparison reported no effect at all, and a spurious 50% penalty on the encode stage. Both came from the harness, not the code under test.

The encoder could only ever process one image at a time

--max-num-batched-tokens 8192 against 5,350 tokens per 2048² image made two image requests unbatchable, pinning the encoder at ~25 req/s. Raised to 65,536 for the encode-only instance, it now batches up to 9 requests per step.

All 400 requests were fired at once

--request-rate inf with no concurrency limit put ~400 requests in a queue that drained at 25/s. Median TTFT was 20 seconds, and every stage timing was queue depth divided by service rate. Bounded concurrency replaced it.

The tell was that total time never changed

All four cells of the earlier 2×2 completed in 56.2–56.6 s with identical throughput while the stage numbers moved by 50%. Time was being relabelled, not saved — the signature of a queueing artefact rather than a real effect.

Corrections

Claims made earlier that these runs disprove

  • "There is nothing to win on this hardware." Argued from 128 mostly-idle CPU cores and a GPU-bound decode instance. Wrong: the image transform sits on each request's serial path — prefill cannot start until it finishes — so spare cores elsewhere can't absorb it. Removing it cuts ~130 ms from every request's TTFT.
  • "Grid mode makes the encode leg ~50% slower." Reported from four runs at rate=inf. It was queue depth, and it vanishes entirely under bounded concurrency.
  • "The earlier fast runs were fast because they had no proxy." They had the proxy. They were fast because 1288×728 images fit six per batch under the 8192-token budget, while 2048² images fit one.
Scope

What this does not establish

  • 120 prompts per load point and two replications. Enough to separate a 15–26% effect from run-to-run noise of 2–5%; not enough for a confidence interval.
  • The image pool is real photographs Lanczos-enlarged to 2048², measured at 0.17 MB per megapixel against 0.13 for a native crop — so payload behaviour is representative, but the images are not natively that size.
  • Our advantage disappears above concurrency 8, where the PR's held. The decode instance's queue grows 0 → 2 → 5 → 17 across the sweep while the encoder's stays at 0, so past c=8 this box is decode-GPU-bound and a decode-side CPU saving has nothing left to buy. Their larger MoE model likely shifted that balance.
  • This is ECExampleConnector over shared filesystem. Whether the NIXL transport inherits the same benefit is a separate comparison.
