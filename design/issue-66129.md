# vllm#66129: compressed-tensors loads FP8 k/v scales into BF16 KV-cache layers

Issue: https://github.com/vllm-project/vllm/issues/66129

## Summary

With a compressed-tensors checkpoint that has a static FP8 `kv_cache_scheme`, a
layer whose KV cache is kept unquantized (for example via
`--kv-cache-dtype-skip-layers sliding_window`, which sets `kv_cache_dtype="auto"`)
still receives the checkpoint k/v scales. The FlashInfer backend then multiplies
attention scores and outputs by those scales even though the cache is BF16, which
corrupts attention on those layers. Accuracy degrades silently because outputs stay
well-formed under grammar-constrained decoding.

## Root cause

- `vllm/model_executor/layers/attention/attention.py:321-336`: skip-layer logic sets
  `kv_cache_dtype = "auto"` for matching layers, so those layers have an unquantized
  cache. The checkpoint scale plumbing is not changed by this path.
- `vllm/model_executor/layers/quantization/kv_cache.py:110`
  (`BaseKVCacheMethod.process_weights_after_loading`): only a quantized cache
  (`is_quantized_kv_cache`) copies the checkpoint scales into `_k_scale`, `_v_scale`,
  `_q_scale`, and the `_*_scale_float` host copies. Otherwise the 1.0 defaults from
  `attention.py:151` and `attention.py:165` remain.
- `vllm/model_executor/layers/quantization/compressed_tensors/compressed_tensors.py:1264`
  (`CompressedTensorsKVCacheMethod.process_weights_after_loading`, before this change):
  overrides the base method without calling `super()` and without any
  `kv_cache_dtype` check. It registers `_k_scale`/`_v_scale` from `layer.k_scale`/
  `layer.v_scale` and sets `_k_scale_float`/`_v_scale_float` unconditionally. This is
  the leak.
- `vllm/v1/attention/backends/flashinfer.py:2470-2481`, `2651-2653`, `2669-2671`
  (and `526-527`): FlashInfer passes `layer._k_scale_float`/`_v_scale_float` into the
  kernels regardless of cache dtype. `2190-2191`, `2256-2262` gate on
  `is_quantized_kv_cache` for the bmm scales, but the native prefill/decode calls at
  `2470-2481` and `2651-2671` do not, so they consume the leaked scale.

## Proposed fix (implemented on this branch)

In `CompressedTensorsKVCacheMethod.process_weights_after_loading`, when
`not is_quantized_kv_cache(layer.kv_cache_dtype)`, replace the k and v scales with
`torch.ones_like(...)` before registering the `_k_scale`/`_v_scale` buffers and
computing the `_float` values. The condition is exactly the one `BaseKVCacheMethod`
uses (`compressed_tensors.py:1273`).

Deliberately not changed:
- `_q_scale` still comes from the checkpoint. The q scale is used for FP8 queries
  (see PR #64329, which fixes FlashInfer's q scale for non-FP8 queries). Changing it
  here would be a separate behavior change.
- The FlashInfer call sites are left alone. With k/v buffers at 1.0 they are correct
  for unquantized caches, so a second guard there is defense in depth only.

## Test plan

- Added `test_compressed_tensors_kv_scales_follow_kv_cache_dtype` in
  `tests/quantization/test_compressed_tensors.py`, parametrized on `auto` (expects
  k/v = 1.0) and `fp8` (expects checkpoint k/v = 0.0038 / 0.0344). It is CPU-only: it
  builds `CompressedTensorsKVCacheMethod` with a mocked quant config, calls
  `create_weights`, loads scales directly, and calls `process_weights_after_loading`.
- Before the fix, the `auto` case should fail (`_k_scale_float == 0.0038`). After the
  fix it passes.
- Manual GPU check (not run here): serve `unsloth/gemma-4-26B-A4B-it-NVFP4` with
  `--kv-cache-dtype fp8 --kv-cache-dtype-skip-layers sliding_window` on FlashInfer and
  compare per-layer attention output with the reference, as in the issue. Run a GSM8K
  or similar accuracy eval against TRITON_ATTN.

## Risks

- Behavior change only for layers with an unquantized cache that also have a
  compressed-tensors `kv_cache_scheme`. These layers previously used the checkpoint
  scale (incorrect per the issue), so the change should only move outputs toward
  correct values.
- The `ones_like` buffers keep the shape of the loaded parameter (ATTN_HEAD gives n
  scales); `_float` uses max, which is 1.0 for all-ones. Buffers stay buffers, so
  level-2 sleep behavior is unchanged.
- The test does not exercise the FlashInfer kernel path. A GPU run is needed to
  confirm the end-to-end fix.
- Environment: this worktree's test file imports `compressed_tensors`, which is not
  installed here, and `tests/conftest.py` needs `tblib`, also not installed. The test
  could not be run locally. See the report.
