# Issue 66610: /detokenize silently drops out-of-vocabulary token IDs

## Summary

`POST /detokenize` returns HTTP 200 when the request contains token IDs outside
the model vocabulary. Those IDs are dropped from the decoded text, so the client
receives wrong output with no error. `/v1/completions` rejects the same ID with
HTTP 400 `Token id 999999999 is out of vocabulary`.

## Root cause

- `vllm/entrypoints/serve/tokenize/api_router.py:71` routes `/detokenize` to
  `ServingTokenization.create_detokenize`.
- `vllm/entrypoints/serve/tokenize/serving.py:137-163` (before the fix) passed
  `request.tokens` straight to `renderer.tokenize_prompt_async()` without any
  vocabulary check.
- Because the input is `TokensPrompt`, tokenization is skipped and the request
  goes to the detokenize step: `vllm/renderers/base.py:691` calls
  `_async_tokenizer_decode`, which is `_decode` (`vllm/renderers/base.py:228-229`,
  `tokenizer.decode`). The HF/fast tokenizer decode skips IDs it has no token
  for, so nothing fails and nothing is logged.
- The generation path validates first. `vllm/v1/engine/input_processor.py:642`
  calls `self.renderer.validate_token_ids(prompt_ids)`, which is defined at
  `vllm/renderers/base.py:453-481`. It rejects negative IDs and IDs above
  `max(tokenizer.max_token_id, model_vocab_size - 1)` with
  `VLLMValidationError`. `VLLMValidationError` is already mapped to 400 for this
  endpoint (see `TestDetokenizeClientErrorResponses` in
  `tests/entrypoints/serve/tokenize/test_serving_tokenization.py`, PR #52622).

So the bug is that `/detokenize` never calls the validator that the generation
path and the KV-transfer path (`vllm/renderers/online_renderer.py:164`) already
use.

## Proposed behaviour

Return HTTP 400 (`BadRequestError`, `param: "tokens"`) when any ID is out of
vocabulary, including mixed valid/invalid lists. No partial output.

Reasoning:
- It matches `/v1/completions` for the same input, which is the consistency
  the issue asks for.
- It matches the Rust frontend fix referenced in the issue (#62775).
- `check-api-compat` was considered. `/detokenize` is a vLLM-specific endpoint
  with no OpenAI counterpart, so the upstream spec does not define its error
  behaviour. The skill says not to use it for such endpoints. The decision rests
  on vLLM consistency and on the `VLLMValidationError` to 400 mapping that is
  already in place.
- Silent truncation is the worst option for a detokenize API: callers cannot
  tell that output was lost.

## Change

`vllm/entrypoints/serve/tokenize/serving.py`, `create_detokenize`:

```python
self.renderer.validate_token_ids(request.tokens, parameter="tokens")
```

placed before `tokenize_prompt_async`. The validator already handles the empty
list and negative IDs. `DetokenizeRequest` already restricts `tokens` to
`0 <= id <= 2**63 - 1` at the schema level, so the negative branch is a backstop.

## Test plan

Added to `tests/entrypoints/serve/tokenize/test_serving_tokenization.py`:
- `test_detokenize_rejects_out_of_vocabulary_ids_before_decoding`: builds a real
  `ServingTokenization` with a mocked renderer whose `validate_token_ids` raises
  for `[9707, 999999999]`. It asserts that `create_detokenize` raises
  `VLLMValidationError` (`parameter="tokens"`), that validation sees the full
  list (so mixed input is covered), and that `tokenize_prompt_async` (the decode
  step) is never called.

Existing `TestDetokenizeClientErrorResponses` tests continue to pin the 400
mapping.

Recommended before merge (not done here, no GPU or full test env):
- Run the test file under the project venv (`uv`, `.venv/bin/python -m pytest`).
- Live check on CPU or small model: `POST /detokenize` with `[9707]` (200),
  `[9707, 999999999]` (400), `[151936]` for Qwen2.5-0.5B (400), `[-1]` (400 or
  422 from schema validation).
- Regression check that `/detokenize` for valid IDs returns the same text as
  before.

## Risks

- Vocabulary bound: the validator uses the larger of the tokenizer max ID and
  the model vocab size minus one. For models with padded embedding tables, IDs
  in the padding range pass validation but may still decode to nothing. This is
  the same gap as generation, so it is not a regression, but it is not fully
  fixed here.
- Behaviour change: clients that relied on silent dropping will now get 400.
  This is the intended fix, but it is user-visible. Release notes should mention
  it.
- Duplicate work: open PR vllm-project/vllm#66614 ("[Bugfix][Frontend] Reject
  out-of-vocabulary token ids in /detokenize") targets the same bug. AGENTS.md
  says not to open a second PR for the same fix, so this change should be
  compared with #66614 before anything is submitted. This branch is local only.
- Performance: one `max()`/`min()` over the token list. Negligible next to
  decode.
- Tests were not executed in this environment (see report).
