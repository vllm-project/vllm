# Issue #65401: get_top_k_tokens applies scaling and soft capping in the wrong order

Issue: https://github.com/vllm-project/vllm/issues/65401

## Open PRs

- PR #65415 "fix(logits_processor): apply soft capping before scaling in get_top_k..." is open and targets this issue. Check it before opening another PR.
- Issue comment from seansie0830 (2026-11-03) says a fix is in progress with a unit test. This is the same fix.

## Summary

`LogitsProcessor.get_top_k_tokens(..., return_log_probs=False)` returns top-k scores that differ from `forward()` for the same token ids when both `scale != 1.0` and `soft_cap` is set. The candidate ids are the same. Only the scores differ.

Worked example from the issue (raw logit 4.0, scale 2.0, soft_cap 3.0):

- `forward()` (soft cap, then scale): `2 * 3 * tanh(4 / 3)` = 5.220370
- `get_top_k_tokens` before fix (scale, then soft cap): `3 * tanh(2 * 4 / 3)` = 2.971171

I checked this in pure torch, outside vLLM, and the numbers match.

## Root cause

The two code paths disagree on order.

- `vllm/model_executor/layers/logits_processor.py:113-119` (`forward`): soft cap first (`logits / soft_cap`, `tanh`, `* soft_cap`), then `logits *= scale`.
- `vllm/model_executor/layers/logits_processor.py:236-239` (`get_top_tokens`): soft cap first, then scale. This matches `forward`.
- `vllm/model_executor/layers/logits_processor.py:293-297` (`get_top_k_tokens`, `return_log_probs=True`): soft cap first, then scale. This matches `forward`.
- `vllm/model_executor/layers/logits_processor.py:323-327` (`get_top_k_tokens`, `return_log_probs=False`, before fix): scale first, then soft cap. This is the bug. The scale and soft cap are applied to the k selected values after top-k selection, and the order is reversed.

Selection is not affected. Both `tanh` and a positive scale are monotonic, so top-k by raw logit selects the same ids. Only the returned values are wrong.

## Proposed fix

Swap the two blocks at `logits_processor.py:323-327` so soft cap runs before scale. This matches `forward()`, `get_top_tokens()`, and the `return_log_probs=True` branch. The docstring at lines 282-283 still holds and does not need changing.

```python
if self.soft_cap is not None:
    values = torch.tanh(values / self.soft_cap) * self.soft_cap
if self.scale != 1.0:
    values = values * self.scale
```

The optimization stays: only the k selected values are transformed, not the full vocabulary.

## Tests

- Added `tests/model_executor/layers/test_logits_processor_top_k.py`. It is CPU-runnable. It parametrizes `scale` over {1.0, 2.0} and `soft_cap` over {None, 3.0}. For each case it builds a single-shard `VocabParallelEmbedding` with `disable_tp=True`, as in the issue reproducer, and asserts `get_top_k_tokens` values equal `full_logits.gather(-1, ids)`.
- The parametrization with `scale=1.0` and `soft_cap=None` is a control. It passes before and after.
- Consider also a case with `return_log_probs=True` to lock in that branch's behavior, which is already correct.
- An end-to-end model accuracy test is not needed. The bug only affects returned candidate scores.

## Risks

- Behavior change for any caller that reads the scores from `get_top_k_tokens` with `return_log_probs=False` and a soft cap plus non-unit scale. Those values change to match `forward()`.
- Callers found by grep: `vllm/model_executor/models/qwen3_dflash2.py:565`, `vllm/model_executor/models/lilicorr.py:489`, `vllm/models/beam/amd/dflash2.py:601`, `vllm/models/beam/nvidia/dflash2.py:616`. Each returns the values as candidate scores. I did not check whether the downstream DFlash2 and LiliCorr code consumes these scores directly. Those models' candidate processors would need a soft cap plus non-unit scale to be affected.
- Existing tests `tests/v1/spec_decode/test_lilicorr.py:277` (uses `return_log_probs=True`) and `tests/v1/spec_decode/test_dflash2.py:915` (ids only) do not depend on the changed values.
- Models with `soft_cap` but `scale == 1.0` are unaffected, because the two orders are identical when scale is 1.0.
- The `scale <= 0` guard above the function is unchanged. Non-positive scales are still rejected.
