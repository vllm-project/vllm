# Issue #16353: Run performance benchmarks for multi-modal models in CI

## 1. What the issue asks for

Performance benchmarks in vLLM CI cover text-only models (e.g. Llama). The issue asks for
benchmarks on multi-modal models so regressions in multimodal paths (memory leaks, slow
batching, processor-cache changes) are caught. The original pitch also suggests tracking peak
memory with `resource.getrusage` (host RSS).

## 3. Existing infrastructure

### Performance benchmark pipeline (`.buildkite/performance-benchmarks/`)

- `scripts/run-performance-benchmarks.sh` runs latency, throughput and serving tests. The README
  says it is triggered manually, and that continuous results are published at perf.vllm.ai via
  PyTorch CI HUD. The README also asks that a run take about 1 hour.
- Config files in `tests/`:
  - `latency-tests.json`, `throughput-tests.json`, `serving-tests.json` (GPU defaults)
  - hardware variants: `*-cpu.json`, `*-arm64-cpu.json`, `*-hpu.json`
  - `nightly-tests.json` (larger suite, e.g. sonnet-dataset runs)
  - `genai-perf-tests.json`
- Format for serving tests: a `defaults` block (`qps_list`, `max_concurrency_list`,
  `server_parameters`, `client_parameters`) plus a `tests` list. Each test has `test_name`,
  `server_parameters`, `client_parameters` (for example `dataset_name`, `num_prompts`).
- Scripts `launch-server.sh`, `compare-json-results.py` and `convert-results-json-to-markdown.py`
  handle launch, regression comparison and reporting.

### Multimodal coverage that already exists

- `.buildkite/performance-benchmarks/tests/serving-tests-cpu-asr.json` has one audio entry
  (`serving_whisper_large_v3_turbo_librispeech_clean_tp1`). It is the only multimodal perf
  config I found. No VLM (image) entry exists in any `serving-tests*.json`.
- `vllm/benchmarks/datasets/datasets.py` and `vllm/benchmarks/serve.py` support a `random-mm`
  dataset with flags: `--random-mm-base-items-per-request`, `--random-mm-bucket-config`,
  `--random-mm-limit-mm-per-prompt`, `--random-mm-num-mm-items-range-ratio`.
- `openai-chat` is the chat backend that sends multimodal content (used by the closed #39154 and
  present in `vllm/benchmarks/lib/endpoint_request_func.py`).
- `vllm/benchmarks/mm_processor.py` benchmarks the multimodal processor on its own (`random-mm`).
- Correctness/regression: `tests/models/multimodal/generation/test_memory_leak.py`
  (Qwen/Qwen3-VL-4B-Instruct, `enforce_eager`, 2 warmup + 16 measured rounds, GPU growth and CPU
  peak-RSS thresholds). It runs as a `core_model` step in `.buildkite/test_areas/models_multimodal.yaml`
  and in `.buildkite/test-amd.yaml`. It is a leak test, not a throughput or latency benchmark.

### The gap

1. No image/VLM serving or throughput entry exists in the perf pipeline configs.
2. The perf JSON records throughput and latency only. It has no peak-memory field.
3. The memory-leak test runs in per-PR correctness CI, not in the perf pipeline, so it does not
   produce comparable perf numbers.

## 4. Design (phase 1 implemented)

### Models
- Phase 1: `Qwen/Qwen3-VL-4B-Instruct`, as the maintainer asked ("Let's test Qwen3-VL first").
- Phase 2 (only if the maintainer asks): Qwen3.5 or another VLM.

### Config
- Add one entry to `.buildkite/performance-benchmarks/tests/serving-tests.json` (or a new
  `serving-tests-multimodal.json` referenced by the run script, if the team prefers separation):
  - `test_name`: `serving_qwen3vl_4b_tp1_random_mm_1img`
  - `server_parameters`: model, `tensor_parallel_size: 1`, `limit_mm_per_prompt: {"image": 1}`,
    `max_model_len` capped (8192 is enough for a short image prompt)
  - `client_parameters`: `backend: openai-chat`, `endpoint: /v1/chat/completions`,
    `dataset_name: random-mm`, `random-mm-base-items-per-request: 1`,
    `random-mm-limit-mm-per-prompt: {"image": 1}`, `random-mm-num-mm-items-range-ratio: 0`,
    `random-input-len` and `random-output-len` kept small, `num_prompts` about 100
  - `max_concurrency_list`: a small set, e.g. `[16, 64]`
  - Exact flag spellings and dataset defaults must be checked against `vllm/benchmarks/serve.py`
    before any PR.

### Peak memory
- Keep it out of the first PR (the maintainer asked for coordination first). Later: sample GPU
  memory via `current_platform` around the server run, and record host RSS with
  `resource.getrusage`, as the maintainer suggested. Add the fields to the result JSON so
  `compare-json-results.py` can diff them.

### CI wiring
- Perf runs are manual today. A scheduled or nightly job is a cost and hardware decision, so it
  needs maintainer sign-off. The smallest option is a single entry in the existing GPU
  `serving-tests.json`, which keeps the run inside the ~1 hour budget.

### Runtime and cost bounds
- One model, one image per request, `num_prompts` about 100, two concurrency levels. Expected
  runtime is a few minutes on one GPU. Confirm this on a perf run before merging.
