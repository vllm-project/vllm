# Issue #66436: streaming /v1/responses drops logprobs for empty text deltas

## Summary

With `stream: true`, `include: ["message.output_text.logprobs"]` and
`top_logprobs` set, `response.output_text.delta` events carry the logprobs of
only the token that produced visible text. When a visible character spans
several tokens (the issue uses `🪿`, 3 tokens in Qwen3-4B), the earlier tokens
produce empty text deltas, and their logprobs are discarded. The same loss
shows up in `response.output_item.done`, `response.content_part.done` and
`response.completed`, which are built from the accumulated delta logprobs.

## Root cause

The streaming loop in `_process_simple_streaming_events` skips a step as soon
as its delta has no content:

- `vllm/entrypoints/openai/responses/serving.py:1269-1270`: `if not delta_message: continue`
  (the `DeltaMessage` branch is only hit when the parser returns `None`).
- `vllm/entrypoints/openai/responses/serving.py:1275-1283` (before the fix):
  `if target_state == _StateType.NONE: continue`.
- `vllm/entrypoints/openai/responses/streaming_events.py:1328-1329`
  (`resolve_target_state`): `if delta_message.content:` is falsy for `""`, so an
  empty-text step resolves to `_StateType.NONE`.

Logprobs are only attached in `emit_delta` (`streaming_events.py` CONTENT branch,
around line 1415) via `_get_logprobs(output)`
(`serving.py:1234-1245`), which reads the current step's `token_ids`/`logprobs`.
Because the step is skipped before `emit_delta` runs, those tokens never reach
`emit_simple_content_delta` (`streaming_events.py:894-912`) and never reach
`state.accumulated_logprobs`.

Result: the logprobs of N-1 tokens are lost per multi-token character. The
issue's own comparison confirms the expected contract: Chat Completions emits
every token's logprobs in its chunk (empty `content` included) and OpenAI's
Responses endpoint emits all token logprobs with the text delta.

## Upstream spec expectation

Source: installed `openai` Python SDK 2.14.0 (`types/responses/response_text_delta_event.py:48`):

> `logprobs: List[Logprob]` — "The log probabilities of the tokens in the delta."

and the same wording for `response_text_done_event.py:45`. The field is
per-delta: each token's logprob must appear in exactly one delta, and the
aggregate over deltas is the set of tokens in the output text. An empty-text
delta is not a token boundary the spec recognizes, so there is no spec basis
for dropping the logprobs of tokens whose text is held back.

Not verified: the official OpenAPI YAML (`openai/openai-openapi`) was not
fetched in this session; the claim above rests on the SDK type docstrings. The
SDK in the python3.12 site-packages is 1.52.0 and lacks `types/responses`, so
2.14.0 from python3.13 was used.

## Proposed fix (implemented)

Carry the logprobs of content-less steps forward to the next content delta:

1. `SimpleStreamingEventProcessor` gets `pending_logprobs` and a
   `defer_logprobs(output, get_logprobs)` method
   (`streaming_events.py:1295-1310`). It only buffers while the current state is
   `NONE` or `CONTENT`; steps inside `REASONING` or `TOOL_CALL` are ignored, so
   reasoning or tool-call tokens never leak into `output_text` logprobs.
2. `emit_delta` CONTENT branch prepends pending logprobs to the current
   logprobs and clears the buffer (`streaming_events.py:1415-1416`).
3. `close_current` flushes any remaining pending logprobs into the content
   part's `accumulated_logprobs` when a CONTENT state closes
   (`streaming_events.py:1351-1358`). This covers a trailing EOS token whose
   text is empty and which would otherwise never reach a delta.
4. `serving.py:1269-1283`: both skip paths call `defer_logprobs`. The
   NONE-only check runs over all split parts of the step, so one engine step
   is deferred once and never double-counted.

Result: per-token logprobs are preserved and attributed to the delta that
carries the visible text, and the final `accumulated_logprobs` contains one
entry per content token.

## Risks

- **Overlap with open PR #66449** ("[Bugfix] Preserve Responses API logprobs
  across empty text deltas", opened 2026-11-09). It targets the same
  behavior. AGENTS.md says not to open a duplicate PR. This branch is local
  only, not pushed; the choice of which fix to land belongs to the maintainers.
- **Trailing-token attribution:** if a CONTENT state never sees another content
  delta, the buffered logprobs go only into the final content part, not into any
  delta. Consumers reconstructing logprobs from deltas alone would miss them.
- **Parser returning `None`:** `if not delta_message` now defers logprobs for
  any parser that returns `None`. The state guard limits this to NONE/CONTENT,
  but a parser returning `None` mid-content on a token that is not text would
  attribute its logprob to the next content delta.
- **Harmony path not changed:** `_process_harmony_streaming_events` is untouched.
  Logprobs there are rejected for gpt-oss (`serving.py:258-263`), so no change
  is needed.
- **Performance:** `_get_logprobs` runs only for deferred steps, and only when
  logprobs were requested; the cost is one list build per empty step.
