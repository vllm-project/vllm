# Design: unify boolean environment variable parsing (vllm#66493)

## Summary

`vllm/envs.py` parses boolean environment variables in six different ways. The
same input (`true`, `2`, `false`) gives different results depending on which
variable it is set for: a crash (`ValueError`), a silent `False`, a silent
`True`, or a correct value. The issue asks for one parser with defined accepted
values, and loud failure for values it does not understand.

Open PRs that mention this issue at the time of writing (checked with
`gh search prs --repo vllm-project/vllm 66493 --state open`):

- #66536 "Unify boolean environment variable parsing" (independent implementation, includes a 161-variable audit and a 924-case token matrix)
- #66543 "[Bugfix] Unify boolean env-var parsing in vllm/envs.py" (same consolidated direction)

Both PRs are competing with this design. The issue thread already shows the
two authors aware of each other and open to consolidating. This branch should
be coordinated with them before it lands, not merged alongside them.

Note on the issue text: it says the failure happens at `import vllm.envs`. In
this checkout the lambdas in `environment_variables` are read lazily through
`__getattr__`, so `import vllm.envs` succeeds and the `ValueError` is raised on
attribute access (for example `envs.VLLM_BATCH_INVARIANT`). The user-visible
outcome is the same; the message is still generic
(`invalid literal for int() with base 10: 'true'`) and does not name the variable.

each variable, but they are a separate correctness problem.

## Proposed helper

```python
_TRUE_ENV_VALUES = frozenset({"1", "true", "yes", "on"})
_FALSE_ENV_VALUES = frozenset({"0", "false", "no", "off"})


def get_bool_env(name: str, default: bool) -> bool:
    raw = os.environ.get(name)
    if raw is None or raw.strip() == "":
        return default
    value = raw.strip().lower()
    if value in _TRUE_ENV_VALUES:
        return True
    if value in _FALSE_ENV_VALUES:
        return False
    raise ValueError(
        f"Invalid boolean value {raw!r} for environment variable {name}. "
        "Expected one of: 1, 0, true, false, yes, no, on, off."
    )
```

Accepted values (case-insensitive, surrounding whitespace ignored):

- true: `1`, `true`, `yes`, `on`
- false: `0`, `false`, `no`, `off`
- unset or empty/whitespace only: returns `default`
- anything else: `ValueError` naming the variable

A tri-state variant for the `maybe_convert_bool` sites (returns `None` when
unset, otherwise delegates) should be added in phase 1 rather than changing
the helper's signature.

Decision on invalid values: raise, do not warn. Silent fallback is the failure
mode being reported. The issue comment from AryakumarMishra also leans this
way.

## Compatibility analysis

Must keep working unchanged:

- `"1"` and `"0"` for every variable (all six styles accept them today; the helper accepts them too).
- Unset variables return the same default as today. Defaults of `"1"` in the old code map to `default=True` (for example `VLLM_CPU_INT4_W4A8`, `VLLM_USE_LAYERNAME`, `VLLM_USE_DEEP_GEMM`). Verified by `test_migrated_getter_keeps_nonzero_default`.
- `"True"`/`"False"` (capitalized) for the `.lower()` family, which already accept them.

Intended behavior changes:

- `"true"`, `"false"`, `"yes"`, `"on"`, `"no"`, `"off"` now work for the bool(int) and `== "1"` sites. Previously they crashed or were silently ignored.
- Empty string (`VAR=`) for bool(int) sites returns the default instead of crashing.

Breaking changes to call out in the PR:

- `"2"`, `"enabled"`, `"-1"` and similar values previously evaluated to `True` for bool(int) sites and to `False` for `== "1"` sites. They now raise at attribute access. Anyone relying on `VAR=2` meaning true loses that; this is intentional but must be in the release notes.
- Some `== "1"` variables currently treat any typo as off. After migration, a typo raises. Scripts or CI configs that set a value like `VLLM_USE_AOT_COMPILE=enabled` would start failing.

Special cases that should NOT use the boolean helper:

- `NO_COLOR` and `FORCE_COLOR` (row 6). The no-color.org convention is that `NO_COLOR` is honored when set to any non-empty value, so `NO_COLOR=false` currently disabling color is not necessarily a bug. Migrating these to `get_bool_env` would silently change the behavior of `NO_COLOR=anything` for users who rely on the convention. Keep presence semantics and document them; do not migrate in this effort without a maintainer decision.
- `VLLM_USE_FLASHINFER_SAMPLER` (row 3) uses presence-based defaulting with a hardware-dependent default `True`. Its migration needs an explicit "unset means hardware default" path, so it belongs in phase 2.
- Defaults that are computed at runtime (`VLLM_USE_AOT_COMPILE` at 408 depends on torch version and `disable_compile_cache()`) must keep their computed default string; migrate only the parsing.

## Phasing

Do not migrate all sites in one change. Proposed order:

- **Phase 0 (this branch, first commit):** add `get_bool_env`; migrate the 24 single-line `bool(int(...))` lambdas, `disable_compile_cache`, and the two rust-path reads; add unit tests. Mechanical, same defaults, only invalid values and `true`/`yes`/`on`/`off` change.
- **Phase 1:** `maybe_convert_bool` (6 sites) via a tri-state helper; the 26 `.lower() in (...)` sites (mechanical, with the rust-path `auto` value kept separate); `VLLM_DEBUG_LOG_API_SERVER_RESPONSE`.
- **Phase 2:** the 14 `== "1"` sites and `VLLM_USE_FLASHINFER_SAMPLER`. These change behavior for `true`/`yes`/`on` (previously silently off) and for typos (previously silently off, now raise). Needs a release note and a maintainer sign-off on the strictness choice.
- **Phase 3:** `NO_COLOR` / `FORCE_COLOR`: maintainer decision on semantics, then separate PR.
- **Phase 4:** sync `TYPE_CHECKING` defaults (#54281) and add a test that every boolean-annotated variable parses through the helper.

## Test plan

Phase 0 (done in this branch, CPU-only):

- `tests/test_envs.py::TestGetBoolEnv`: true and false token sets (including case and whitespace), unset and whitespace-only returns default for both default values, invalid values raise `ValueError` naming the variable, `VLLM_BATCH_INVARIANT=true` works (regression for the crash), `VLLM_CPU_INT4_W4A8` keeps its `"1"` default, `VLLM_BATCH_INVARIANT=2` raises naming the variable.
- Run `tests/test_envs.py` and compare against the base commit. Result: 7 pre-existing failures on the base commit and on this branch (missing `tblib`/`vllm._version`-dependent tests and cache-state tests when run with `--noconftest`), 22 new tests passing.

Later phases:

- Parametrized sweep over every migrated variable name: `"true"`, `"false"`, `"1"`, `"0"`, `""`, and `"2"` expected results.
- A grep-based audit in CI or as a pytest: fail if a new `bool(int(os.getenv`, `== "1"`, or `.lower() in ("1", "true")` appears in `vllm/envs.py`.
- Run `vllm/envs.py` import plus `vllm.envs.environment_variables` access on CPU to confirm no import-time regressions.
- A GPU end-to-end run is not possible in this environment (no GPU); needs a maintainer or CI run for `VLLM_BATCH_INVARIANT` and the AITER variables.

## Risks

- Strictness breaks existing deployments that set values such as `2`, `enabled`, or typos on `== "1"` variables. Mitigation: release note, and the phase split above so the riskiest styles land last.
- Error timing: the error is raised on first access, which may be inside a request path rather than at startup for variables read lazily. Mitigation: consider validating boolean variables eagerly at engine init in a later phase.
- Overlap with #66536 and #66543: three competing implementations would produce merge conflicts across the same ~80 lines of `envs.py`. Mitigation: coordinate on one design before landing; this doc can be the basis for that discussion.
- `NO_COLOR` / `FORCE_COLOR` semantics: migrating them would change the convention-based behavior. Mitigation: excluded from this design.
- Hidden consumers: some variables are read elsewhere (`tests/ci_envs.py` still uses `bool(int(...))`, and call sites outside `envs.py` read `os.environ` directly). Those are not covered by this change and need a separate audit.
