## Summary

`MultiModuleMTPSpeculator` keeps per-request-slot caches of the last `S-1` draft inputs (`S = num_speculative_steps`). These caches are used to re-prefill tokens that a later MTP module's KV cache needs after rejections. The cache is never reset when a slot is reassigned, and the re-prefill reads are not bounded by how many entries were actually written for the current request. A new request can therefore re-prefill the previous occupant's token ids, target hidden states, and input embeddings, at the new request's positions (including negative positions).

- Neither kernel checks how many cache entries are valid for this request. `R` can be up to `S-1` even when the request has produced fewer tokens.

Concrete failure (from the issue POC, not re-run here):

1. Request A (6-token prefill, finishes) leaves slot 0 with token ids `[9005, 9006, 9007]` and hidden state `7.0`.
2. Request B is assigned slot 0. `add_request` is a no-op, so the cache is unchanged.
3. B's 2-token prefill writes only the tail: `[9005, 5001, 5100]`. Slot 0 still holds A's `9005`.
4. B's first decode rejects all 4 drafts (`R = 3`). The re-prefill reads `9005` and hidden state `7.0`, and places them at position `-1`.

## Root cause

Two independent defects combine:

1. **No per-slot reset.** Slot reuse does not clear the cache (`add_request` is not overridden).
2. **No valid-length bound.** The cache write only covers the tail of a short query, and the re-prefill reads `R = num_rejected - 1` entries without checking how many were written for the current request. Stale head entries are read as if they were valid.

Either defect alone is enough to create cross-request contamination. A reset alone would still leave stale entries when a request is shorter than the window, because the head slots are never written.

## Proposed fix

1. **Track valid tail length per slot.** Add `cached_num_valid: torch.Tensor` of shape `[max_num_reqs]`, int32, on device. This is the number of right-aligned valid entries in the window.
2. **Reset on admission.** Override `add_request(req_index)` in `MultiModuleMTPSpeculator` to set `cached_num_valid[req_index] = 0`. This is a host-side call, outside the CUDA graph, so the cost is negligible.
3. **Record writes.** In `_cache_inputs_kernel`, store `cached_num_valid[req_state_idx] = last_token_index + 1 - max(window_start, query_start)`, which is the number of tail entries written this step (at most `S-1`).
4. **Clamp re-prefill.** In both prepare kernels, use `R_eff = min(max(0, num_rejected - 1), cached_num_valid[req_state_idx])`. Read slots and positions from `R_eff`, not `R`.
5. **Keep the rest of the layout unchanged.** `num_rejected` still controls `num_input_hidden_states` and the draft query length. Only the re-prefill count changes. The kernel that computes `last_token_indices` and the draft input count must use the same `R_eff`, or the buffer layout will be inconsistent. This is the main risk (see below).

Alternative considered: clearing the cache rows in `add_request` only. This fixes the cross-request case but not the short-request case where the head is stale. Rejected as incomplete.

## Test plan

- **CPU unit test (feasible if triton is installed):** run `_prepare_input_buffers_kernel`, `_prepare_input_hidden_states_and_embeddings_kernel`, and `_cache_inputs_kernel` under `TRITON_INTERPRET=1` on CPU, with `S = 4`, `H = 8`, two slots. Cases:
  - A finishes, B reuses slot 0 with a 2-token prompt and rejects all drafts. Assert no token id from A (`>= 9000`) and no negative positions appear in B's draft inputs.
  - Full-window request (query length >= `S-1`) with `R = S-1`. Assert the re-prefill still reads the correct cached values (no regression).
  - `num_rejected = 0` and `1`: no re-prefill, no change in behavior.
  - MM path (`cached_draft_input_embeds` not None): same clamp applied to embeddings.
- **Existing tests:** `tests/v1/worker/test_gpu_target_dependent_ar_speculator.py` (from PR #66951) shows the test layout for a sibling speculator. The new test should follow that layout.
- **GPU validation (not possible here):** end-to-end MTP run with `num_speculative_tokens > 1` and a draft with more than one MTP module, checking that acceptance rate and outputs are unchanged for non-contaminated requests.

## Risks

- **Draft layout change.** Clamping `R` changes the number of draft input tokens for a request, which changes `last_token_indices`. If any kernel computes that count from `R` and another from `R_eff`, the buffers will be inconsistent. The fix must use one shared value.
- **Acceptance rate.** A request that is shorter than the window will now re-prefill fewer tokens. This is correct, but it may change acceptance metrics slightly.
- **CUDA graphs.** The count is read from device memory inside Triton kernels, so no shape changes. The host-side reset in `add_request` must not run inside a captured graph. It does not, because `add_requests` runs in eager host code.
- **Overlap with PR #66951.** That draft changes the same kernels. Implementing a second version here would conflict with it. Review of #66951 should decide the design.
- **Not verified in this worktree:** Triton is not installed here, and there is no GPU. The kernel behavior described above comes from code reading and the issue POC, not from a test run.
