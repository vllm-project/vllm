# vllm#66241: `compilation_config.backend` accepts arbitrary strings

## Summary

`CompilationConfig.backend` is a plain `str`. In `STOCK_TORCH_COMPILE` and
`DYNAMO_TRACE_ONCE` modes, any value that is not a registered torch.compile
backend is passed to `resolve_obj_by_qualname`, which does
`rsplit(".", 1)`, `importlib.import_module`, and `getattr`. A garbage value
(e.g. `"__main__.backend"`) therefore fails at engine init with a bare
`AttributeError` that does not name the config field or list valid values.

## Root cause

- `vllm/config/compilation.py:542` declares `backend: str = ""`. No validator
  constrains it.
- `vllm/config/compilation.py:1190-1197` (`__post_init__`) is the only backend
  check today. It runs only when `mode == VLLM_COMPILE`, and only allows
  `""`, `"eager"`, `"inductor"`. It does not cover the other two modes.
- `vllm/config/compilation.py:1243` `init_backend`: for `STOCK_TORCH_COMPILE`
  and `DYNAMO_TRACE_ONCE`, a value not in
  `torch._dynamo.backends.registry.list_backends()` goes to
  `resolve_obj_by_qualname` (`vllm/config/compilation.py:1281` before the fix).
- `vllm/utils/import_utils.py:119-123` `resolve_obj_by_qualname`: unpacks
  with `rsplit`, so a dotless string raises `ValueError` ("not enough values
  to unpack"); a dotted string with a missing attribute raises
  `AttributeError`. Neither names the config field.
- Callers: `vllm/compilation/wrapper.py:59` (stock torch path) and
  `vllm/compilation/wrapper.py:108` (VLLM_COMPILE path, which ignores the
  string except for the piecewise check above).

## Valid values

1. `""`: replaced by `current_platform.get_compile_backend()` in `__post_init__`.
2. Any name in `list_backends(exclude_tags=())` (torch registry, e.g.
   `eager`, `inductor`, `aot_eager`, plus plugin entry points).
3. Fully qualified `package.module.attr` names, for STOCK/DYNAMO modes only.
4. For `VLLM_COMPILE`: only `""`, `eager`, `inductor` (existing check).

Currently accepted but invalid in STOCK/DYNAMO: any dotless non-registry name
(`"foo"`, `"__main__"`), empty segments (`"a..b"`), non-identifier segments
(`"1x.y"`), and dotted names that do not import (`"__main__.backend"`).

## Proposed change (implemented in commit 18ca3d4b6a)

1. Config construction (`__post_init__`): for STOCK/DYNAMO modes with a
   non-empty backend that is not a registered torch backend, require at least
   two dot-separated Python identifiers. Otherwise raise `ValueError` that
   names `compilation_config.backend`, the mode, and the valid forms.
2. `init_backend`: wrap `resolve_obj_by_qualname` and re-raise
   `ImportError`/`AttributeError`/`ValueError` as a `ValueError` naming the
   field, with the original error chained.
3. Factor the torch registry lookup into `_torch_compile_backends()`.

Deliberately not done: importing the target at config construction. That
runs user code in the config-building process (and may not be importable in
the process that builds the config). So a syntactically valid but missing
target, such as `"__main__.backend"`, still passes construction and fails in
`init_backend`, now with a named `ValueError`.

## Test plan

- `tests/compile/test_config.py`, three CPU tests:
  - malformed names (`not_a_backend`, `__main__`, `a..b`, `1x.y`) raise
    `ValueError` at construction;
  - `eager` and a qualified `my_pkg.mod.my_backend` are accepted;
  - an unimportable qualified name makes `init_backend(MagicMock())` raise
    `ValueError` mentioning `compilation_config.backend`.
- Not yet run: pytest needs test deps (`tblib`, `psutil`, ...) not installed
  in this environment. Run `pytest tests/compile/test_config.py -k stock_compile`
  after installing test requirements.
- Manual repro from the issue on a GPU host: `LLM(..., compilation_config=
  {"mode": 1, "backend": "__main__.backend"})` should now fail with the named
  `ValueError`, not a bare `AttributeError`.

## Risks

- Behavior change for STOCK/DYNAMO users who pass a dotless backend name that
  is not in the torch registry at config time. Such values already failed at
  init, so the only change is an earlier, clearer error. Torch backends that
  are registered lazily after config construction would be rejected early;
  `list_backends` includes entry points, which mitigates this, but was not
  verified across torch versions.
- `_torch_compile_backends()` imports `torch._dynamo` during config
  construction for STOCK/DYNAMO modes (previously imported only at init).
- `self.mode.name` assumes `mode` has been normalized to `CompilationMode`
  by the field validator (`vllm/config/compilation.py:1004`). Not verified
  for every construction path.
- No user-facing docs
  changed; the field docstring at `compilation.py:542` already describes the
  accepted forms.
